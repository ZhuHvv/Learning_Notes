## 商城购买：第 01—10 题

### 第 01 题：单商品购买完整链路

**原始问题**

> 一次商城单商品购买请求从到达服务器，到扣除货币、发放商品，再到返回客户端，实际经过哪些服务和处理环节？

**你的回答**

> 首先gate网关服务收到客户端的购买请求，发送到master后转发给shop商店服务，由于我们批量购买和单商品购买调用的是同一接口，所以需要把单商品包装成商品列表，然后进行一系列的限购等条件检验，如果检验通过则调用rpc请求entity服务对用户数据进行处理，包括元宝扣除、物品发放等，结果返回给shop服务，shop收到响应后，对成功结果需要做限购等条件的数据更新，之后调用gate服务向客户端返回结果。过程中出现限购条件不满足或用户元宝不足等购买失败等情况则直接返回

**优劣点**

- 优点：服务路由、接口复用、资产修改归属、限购更新时机和失败返回都说明了，正常链路较完整。
- 不足：没有展开资产落库、扣款发货原子性；本题未继续追问这些内容，属于尚未核实，不是已确认错误。
- 关键边界：Shop 限购更新发生在 Entity 成功响应之后，存在需要后续考察的跨服务窗口。

**参考回答——现有实现**

> 请求经过 Gate、Master 到 Shop。Shop 将单商品转换为商品列表，复用批量购买入口，检查限购等条件。通过后调用 Entity，由 Entity 处理元宝扣除和物品发放。Shop 收到成功响应后更新限购等状态，再通过 Gate 返回结果。校验失败或资产不足则返回失败。资产操作与限购更新分属不同处理阶段；是否存在数据库事务或其他持久化保障，需要另外确认。

### 第 02 题：限购并发与玩家锁

**原始问题**

> 你提到限购校验在 Shop 完成，而限购数据要等 Entity 扣款、发货成功后才更新。如果同一玩家同时发来两次购买请求，而限购只剩一次，你们现有实现如何处理？请结合简历中的玩家粒度 Redis 分布式锁，说明锁从哪里开始持有、到哪里释放。

**你的回答**

> 我们通过用户级别的redis分布式锁来保证同一用户的购买请求串行化处理。在收到购买请求后，利用SETNX在redis中添加以用户id为键的锁，并且后续的sql操作也需要根据用户当前数据进行条件判断。用这种办法减少同用户购买的竞争

**优劣点**

- 优点：锁粒度按用户，避免不同玩家互相阻塞；说明了请求开始阶段加锁。
- 不足：“保证串行化”缺少租约有效期等前提；没有在本题直接说明释放位置。SQL 条件的具体内容和数据归属没有展开，不能视为已经证明的业务兜底。
- 事实边界：说了 SETNX 和 TTL，不等于已确认获取锁与设置 TTL 是两个独立命令，也未确认是否续租。

**参考回答——结合后续回答整理现状**

> 请求进入 Shop 后，先获取以玩家 ID 为粒度的 Redis 锁，再执行校验、Entity RPC 和 Shop 后续处理，请求结束时尝试释放锁。在租约有效的情况下，同一玩家的购买请求可以受这把锁协调。后续 SQL 的条件判断需要具体说明，不能笼统认定它覆盖了锁过期或跨服务失败的问题。

### 第 03 题：加锁失败与解锁时机

**原始问题**

> 假设同一玩家的两次购买请求分别到达两个 Shop 实例，第一个请求已经拿到锁并向 Entity 发起 RPC，第二个请求此时加锁失败，你们实际会怎样处理第二个请求？第一个请求的锁又会在什么时机释放？

**你的回答**

> 第二个请求会每隔50ms尝试重新获取锁，如果尝试次数超过1000次就返回失败。
>
> 第一个请求的锁会在shop服务处理该请求执行结束时尝试释放

**优劣点**

- 优点：重试间隔、次数、失败行为和释放位置具体。
- 不足：没有说明等待与请求超时的关系，这一点本题未核实，不应认定实现一定没有控制。
- 原理边界：50ms × 1,000 是约 50 秒的重试间隔量级，实际还包含 Redis 调用和调度耗时。

**参考回答——现有实现**

> 第二个请求每隔 50ms 重试获取锁，超过 1,000 次返回失败；第一个请求在 Shop 处理结束时尝试释放。这个策略允许等待前一个请求完成，但最长等待较长。它与 RPC 超时、客户端等待时长是否协调，需要结合实际配置进一步确认。

### 第 04 题：TTL 过期与旧请求解锁

**原始问题**

> 按照你给出的参数，第二个请求可能等待约 50 秒。你们给锁设置了多长的过期时间？如果第一个请求尚未执行结束，锁却已经过期并被第二个请求重新获取，此时第一个请求结束时会怎样释放锁？

**你的回答**

> 锁的ttl是60秒
> 这种情况下两个请求都会处于执行阶段，第一个请求尝试释放锁，但是我们给每次加锁会给一个唯一的token作为凭证，所以旧请求释放时发现token对不上就释放不了新请求加的锁

**优劣点**

- 优点：正确识别两次请求可能同时执行；理解 token 用于区分锁持有者，旧请求不应删除新锁。
- 不足：本题回答没有明显错误。token 解决的是误解锁，不能恢复已经失去的业务互斥。

**参考回答——现有实现与保障边界**

> TTL 是 60 秒。如果旧请求执行超过租约时间，新请求可能获取锁，此时二者可能同时执行。每次加锁使用唯一 token，旧请求解锁时必须核对 token；不一致就不删除。这个机制保护新锁不被旧请求误删，但无法阻止旧请求继续修改业务数据。

### 第 05 题：检查 token 与删除的原子性

**原始问题**

**你的回答**

> 通过redis脚本原子性的执行查和删，先获取锁，检查value是否与提供的token相等，如果相等则删除锁，否则不操作

**优劣点**

- 优点：说明了比较和删除必须在同一段 Redis 脚本中原子执行，回答正确。
- 不足：“先获取锁”用词容易被理解为重新加锁；这里实际应表述为读取锁键的 value。

**参考回答——现有实现**

> 用 Lua 脚本读取锁键的 value，与本次请求持有的 token 比较。相等才删除，否则不操作。比较和删除在一次脚本执行中完成，避免拆成两个客户端命令后被其他请求插入。脚本防止误删新锁，不保证旧业务在租约失效后停止执行。

- 不足：没有说明跳过后的数据新鲜度与长时间卡住的监测，这些未被继续追问，不能认定实现一定缺失。
- 成立条件：所有刷新入口必须使用同一榜单对应的锁。

**参考回答——现有实现**

> 定时触发后先尝试获取该榜单的锁。如果上一轮仍持有锁，本轮就直接跳过，不等待也不排队；成功获取才执行刷新。这样在当前锁覆盖范围内避免同榜单并发刷新。代价是慢任务可能让快照在更长时间内不更新，需要结合刷新耗时和数据新鲜度观察运行情况。

### 第 28 题：快照替换与并发读

**原始问题**

> 如果客户端正在读取旧榜单快照，刷新协程此时完成了新快照，你们具体怎样替换它，保证并发查询安全？你说的“删除旧对象”在 Go 代码中实际是什么操作？

**你的回答**

> 我们为每个榜单创建一个榜单对象，其内部保存了属于他的快照。我前面说的不太准确，是直接将内部快照对象赋值为新创建的榜单快照对象。
> 当前方案并没有做这方面并发安全考虑，优化的话可以通过读写锁来管理

**优劣点**

- 优点：主动纠正了对象生命周期的描述，承认同步缺失，并提出有效的改进方向。
- 不足：若读写发生于不同 goroutine，直接无同步读写快照引用存在数据竞争；构建新对象本身不能替代安全发布。

**参考回答——现状与假设改进**

> 当前实际是替换榜单对象中的快照引用，没有显式同步，因此并发读取与替换存在风险。改进可以先独立构建新快照，再在写锁内替换引用；读方通过读锁取得引用。如果发布后的快照完全只读，读方可以在安全取得引用后释放锁，再读取对象内容。旧对象在不再被任何地方引用后由 GC 回收，不需要手动删除。若快照内部仍会修改，还需要覆盖这些修改的同步规则。

### 第 32 题：观战关系的断线与重建

**原始问题**

**你的回答**

> 首先，除了这个映射之外，每个用户的session对象中有一个属性存储观看的比赛id；当发生断连，旧gate会根据用户id做断连的连接处理并且根据这个属性在比赛-观众数组映射中移除这个用户。
> 建立新连接时不会自动进入原本观赛。后续用户重新进入观赛才会更新

**优劣点**

- 优点：指出 session 上保存比赛 ID，可用于反向清理；明确重连不自动恢复观战，是一个具体业务规则。
- 不足：本轮“根据用户 ID 清理”可能让人误以为只按用户删除，新旧连接的区分需要下一题补充。加入观战时的具体通知链路未说明。

**参考回答——结合后续澄清的现有实现**

> session 保存当前观看的比赛 ID。进入观战后，把对应 session ID 加入该比赛的观众集合。断线时通过连接回调中的 session ID 找到旧 session，再根据它保存的比赛 ID 清理对应观众记录。新连接不会自动恢复观战，用户再次进入后才建立新 Gate 上的关系。

### 第 33 题：旧连接回调与新 session

**原始问题**

> 假设玩家重连到了同一个 Gate，新 session 已经进入观赛，旧连接的断开回调才被处理。你提到断连处理是根据用户 ID 执行的，现有实现如何区分新旧 session，避免把新连接的观赛记录一起移除？

**你的回答**

> 这里有区别，gate维护的还有两个映射，一个是sessionid到session对象的映射，一个是用户id到session对象的映射。
> 当发生断连时，会在回调中得到连接对应的session_id，然后通过映射得到session对象，对象中有所属的用户id。
> 清理用户id对应的session对象时会核对是否指向就对象。

**优劣点**

- 优点：给出了两个索引的作用；清理用户当前连接映射时核对对象身份，能够解释如何避免旧连接回调直接删除新连接映射。
- 不足：这一题尚未说明比赛观众集合怎么删，因此继续追问该部分。
- 原文说明：“就对象”按原文保留，结合上下文理解为“旧对象”。对象比较与删除本身也应处于正确的同步范围，但本题未核实该细节。

**参考回答——现有实现**

> 断开回调带的是旧连接的 session ID，先据此定位旧 session，而不是直接拿用户 ID 清理当前连接。删除用户 ID 到 session 的映射时，要确认映射仍指向这个旧 session；如果已经指向新 session，就保留。这样能区分同一个玩家的两个连接实例。比赛观众集合另按 session ID 清理。

### 第 36 题：广播读锁的持有范围

**原始问题**

> 广播时，这把读锁具体从哪里开始持有、到哪里释放？向各个 session 发送消息时是否仍持有读锁，如果某个 session 的发送发生阻塞，会怎样影响观众进入和断线清理？

**你的回答**

**优劣点**

- 优点：清楚说明锁只覆盖集合读取与复制，发送在解锁后进行，避免慢发送长时间阻塞集合写入，是有效的锁粒度设计。
- 不足：本题没有明确错误。复制后 session 已失效、发送队列满等处理未继续考察，不应记为实现缺失。
- 保障边界：复制得到的是某个时刻的成员快照，不保证发送时连接仍然存在；这与 map 访问是否安全是两件事。

**参考回答——现有实现与边界**

> 广播先持有读锁，根据比赛 ID 找到观众集合，把 session ID 复制到局部列表，然后立即释放锁，后续逐个发送不再持有这把集合锁。这样某个发送阻塞不会因为占着这把读锁而阻止观众加入或断线清理。复制后连接可能变化，发送阶段如何处理失效 session 是另一个问题，本轮没有提供具体实现。

### Lobby 职责与单实例部署

#### 补充 L01　项目中的 Lobby 负责什么

**面试参考回答**

> Lobby 维护玩家在大厅侧的状态，协调队伍、房间、匹配、赛事和对局。它知道玩家当前在哪支队伍、哪个房间、是否正在匹配、绑定了哪一局，以及这局由哪台 Game 承载。开局前用这些状态组织玩家和分配 Game，重登时提供原对局信息，对局结束或 Game 异常时处理大厅状态的收尾。

| 场景 | Lobby 的具体工作 |
| --- | --- |
| 上线、断线与重登 | 维护用户 ID、Gate 会话和大厅用户对象的关系，处理连接变化，提供玩家当前对局绑定查询。 |
| 队伍与好友房 | 管理邀请、加入、退出、成员状态、房间座位、准备和请求开局。 |
| 匹配与开局 | 按玩法检查进入条件，维护匹配队列和匹配结果，选择 Game 节点，提交创建对局请求。 |
| 对局生命周期 | 记录 Game 节点和对局 ID，接收运行、结束等状态通知，更新玩家、队伍和房间状态。 |
| 赛事与观战 | 接收赛事服的分组、开赛、结果、下一场等消息，维护观众所属比赛，发起比赛通知。 |
| 依赖节点异常 | 监听 Game、AI、Entity 的服务事件，执行对应的大厅侧处理。例如 Game 断开后通知相关玩家异常结束并清理绑定。 |
| 公告转发 | 收到服务器公告后转给可用 Gate，由 Gate 向符合条件的会话投递。 |

#### 补充 L02　一次 2v2 匹配怎样经过各个服务

**面试参考回答**

> 玩家发起匹配，Gate 把 `CReqMatch` 转给 Lobby。Lobby 根据会话找到玩家，检查当前队伍、匹配和对局状态，再进入对应玩法的匹配器。匹配成功后，Lobby 选择可用 Game 节点，生成对局 ID 并登记，向该节点发送建局请求。Game 返回成功后，Lobby 记录玩家与对局的绑定。进入对局后，Gate 根据会话里的 Game 绑定转发局内操作。结束时 Game 通知 Lobby，Lobby 清理对应玩家绑定并更新队伍、房间状态，玩家资产、任务等结算由 Entity 的对应处理完成。

**建局失败时的边界**

Lobby 的建局回调遇到 RPC 错误或 Game 返回失败，会移除刚登记的对局。若面试官继续问“超时是否说明 Game 没有创建成功”，需要讨论请求执行结果不确定的情况，并进一步检查 Game 是否能按同一对局 ID 查询或去重。当前整理核对了 Lobby 回调的清理逻辑，跨服务建局的完整恢复机制仍需专门核实。

#### 补充 L04　为什么当前 Lobby 采用单实例

**面试参考回答**

> 当前实现把队伍、房间、匹配队列和玩家对局绑定集中在 Lobby 的进程内存中。这些状态涉及多个玩家，例如同一支队伍的加入、退出和开始匹配，都需要读写同一个队伍对象。使用一个 Lobby，可以直接维护同一份数据，减少跨节点定位、同步和迁移的复杂度。Gate 也按单节点策略访问 Lobby。相应代价是故障会影响大厅业务，容量也受单实例处理能力约束。

| 本地状态 | 主要表示 |
| --- | --- |
| 玩家与会话 | `userManager.id2user`、`ss2user`。 |
| 队伍与房间 | `TeamManager.teamMap`、`RoomManager.roomMap`。 |
| 匹配队列及结果 | 玩法匹配器中的玩家匹配表和匹配结果。 |
| 对局及玩家归属 | `GameManager.gameMap`、玩家对象中的 `game`。 |

每个 Gate 注册 Lobby 时使用 `WithLoadBalanceSingleton`。它首次选择可用列表中的第一个节点并缓存 ID，后续转发沿用该 ID。当前实现的节点事件回调为空。Entity 重登查询也直接取可用 Lobby 列表的第一个节点。

项目启动脚本同时只启动一个 Friend、Email 等实例。面试里描述“只有 Lobby 单点”时，应说明所指的线上环境及核实依据。仓库脚本能证明的是脚本计划启动的实例数。

#### 补充 L05　再加一个 Lobby，按玩家 ID 哈希分流，为什么还需要改业务

**面试参考回答**

#### 补充 L06　为什么 Game 可以部署多个

**面试参考回答**

> Game 可以按一桌对局划分。Lobby 开局时选定节点，同桌玩家后续的局内操作通过绑定路由到该节点，因此每台 Game 可以管理自己承接的若干桌。Lobby 的状态则跨越开局前的多个玩家和队伍。扩展 Lobby 时，需要为队伍、房间和匹配池确定归属，并把相关请求送到负责它们的节点。

#### 补充 L07　Lobby 挂了，玩家会受到哪些影响

**面试参考回答**

> 需要按玩家当时所处的流程判断。正在组队或匹配的玩家依赖 Lobby 的内存状态，进程退出会丢失这部分现场。已经进入对局、连接和 Game 绑定仍然有效的玩家，其出牌消息由 Gate 直接发到 Game，这条转发路径可以继续工作。此时若玩家断线重登，Entity 查询原对局绑定的流程依赖 Lobby，会受到影响。对局结束后的大厅收尾也需要考虑通知失败后的恢复。

另一个方向也值得准备。Game 节点发生断连时，存活的 Lobby 会遍历登记在该节点上的对局，通知相关玩家异常结束，清理绑定并移除对局记录。这体现了 Lobby 的跨对局管理职责。

#### 补充 A02　Entity 内的 Activity、Task 组件与独立 Activity 服务如何分工

**面试参考回答**

> Entity 内的 Activity 组件处理玩家活动的开放、展示、通用活动状态，以及活动和任务的关联。Task 组件负责行为匹配、进度、完成、重置和领奖状态。独立 Activity 服务承接具体活动玩法的请求、规则校验、状态更新和算奖，例如抽奖轮次、奖品权重和次数限制。它需要改变玩家资产时，会请求该玩家所属的 Entity 扣券或发奖。

#### 补充 A15　扣券发奖成功，保存抽奖记录失败，会怎样

**现有实现边界**

`TaskRaffle.draw()` 先请求 Entity 扣券并发奖，成功后更新抽奖次数等状态，再调用 `p.save()`。当前这处调用忽略了保存返回错误。资产变更和活动状态保存分步进行，因此存在奖品已经发出、活动记录尚未可靠保存的失败窗口。重试时能否再次发奖，取决于恢复后的状态和实际去重机制。

**面试参考回答**

> 我会沿实际提交顺序检查。这个抽奖流程包含资产处理和活动状态保存两个请求，玩家锁能够限制同一时刻的并发进入。要实现故障后安全重试，还需要为一次抽奖保留稳定的业务标识和已确定的结果，让资产执行与活动记录都能识别重复处理，并设计待完成状态、重试和查询恢复。

消息中的 `GetID` 在已检查的资产处理里用于日志。判断幂等能力，要找到该标识参与查询、唯一约束或原子去重的执行位置。保存 RPC 返回、标记 dirty、数据库更新分别处于不同阶段。

源码入口见 [资产处理与后续保存](D:/Codes/vxsgs/sgs_wx/activity/activity_task_raffle.go:182)、[V2 保存请求处理](D:/Codes/vxsgs/sgs_wx/entity/entity_msg_handler.go:5450)、[玩家组件保存](D:/Codes/vxsgs/sgs_wx/entity/userdb/db.go:679)。

#### 补充 A16　自动抽奖怎样处理通知丢失、抢锁失败和服务重启

**现有入口与改造考虑**

当前 `OnAddProp()` 获取玩家锁失败时直接返回。它适合承接现有道具变化回调，但要让“发券后最终自动抽奖”成为可靠业务承诺，需要补充失败后能够再次执行的依据。

**面试参考回答**

> 如果需求要求最终一定完成自动抽奖，我会记录可恢复的待处理业务状态，使用稳定标识关联一次发券或抽奖，并让重复执行返回同一个结果。抢锁失败、RPC 超时或服务重启后，可以据此查询进度并继续完成。任务发券、券消费、开奖结果和客户端展示各自需要明确成功状态。恢复时读取已确定的结果，避免因为重试重新抽取奖品。

这是对自动抽奖方案的可靠性设计。需要落实到数据结构、实际提交接口和恢复任务后，再通过重复通知、并发触发、保存失败和进程重启测试验证。

### 002 · 助手

我们先从第一阶段的核心认识开始。

**消息队列首先改变的是：生产者与消费者是否必须在同一时刻完成协作。**

假设订单创建后，需要发送通知和更新统计。同步调用时，订单服务必须等待下游响应，下游的延迟和故障会进入订单请求的执行链路。

引入消息系统以后，订单服务可以先把事件交给消息系统，由下游稍后处理。这带来了三个需要单独判断的完成时刻：

- 订单已经写入业务数据库。
- 订单事件已经被消息系统接受。
- 下游已经完成通知或统计更新。

这三个时刻之间存在间隔，也存在故障窗口。例如，数据库提交成功后，进程可能在发送消息之前崩溃。后面学习 Outbox、CDC 和一致性方案，就是为了解决这一类具体问题。

**缓冲能力也有明确的容量边界。**

假设每秒进入 10,000 条消息，消费者只能处理 6,000 条，那么积压每秒增加 4,000 条。持续 10 分钟，就新增 240 万条积压。

队列能让下游按自己的速度处理，但持续超载仍需要扩容、限流或减少工作量。而恢复后的消费能力还必须高于新的流入速度，才有余量消化历史积压。之后所有“削峰”和“积压治理”的分析，都要回到这个收支关系。

接着是理解 Kafka 最重要的一步：**它的核心抽象是可保留、可重放的分区日志。**

在常规 Consumer Group 模型下，同一份日志可以由多个消费组独立读取，各自记录进度。某个消费组读过消息，并不直接触发该消息删除；数据保留由日志清理策略管理。这使通知服务、统计服务以及后来加入的数据处理服务能够使用同一条事件流。[Kafka 设计文档](https://kafka.apache.org/41/design/design/)

由此可以推导出后续架构：

- 日志需要承载更多读写，于是考虑**分区与分布式部署**。
- 节点可能故障，于是需要**副本与恢复机制**。
- 消费者会暂停或崩溃，于是需要**独立保存消费进度**。
- 网络可能丢失响应，于是需要处理**结果未知、重试与重复**。
- 一次业务处理可能关联多条记录，于是进一步需要研究**事务及其保证范围**。

接下来就从“设计一个最简单的单机持久化消息系统”开始，依次加入独立消费进度、分区和副本，推导出 Kafka 的整体架构。这样后续看到具体类、协议字段和磁盘文件时，都能知道它们究竟在解决哪个问题。

### 006 · 助手

我们先解决第一个问题：**如果让你设计一个能够保存消息、允许消费者稍后读取的系统，最简单的实现是什么？**

这一讲只讨论单机，不引入分区、副本和集群。我们先设计一个教学模型，再理解它为什么会逐渐演化成 Kafka 的日志模型。

假设订单服务不断产生“订单已创建”事件，通知服务负责读取事件并发送通知。

最初的数据路径很简单：

```text
订单服务 → 消息服务 → 通知服务
 生产者     Broker     消费者
```

这里的 Broker 就是负责接收、保存和提供消息的服务进程。

**首先，要让消息能够等待消费者。**

最容易想到的实现，是 Broker 在内存里维护一个队列：

```text
队头 → [订单 A] [订单 B] [订单 C] ← 队尾
```

生产者把消息放到队尾，消费者从队头取出。这样即使消费者暂时很慢，生产者也可以继续发送，消息先在队列里等待。

但是，内存队列有两个直接的问题：

- Broker 进程退出后，内存中的消息消失。
- 消费者长时间跟不上，消息会耗尽内存。

如果我们希望消息能在进程重启后继续存在，就需要把消息保存在文件里。

**接下来，最简单的文件组织方式是追加日志。**

每来一条消息，就把它写到文件末尾：

```text
文件开头
┌────────┬────────┬────────┬────────┐
│ 订单 A │ 订单 B │ 订单 C │ 订单 D │ → 继续追加
└────────┴────────┴────────┴────────┘
```

这里的“日志”指的是**按顺序追加的数据记录**，不是给开发者查看的运行日志。

为什么先选择追加？

因为我们暂时只需要完成两个动作：保存新消息，以及按顺序读取历史消息。追加文件就能支持这两个动作，不需要每次写入时寻找空位，也不需要搬动已有记录。

但真实文件只是一串字节，没有图中天然存在的方框。系统必须知道一条消息从哪里开始、在哪里结束。

我们可以先设计一种简单记录格式：

```text
[消息长度][消息内容][校验信息]
```

读取时，先读长度，再读取对应数量的字节，最后检查记录是否完整。这个设计也为处理“写到一半突然崩溃”提供了依据。

这是教学用格式，Kafka 的实际实现还涉及消息批次、更多字段和版本，我们会在存储章节拆开。

还有一个必须从现在就区分的概念：

> **调用文件写入成功，不一定意味着数据已经持久化到存储设备。**

普通缓冲文件 I/O 通常先把数据写入操作系统的页缓存，之后再回写到设备。因此，Broker 进程崩溃与整台机器断电，是不同的故障条件。后面讨论刷盘与副本时，我们会明确每种“写成功”到底保证什么。

现在暂时假设，消息已经按照我们要求的持久化条件保存成功。

**文件能够保存消息以后，还需要给消费者一个定位方法。**

我们给每条消息分配一个递增编号，称为 offset：

| offset | 消息 |
|---|---|
| 0 | 订单 A |
| 1 | 订单 B |
| 2 | 订单 C |
| 3 | 订单 D |

消费者可以请求：“从 offset 2 开始，给我读取一批消息。”

注意两个区别：

- offset 是消息在这条日志中的**逻辑位置**。
- 文件位置是记录在文件中距离开头多少字节的**物理位置**。

它们不是一回事。消息长短不同，不能直接用 offset 乘一个固定长度找到文件位置。后面学习索引，就是解决“如何从逻辑位置高效找到物理位置”。

现在我们已经得到一个很小的消息系统：

```text
生产者：向日志末尾追加消息
Broker：保存日志，支持按 offset 读取
消费者：记录自己读到哪里
```

**这时出现了一个关键选择：消息读完后，要不要删除？**

如果只有通知服务一个消费者，读完就删除看起来很自然。

但现在统计服务也想使用订单事件：

```text
                  ┌→ 通知服务
订单事件日志 ──────┤
                  └→ 统计服务
```

通知服务处理得快，统计服务处理得慢。如果通知服务读完就把消息删除，统计服务就无法再读取它。

一种办法是给每个业务保存一份独立的消息。另一种办法是：**日志保留一份，每个业务各自保存消费进度。**

例如：

```text
日志：        [0:A] [1:B] [2:C] [3:D]

通知服务：下一条需要处理的是 3
统计服务：下一条需要处理的是 1
```

这样，通知服务向前推进，不会改变统计服务的位置。新业务也可以在数据仍然保留的范围内，从较早的位置开始读取。

由此我们得到两个相互独立的状态：

| 状态 | 回答的问题 |
|---|---|
| 日志中的消息数据 | 系统保存了哪些事件？ |
| 每个业务的消费进度 | 这个业务处理到了哪里？ |

这就是理解 Kafka 常规消费模型的基础：**消息存储与消费进度分开管理。**

同时，日志也不能无限增长。系统需要另外制定保留规则，例如保留一定时间，或者限制保留的数据量。这意味着消费者如果落后太久，它尚未读取的数据也可能已经被清理。消费进度不会自动替它锁住所有历史数据。

**最后，还要把“读取过”与“处理完成”分开。**

假设通知服务已经从 Broker 读到了订单 C，但还没有发送通知，此时它崩溃了。

如果我们把“读取过”直接当成“处理完成”，重启后就可能跳过 C。

所以，至少在概念上，要区分：

- **读取位置**：客户端已经读取到了哪里。
- **已提交的消费进度**：发生故障后，系统应该从哪里恢复。

在本讲的模型里，约定提交值表示“下一条需要处理的消息位置”。例如：

```text
读取了：       offset 0、1、2
完成了：       offset 0、1
提交的进度：   2
```

重启后从 2 开始，订单 C 仍然需要处理。

但这里又出现了一个故障窗口：

```text
完成订单 C 的通知
        ↓
提交消费进度 3
```

如果通知已经发送成功，进程却在提交进度之前崩溃，重启后仍会从 2 开始，订单 C 就可能再次触发通知。

到这里，重复处理已经自然地出现了。它来自**业务处理和消费进度提交是两个独立动作**。后续的交付语义、幂等和事务，都会围绕这个边界展开。

这一讲先停在这里。我们已经从一个内存队列推导出了：追加日志、消息边界、offset、独立消费进度，以及故障恢复时的重复问题。

### 008 · 助手

对。**已提交进度是 3，恢复后会从 offset 3 开始，因此订单 C 会被跳过。** 即使 C 仍然保存在日志里，这个消费者也不会按正常恢复流程再处理它。

这说明，“消息有没有丢”需要明确是哪一层：这里存储中的消息可以完好无损，但业务处理已经遗漏了。

把两种执行顺序放在一起，就能看出问题：

| 执行顺序 | 两步之间崩溃的结果 |
|---|---|
| 先提交进度，再处理业务 | 恢复后跳过尚未处理的消息，可能遗漏 |
| 先处理业务，再提交进度 | 恢复后重新处理已完成的消息，可能重复 |

**仅仅调整这两个动作的先后顺序，无法同时消除遗漏和重复。** 想继续解决，就需要引入新的机制，例如让重复处理不产生额外效果，或者在适用范围内把处理结果与消费进度原子地提交。这部分后面会系统展开。

现在，我们的单机模型已经有了三个核心部分：

```text
追加日志：保存发生过的事件
消费进度：保存各业务的处理位置
保留策略：决定历史数据何时清理
```

接下来需要解决的是容量问题：当一条日志承载不了全部读写时，如何把数据拆开。由此就会引出 Kafka 的 **Partition（分区）**，以及它与并行度、顺序保证之间的关系。

### 010 · 助手

上一讲，我们得到了一条可以持久化的日志，以及独立保存的消费进度。现在继续解决：**一条日志的处理能力不够时，怎样扩展？**

先假设所有订单事件都写入同一条日志：

```text
订单日志：[A创建] [B创建] [A付款] [C创建] [B付款] …
```

这条日志不断增长，写入流量、存储容量和消费工作量，都可能成为瓶颈。即使换更强的机器，单机资源仍然有上限。

一个自然的想法是：**把订单分成几组，每组使用自己的日志，各自追加和读取。**

```text
订单事件
  ├─ P0：[A创建] [A付款] …
  ├─ P1：[B创建] [B付款] …
  └─ P2：[C创建] [C付款] …
```

这里的 P0、P1、P2，就是三个 **Partition，分区**。在 Kafka 中，`orders` 这样的 Topic 表示一类消息，而 Topic 内部可以包含多个分区。消息发送到某个 Topic，最终会追加到其中一个分区。[Kafka 官方概念说明](https://kafka.apache.org/41/getting-started/introduction/)

注意，分区保存的是拆分后的不同消息；同一份数据保存多份，则属于后面要讲的副本机制。

**分区带来的关键变化，是把一条日志变成多条可以独立工作的日志。**

暂时忽略副本，我们可以这样放置：

| Broker | 保存的分区 |
|---|---|
| Broker 1 | P0 |
| Broker 2 | P1 |
| Broker 3 | P2 |

于是，不同分区的读写可以利用不同机器的 CPU、磁盘和网络资源。一个 Broker 也可以保存多个分区，分区数并不需要等于 Broker 数。

但增加分区只是提供了并行的条件。假如绝大多数消息仍然进入 P0，那么 Broker 1 仍然可能过载，另外两台却很空闲。**能否扩展，还取决于消息是否分布合理。**

接下来，要重新理解 offset。

拆分之后，每个分区都维护自己的 offset：

```text
P0：[0:A创建] [1:A付款] [2:D创建]
P1：[0:B创建] [1:B付款]
P2：[0:C创建] [1:C付款]
```

P0 的 offset 1 与 P1 的 offset 1 是不同记录。因此，在一个 Kafka 集群内，定位消息需要：

```text
Topic + Partition + Offset
```

消费进度也随之变成“每个分区各自一个位置”：

```text
通知业务的已提交进度：
P0 → 2
P1 → 1
P2 → 2
```

沿用上一讲的约定，这表示恢复时分别从 P0 的 2、P1 的 1、P2 的 2 开始读取。整个 Topic 没有一个能替代这些位置的统一 offset。

**多条日志能够独立推进，也意味着它们之间没有天然的总顺序。**

例如：

```text
P0：[A创建]
P1：[A付款]
```

假设读取 P0 的消费者正在暂停，读取 P1 的消费者正常运行，那么业务可能先处理“A付款”，之后才处理“A创建”。

即使生产者先发送了创建事件，也不能仅凭两个分区里的 offset，推导出跨分区的处理顺序。Kafka 的日志顺序保证以分区为边界。[Kafka 分区与顺序说明](https://kafka.apache.org/41/getting-started/introduction/)

所以，如果业务要求同一订单的事件按顺序处理，就需要让它们进入同一个分区。

常见做法是把订单 ID 作为消息的 **key**，由分区策略决定目标分区。教学上可以先理解成：

```text
分区编号 = hash(订单ID) % 分区数量
```

这只是帮助理解的简化公式，具体客户端算法以后再展开。

在分区数量、key 的编码和分区策略保持一致的条件下，同一个订单就会被稳定地映射到同一个分区：

```text
订单 A → P0：[A创建] [A付款] [A发货]
订单 B → P1：[B创建] [B付款]
```

但同一分区仍然只是顺序处理的基础。完整链路还要求：

- 生产端按期望顺序组织发送，正确处理重试。
- 消费端保持相关消息的处理顺序。

例如，消费者顺序读到了“创建”和“付款”，却交给两个线程同时执行，付款操作仍可能先完成。**日志中的顺序与业务操作的完成顺序，需要分别保证。**

现在来看消费端如何利用多个分区。

上一讲的“通知业务”，可以运行多个消费者实例共同处理消息。Kafka 用 **Consumer Group，消费组**，把这些实例组织为一个协作整体。

在常规消费组的稳定分配下，同一个分区只交给组内一个消费者负责；一个消费者可以负责多个分区。假设大家都订阅同一个三分区 Topic，可能得到：

| 组内消费者数量 | 一种分配结果 |
|---|---|
| 1 个 | C1 负责 P0、P1、P2 |
| 2 个 | C1 负责 P0、P1；C2 负责 P2 |
| 3 个 | C1、C2、C3 各负责一个分区 |
| 4 个 | 三个消费者各负责一个，另一个没有该 Topic 的分区 |

因此，对这个 Topic 而言，增加到第四个消费者，不能继续通过分区分配提高并行度。消费者内部当然还可以并发处理，但那需要自己解决顺序和进度提交的问题。[Kafka 消费模型设计](https://kafka.apache.org/41/design/design/)

不同业务则使用不同消费组：

```text
orders 的同一份日志
    ├─ 通知组：C1、C2 协作，保存通知组的进度
    └─ 统计组：C3、C4 协作，保存统计组的进度
```

由此可以把两个概念连起来：

**组内分担工作，组间独立读取。**

如果通知和统计都需要读取全部订单事件，就应分别建立消费组；把它们放在同一个组里，会让它们分担分区，无法自然实现“两种业务各处理一遍”。

分区设计还有一个重要取舍：**顺序要求越集中，能够拆开的工作就越少。**

按订单 ID 分区时，不同订单可以并行处理；如果所有消息都使用同一个 key，它们可能集中到一个分区，其他分区无法替它分担工作。

所以，设计 key 前应该先明确：“哪些事件之间确实需要顺序？”订单系统通常关心同一订单的状态演进，并不需要让订单 A 的付款与订单 B 的创建排出一个全局顺序。

我们先用一个场景检查这个取舍：

**一个 Topic 有 6 个分区，通知消费组也有 6 个消费者，但 80% 的消息因为使用了同一个 key，都进入 P0。此时把消费者增加到 12 个，能明显缓解 P0 的积压吗？为什么？**

### 012 · 助手

我们先停在这里，把这些概念放进同一个例子里。上一段把“消息怎么存”和“谁来处理消息”一起展开，节奏太快了。

假设我们有一个电商系统：**订单服务产生订单事件，通知服务读取事件并发送通知。**

整个过程就是：

**订单服务发送消息 → Kafka 保存消息 → 通知服务读取消息。**

这里五个概念分别回答不同的问题：

| 概念 | 通俗理解 | 例子 |
|---|---|---|
| **Producer，生产者** | 谁发送消息 | 订单服务中的 Kafka 生产者客户端 |
| **Consumer，消费者** | 谁读取消息 | 通知服务中的 Kafka 消费者客户端 |
| **Broker** | 哪个 Kafka 服务节点负责接收、保存和提供消息 | 运行中的 Kafka 服务进程 |
| **Topic，主题** | 这条消息属于哪一类 | `orders`，订单事件主题 |
| **Partition，分区** | 这一类消息具体存入哪条日志 | `orders` 的 P0、P1 |

先只考虑**一个 Broker、一个 Topic、一个 Partition**，并暂时忽略副本。

```text
订单服务                                    通知服务
┌─────────────┐                           ┌─────────────┐
│ Producer    │                           │ Consumer    │
│ 发送订单事件 │                           │ 读取订单事件 │
└──────┬──────┘                           └──────▲──────┘
       │                                       │
       │           Kafka Broker 1              │
       │     ┌──────────────────────────┐      │
       └────→│ Topic：orders            │──────┘
             │                          │
             │ Partition P0：           │
             │ [A创建][B创建][A付款]     │
             └──────────────────────────┘
```

在这个例子里：

- **Producer 和 Consumer 是客户端角色**，运行在业务程序中。
- **Broker 是 Kafka 服务端进程**，负责存取消息。
- **Topic 和 Partition 是 Kafka 组织消息的方式**，它们不是另外两个服务进程。

同一个业务程序可以同时包含生产者和消费者。例如，支付服务读取订单事件，又发送支付成功事件。

**Topic 表示消息类别，Partition 是这个类别下面实际追加消息的日志。**

假设 Kafka 同时保存两类消息：

```text
Topic：orders       订单事件
Topic：payments     支付事件
```

生产者发送时，需要指定消息属于哪个 Topic。通知服务也需要指定自己订阅哪些 Topic。

一个 Topic 至少有一个 Partition，也可以有多个：

```text
Topic：orders
    ├─ Partition P0：[订单 A 创建][订单 A 付款]
    └─ Partition P1：[订单 B 创建][订单 B 付款]
```

这里要特别注意：

**P0、P1 是 `orders` 的两部分。发送一条订单消息时，它会进入其中一个分区，不会因为有两个分区就自动各存一份。**

你可以把 Topic 理解为这些分区共同组成的逻辑名称。业务上说“向 `orders` 发送消息”，落实到存储上，就是“向 `orders` 的某个分区追加记录”。

**Broker 和 Partition 的关系，则是“服务节点承载日志”。**

如果有两个 Broker，我们可以把 `orders` 的两个分区分别放在它们上面：

| Kafka 服务节点 | 保存的分区及消息 |
|---|---|
| Broker 1 | `orders` 的 P0：订单 A 创建、订单 A 付款 |
| Broker 2 | `orders` 的 P1：订单 B 创建、订单 B 付款 |

此时，**一个 Topic 跨越了两个 Broker**。所以不能把 Topic 理解成永远装在某一台 Broker 里的文件夹。

反过来，一个 Broker 也可以同时承载不同 Topic 的分区：

| Kafka 服务节点 | 保存的分区 |
|---|---|
| Broker 1 | `orders-P0`、`payments-P1` |
| Broker 2 | `orders-P1`、`payments-P0` |

这些 Broker 一起组成 Kafka 集群。分区让同一 Topic 的数据能够分布到不同节点上。[Kafka 官方概念说明](https://kafka.apache.org/41/getting-started/introduction/)

现在把一条具体消息走一遍。假设订单 A 创建成功，按照当前分区策略，它应该进入 `orders-P0`：

1. 订单服务中的 **Producer** 准备消息：“订单 A 已创建”，目标 **Topic** 是 `orders`。
2. 生产者客户端确定目标 **Partition** 为 P0。
3. 客户端把消息发送给承载 P0 的 **Broker 1**。
4. Broker 1 把消息追加到 P0 的日志中，为它分配该分区内的 offset。
5. 通知服务中的 **Consumer** 从 Broker 1 拉取这条消息，然后执行业务处理。

这里没有“先经过 Topic 服务器，再经过 Partition 服务器”的过程。**Topic 和 Partition 用于确定消息的位置，真正接收网络请求的是 Broker。**

回到上一讲的单机日志模型，就很好对应了：

| 上一讲的说法 | 现在对应的概念 |
|---|---|
| 发送消息的业务程序 | Producer |
| 消息服务进程 | Broker |
| 一条按顺序追加的日志 | Partition |
| 同一类消息的多条日志 | 共同组成一个 Topic |
| 读取消息的业务程序 | Consumer |

消费者组先放到下一步。现在只检查一个关系：

**假设 `orders` 有 P0、P1 两个分区，它们都放在 Broker 1 上。这里有几个 Topic、几个 Partition、几个 Broker？**

刚才说消息是通过类似日志的形式写入文件，那么partition具体是什么？一个broker可以管理多个partition，那么消费者是否只连接一个partition？

### 014 · 助手

**Partition 在逻辑上是一条独立的有序日志；在 Broker 的磁盘上，它的本地数据通常对应一个目录，里面包含多组日志段文件。消费者通过网络连接 Broker，可以从中读取一个或多个 Partition。**

我们把这两部分具体展开。

之前说“把消息追加到一个文件”，是为了先建立最简单的模型。实际使用中，一条分区日志会不断增长，所以 Kafka 会把它切成多个 **Segment，日志段**。

以 `orders` 的 P0 为例，磁盘结构可以简化理解为：

```text
Broker 的数据目录/
└─ orders-0/                    ← orders 的 P0 的本地日志目录
   ├─ 00000000000000000000.log   ← 第一段消息数据
   ├─ 00000000000000000000.index ← 对应的偏移量索引
   ├─ 00000000000000001000.log   ← 第二段消息数据
   ├─ 00000000000000001000.index
   └─ ……
```

这是示意结构，省略了时间索引等其他文件。这里假设第二段从 offset 1000 开始，实际切段位置由配置和运行情况决定。

从消费者看来，它读的是一条连续的分区日志：

```text
P0：offset 0、1、2、……、999、1000、1001、……
```

从磁盘看来，这些记录存放在多个文件中：

```text
第一段：保存前面的一部分记录
第二段：保存后面的一部分记录
……
```

**切换日志段不会创建新的 Partition，offset 也不会因此重新从 0 开始。** 正常追加写入发生在当前活跃的日志段；满足滚动条件后，再建立新段。这也让历史数据可以按段清理。[Kafka 日志实现说明](https://kafka.apache.org/41/implementation/log/)

因此，这几个层级可以这样对应：

| 层级 | 含义 |
|---|---|
| Topic | 同一类消息的逻辑集合 |
| Partition | Topic 中的一条独立有序日志 |
| Segment | 一条分区日志在存储上的分段 |
| `.log` 文件 | 一个日志段中的消息数据文件 |

这里仍按每个分区只有一份数据讲解。引入副本后，同一 Partition 会在不同 Broker 上各有一份本地日志。

你问的第二个问题，需要区分**“连接谁”与“读取什么”**。

Broker 是监听网络端口的服务进程。Partition 是它管理的数据，不会为自己单独监听一个网络端口。

因此，消费者的行为是：

> 连接 Broker，发送请求：“请给我 `orders` 的 P0，从 offset 1000 开始的数据。”

Broker 根据请求里的分区标识和 offset，查找对应日志，再返回记录。消费者不会直接打开 Broker 上的文件。

**一个消费者完全可以读取多个 Partition，也可以连接多个 Broker。**

假设消费者 C1 被分配了 P0、P1、P2，而它们的分布如下：

```text
消费者 C1
   │
   ├── 网络连接 → Broker 1
   │                ├─ orders-P0
   │                └─ orders-P1
   │
   └── 网络连接 → Broker 2
                    └─ orders-P2
```

C1 可以通过与 Broker 1 的连接读取 P0、P1，通过与 Broker 2 的连接读取 P2。**不需要为每个分区单独建立一条连接**；Fetch 请求可以携带多个分区的读取信息。[Kafka 协议说明](https://kafka.apache.org/41/design/protocol/)

例如，发给 Broker 1 的一次请求，在含义上可以是：

```text
读取 orders-P0，从 offset 1000 开始
读取 orders-P1，从 offset 350 开始
```

这也说明，同一个消费者虽然读取多个分区，仍然需要分别维护各分区的读取位置。

上一段提到的限制是：在常规消费组中，**一个分区在稳定分配下由组内一个消费者负责，但一个消费者可以负责多个分区**。这个规则约束的是工作分配，不是网络连接数量。

所以，落实到你的问题：**一个 Broker 可以管理多条分区日志；消费者连接 Broker，并通过请求指定要读取哪些分区、从各自的什么位置开始。**

### 016 · 助手

你的理解接近了：**可以先把一个 Partition 想成一个不断追加消息的“大文件”，但实际存储时，这个“大文件”会拆成多个文件。**

更准确地说，Partition 是 **Kafka 对消息进行划分的单位**，有自己独立的消息顺序和 offset。它不是操作系统里 C 盘、D 盘那种磁盘分区，也不独占一块磁盘。

```text
一个 Partition：一条有序日志
         ↓ 实际存储
一个目录
  ├─ 日志段 1：消息数据文件 + 索引文件
  ├─ 日志段 2：消息数据文件 + 索引文件
  └─ 日志段 3：消息数据文件 + 索引文件
```

这里有两个不同的“拆分”：

- **Topic 拆成多个 Partition**：形成多条独立日志，可以分布到不同 Broker，并行读写。
- **Partition 拆成多个 Segment 文件**：仍然是同一条日志，方便管理文件大小、清理历史数据。

例如，P0 从一个文件增长到十个文件，它仍然只有一个 Partition；不会因此变成十个分区。

所以你可以保留“Partition 类似一个存储消息的文件”这个直觉，再补上一点：**它是一条逻辑上的完整日志，底层由多段文件共同保存。**

```text
  └─ ……持续追加
```

所以，**一个 Partition 包含很多条消息**。这些消息在磁盘上又分段保存在多个文件中：

```text
  ├─ 段文件 1：保存一批消息
  ├─ 段文件 2：保存另一批消息
  └─ ……
```

后面我会用“**一个有序的消息序列**”来描述 Partition，用“**一条消息记录**”描述其中的元素，避免“一条日志”带来的歧义。

### 020 · 助手

对，**这样区分基本准确：Partition 是逻辑上的消息分区，Segment 是它在存储上的分段。**

但 Partition 也有实际存储对应关系。以普通本地存储为例：

| 概念 | 逻辑含义 | 磁盘上的对应 |
|---|---|---|
| Partition | 一个独立、有序的消息序列，拥有自己的 offset | 该分区的每个副本通常对应一个目录 |
| Segment | 这个消息序列中的一段 | 一组文件，包括 `.log` 数据文件、索引文件等 |
| 消息记录 | 序列中的一个元素 | 保存在 `.log` 文件内，实际按批次组织 |

```text
orders 的 Partition 0
  └─ 某个 Broker 上的本地副本目录：orders-0/
       ├─ Segment 1：数据文件 + 索引文件
       ├─ Segment 2：数据文件 + 索引文件
       └─ Segment 3：数据文件 + 索引文件
```

因此，**Partition 决定消息属于哪个有序序列；Segment 决定这个序列如何分段存储。** 一个 Partition 增加了新的 Segment，仍然是同一个分区，offset 也继续向后增长。

那么消费者消费进度和broker的分配进度这些相关信息怎么保存？

### 022 · 助手

这些信息会分别保存。先把你说的“分配进度”拆开：**谁消费哪个分区、分区存在哪个 Broker、消费者处理到哪里，是三种不同的状态。**

按我们正在学习的 Kafka 4.x、常规消费组模型，可以先看这张表：

| 信息 | 例子 | 保存位置 |
|---|---|---|
| 消费者当前读取位置 | C1 下一次从 P0 的 120 开始读 | 消费者客户端内存 |
| 已提交的消费进度 | 通知组在 P0 的恢复位置是 100 | Kafka 内部 Topic：`__consumer_offsets` |
| 消费组的成员与分区分配状态 | 通知组的 C1 负责 P0、P1 | 协调器管理，相关持久状态保存在 `__consumer_offsets` |
| 分区在 Broker 上的分布 | P0 的副本位于 Broker 1、2、3 | KRaft 集群元数据日志 |

我们先把**消费进度**讲清楚。

假设通知服务的消费组叫 `notification-group`。Kafka 保存的进度，在逻辑上可以理解成一张表：

| 消费组 | Topic | Partition | 已提交 offset |
|---|---|---|---:|
| notification-group | orders | P0 | 100 |
| notification-group | orders | P1 | 250 |
| statistics-group | orders | P0 | 80 |

第一行表示：**通知组恢复消费 P0 时，从 offset 100 开始。**

注意，它记录的是“**消费组 + Topic + Partition**”的进度，而不是绑定某个消费者进程。这样 C1 宕机后，C2 接管 P0，也能继续使用通知组保存的进度。

消费者内存中的读取位置可能已经到了 120，但最后提交的位置仍是 100。此时进程崩溃，内存位置消失，正常恢复会使用已提交的 100。读取位置前进，也不代表业务处理已经完成。[消费者位置与提交位置](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

**那么，这张“进度表”在磁盘上怎么保存？**

Kafka 把进度更新编码成记录，写入一个专门的内部 Topic：

```text
__consumer_offsets
```

它也是 Topic，因此也有 Partition；各分区的副本底层也使用日志段文件保存数据。

一次提交可以简化理解为：

```text
消费者：
“请保存：通知组 / orders / P0，进度为 100”
        ↓
负责该消费组的 Broker
        ↓
向 __consumer_offsets 追加一条进度记录
```

负责管理该消费组的 Broker 承担一个角色，叫 **Group Coordinator，消费组协调器**。

协调器既把进度持久化到内部 Topic，也在内存里维护最新值，方便快速查询。协调器发生切换时，可以通过读取已保存的记录重建状态。[官方消费位点存储说明](https://kafka.apache.org/41/implementation/distribution/)

所以，底层并不是每次找到某个文件里的数字，把 `100` 原地改成 `120`。它可以依次追加：

```text
同一个键：通知组 / orders / P0

进度 = 100
进度 = 110
进度 = 120
```

查询时使用最新有效值。旧值之后通过日志压实逐步清理，压实机制我们后面再展开。

**如果你说的“分配”是“哪个消费者负责哪个 Partition”，它也由消费组协调器管理。**

例如：

```text
通知组：
  C1 → P0、P1
  C2 → P2
```

消费者加入、退出或失联时，这个分配关系可能改变。协调器管理成员及分配状态，相关持久记录写入 `__consumer_offsets`；消费者本地也保存自己当前获得的分配结果。新旧消费组协议的具体分配过程不同，后面再细讲。

这里要分清：

- **分配关系**回答：现在谁负责 P0？
- **已提交进度**回答：这个组接着从 P0 的哪里读？

换了负责人，不意味着进度从头开始。

**如果你说的“分配”是“Partition 放在哪些 Broker 上”，则属于集群元数据。**

例如：

```text
orders-P0：
  副本所在节点：Broker 1、Broker 2、Broker 3
  当前 Leader：Broker 1
```

在 KRaft 架构中，这类信息由 **Controller** 管理，持久化到集群元数据日志，并通过控制器仲裁组复制。磁盘上可以看到 `__cluster_metadata-0` 目录，其中包含元数据日志段和快照。Broker 获取这些元数据后，知道自己需要承载哪些分区副本。[KRaft 元数据存储说明](https://kafka.apache.org/41/operations/kraft/)

把它们放回订单例子里：

```text
订单发生了什么？       → orders 中的业务消息
通知组处理到哪里？     → __consumer_offsets 中的已提交进度
通知组由谁处理 P0？    → 消费组的分配状态
P0 的数据保存在哪？    → KRaft 集群元数据
```

Kafka 不能从“已经把消息返回给消费者”推断“业务已经处理成功”。**读取数据和提交进度是两个独立动作**，这正是之前讨论的遗漏、重复问题产生的地方。

### 024 · 助手

整个 Kafka 可以围绕三个问题理解：**谁收发消息、消息如何组织和存储、系统如何记录进度与分工。**

| 概念 | 核心含义 | 与其他概念的关系 |
|---|---|---|
| **Producer，生产者** | 发送消息的客户端 | 向指定 Topic 的某个 Partition 发送消息 |
| **Consumer，消费者** | 读取消息的客户端 | 连接 Broker，读取自己负责的一个或多个 Partition |
| **Broker** | Kafka 服务端节点，运行中的服务进程 | 管理多个分区副本，负责消息存取；多个 Broker 组成集群 |
| **Topic，主题** | 一类消息的逻辑集合 | 例如订单事件 `orders`，包含一个或多个 Partition |
| **Partition，分区** | 独立、有序的消息序列 | 是数据分布和消费分工的基本单位，每个分区拥有自己的 offset |
| **Segment，日志段** | 分区日志在存储上的分段 | 一个分区副本包含多个 Segment，每段包含数据文件和索引文件 |
| **Offset，偏移量** | 消息在分区中的逻辑位置 | 不是文件字节位置；定位消息需要 Topic、Partition、Offset |
| **Consumer Group，消费组** | 共同完成一种消费任务的消费者集合 | 组内分担分区，组间独立消费、独立保存进度 |

把逻辑与物理存储对应起来：

```text
Topic：orders
  ├─ Partition P0：一个有序的消息序列
  │    └─ 每个副本在某个 Broker 上保存
  │         └─ 分区目录
  │              ├─ Segment 1：数据文件 + 索引文件
  │              └─ Segment 2：数据文件 + 索引文件
  └─ Partition P1：另一个独立的有序消息序列
       └─ ……
```

**分区与分段解决不同的问题：**

- Topic 拆成多个 **Partition**，使数据能够分布到不同节点、并行处理。
- Partition 拆成多个 **Segment**，便于管理文件大小和清理历史数据。
- 同一个 Partition 保存多个**副本**，为故障恢复提供数据冗余。

**连接关系与消费分工也要分开：**

消费者连接的是 **Broker**，请求中指定要读取的 **Partition 和 Offset**。一个消费者可以连接多个 Broker、读取多个分区。在常规消费组的稳定分配下，一个分区由组内一个消费者负责；其他消费组可以独立读取这个分区。

系统状态分别保存：

| 状态 | 回答的问题 | 保存位置 |
|---|---|---|
| 当前读取位置 | 客户端下一次从哪里读？ | 消费者内存 |
| 已提交消费进度 | 故障后从哪里恢复？ | `__consumer_offsets`，按“消费组 + Topic + Partition”保存 |
| 消费组分配状态 | 哪个消费者负责哪个分区？ | Group Coordinator 管理，相关持久状态写入 `__consumer_offsets` |
| 集群元数据 | 分区副本在哪些 Broker，谁是 Leader？ | Controller 管理，持久化到 KRaft 元数据日志 |

最后，用一条消息串起整个过程：

**生产者选择 Topic 和 Partition → 发送给对应 Broker → Broker 追加到分区的日志段 → 消费者通过 Broker 读取 → 业务处理 → 提交消费进度。**

其中始终要区分：**消息保存成功、消费者读取成功、业务处理成功、消费进度提交成功，是不同的完成时刻。**

我们回到原来的主线：**为什么需要分区，以及分区如何影响并行度和顺序。**

目前已经推进到：

1. **单机持久化**：消息追加到日志，消费者单独保存进度。
2. **故障恢复**：处理业务与提交进度是两个动作，可能产生遗漏或重复。

所以这个例子里：

接着往下推导：**增加分区，是否就能解决这个热点？**

假设从 6 个分区增加到 12 个，但那 80% 的消息仍然使用同一个 key，并且分区策略仍把同一个 key 映射到同一个分区。那么这些消息仍然会集中在某一个分区上。目标分区可能改变，集中现象依然存在。

```text
商家 M

  └─ 订单 C：创建 → 付款 → 发货
```

### 030 · 助手

对，使用**订单 ID** 作为 key，更符合这个业务的顺序要求。

在分区数量和分区策略保持一致的前提下，同一订单的事件进入同一个分区；不同订单有机会分散到不同分区，并行处理。多个订单也可能落入同一个分区，**不需要给每个订单创建一个分区**。

到这里，我们已经把“为什么分区”串起来了：明确业务所需的顺序范围，再把可以独立处理的数据拆开，提高并行能力。

接下来回到架构主线，解决另一个问题：**分区所在的 Broker 坏了怎么办？**

假设目前只有一份数据：

```text
Broker 1：orders-P0
Broker 2：orders-P1
Broker 3：orders-P2
```

如果 Broker 1 停机，P0 暂时无法提供服务；如果它的磁盘数据永久损坏，P0 的消息就可能丢失。

增加 P1、P2 并不能恢复 P0，因为不同分区保存的是不同消息。因此，我们需要为 **同一个 Partition 保存多份数据**，这就是副本，Replica。

例如，P0 有三个副本：

```text
同一个逻辑分区 orders-P0
   ├─ Broker 1：P0 的副本
   ├─ Broker 2：P0 的副本
   └─ Broker 3：P0 的副本
```

它们复制的是同一个消息序列，offset 对应同样的记录。每份副本都有自己的本地目录和日志段文件；复制过程中，各副本的进度可能暂时不同。

**但三份副本不能各自随意接受写入。**

假设两个生产者同时发送 A 和 B，不同节点可能分别记录成：

```text
Broker 1：offset 10 = A，offset 11 = B
Broker 2：offset 10 = B，offset 11 = A
```

这样，同一个分区的顺序就出现了分歧。

Kafka 为每个分区选出一个 **Leader 副本**，负责接收生产者写入，其他 **Follower 副本**从 Leader 拉取并复制数据。[Kafka 副本设计](https://kafka.apache.org/41/design/design/)

```text
生产者
   │ 写入
   ▼
Broker 1：P0 Leader
   ▲                  ▲
   │ 拉取并复制         │ 拉取并复制
Broker 2             Broker 3
P0 Follower          P0 Follower
```

这里的 Leader 是**针对分区**的角色。同一个 Broker 可以是 P0 的 Leader，同时是 P1 的 Follower。

有了副本，新的关键问题随之出现：**生产者应该什么时候收到“写入成功”？**

我们先推演一种情况：Leader 保存了消息，就立即向生产者返回成功，此时两个 Follower 都还没有复制到这条消息。

**如果紧接着 Leader 的磁盘永久损坏，仅靠剩下的两个副本，能恢复这条已经向生产者确认成功的消息吗？**

### 032 · 助手

**副本针对 Partition。** 我们通常在创建 Topic 时设置“副本因子”，这个配置表示：**该 Topic 的每个 Partition 保存几份。**

例如，`orders` 有 **2 个分区，副本因子为 3**：

| 分区 | Broker 1 | Broker 2 | Broker 3 |
|---|---|---|---|
| P0 | P0 Leader | P0 Follower | P0 Follower |
| P1 | P1 Follower | P1 Leader | P1 Follower |

这里：

- 仍然只有 **2 个逻辑分区**：P0、P1。
- 每个分区有 **3 份副本，包含 Leader 在内**。
- 总共保存 **2 × 3 = 6 份分区副本**。
- P0 的三个副本复制 P0 的消息，P1 的三个副本复制 P1 的消息。
- **每个分区独立拥有自己的 Leader**，没有一个统一的“Topic Leader”。

所以，“Topic 的副本因子是 3”，可以理解为：**要求这个 Topic 下面的每个分区都保存 3 份。**

### 034 · 助手

对。**唯一拥有这条消息的副本已经永久损坏，剩下两个副本又没有复制到它，因此无法恢复。**

这说明：**配置了三个副本，不代表每次返回“发送成功”时，消息已经存在于三个副本中。** 还要看系统在什么条件下返回成功。

Kafka 用生产者参数 **`acks`** 控制这个确认条件：

| 配置 | 生产者等待什么 |
|---|---|
| `acks=0` | 不等待 Broker 的确认，因此无法据此确定 Broker 是否收到消息 |
| `acks=1` | Leader 写入自己的本地日志后即可确认，不等待 Follower 复制完成 |
| `acks=all` | 等待 ISR 中的所有副本完成这条消息的复制 |

刚才“Leader 返回成功，Follower 尚未复制，Leader 的数据就永久损坏”的场景，正是 `acks=1` 存在的风险。[官方 `acks` 配置说明](https://kafka.apache.org/41/configuration/producer-configs/#acks)

注意，这里的“写入本地日志”不等于每条消息都立即刷到物理磁盘。**副本确认与强制刷盘是两个不同机制**，存储章节会继续展开。

`acks=all` 里出现了一个新概念：**ISR，In-Sync Replicas，同步副本集合。**

可以先把 ISR 理解为：**Kafka 当前认为复制进度能够跟上的那组副本，包含 Leader。**

例如，P0 配置了三个副本：

```text
Broker 1：Leader
Broker 2：Follower，正常跟进
Broker 3：Follower，已经长时间落后，被移出 ISR

全部副本：{1, 2, 3}
当前 ISR：{1, 2}
```

Broker 3 被移出 ISR，并不意味着它不再是 P0 的副本。它仍然可以继续追赶，符合条件后再加入 ISR。

假设上面的 ISR 保持不变，那么一次写入的确认过程可以理解为：

```text
Leader 写入消息
       ↓
等待 Broker 2 复制到这条消息
       ↓
满足其他写入条件后，Leader 向生产者返回成功
```

它不需要等待已经退出 ISR 的 Broker 3。这里的 `all` 指的是 **ISR 中的全部副本**，不是配置中的全部副本。

| ④ | F1 | 把 M 追加到自己的本地日志，保留 offset 100 |
| ⑤ | F1 | 再次发送 Fetch：“接下来从 offset 101 开始给我数据” |
| ⑥ | Leader | 根据这个新请求，更新自己记录的 F1 复制进度 |

### 042 · 助手

**副本因子（Replication Factor）就是：一个 Partition 配置多少份副本，包含 Leader 在内。** [官方说明](https://kafka.apache.org/41/design/design/#replication)

例如，`orders` 的副本因子为 **3**，那么它的每个分区通常这样分布：

```text
orders 的 P0 分区
  ├─ Broker 1：Leader    → 一份数据
  ├─ Broker 2：Follower  → 一份数据
  └─ Broker 3：Follower  → 一份数据
```

这里是 **1 个 Leader + 2 个 Follower = 3 份副本**。Leader 自己就算一份。

如果这个 Topic 有 **2 个分区**，每个分区的副本因子都是 3，总共就有 **2 × 3 = 6 份分区副本**。P0 的副本复制 P0 的消息，P1 的副本复制 P1 的消息。

把它和刚才的概念放在一起：

| 概念 | 含义 |
|---|---|
| **副本因子 = 3** | 配置了三份副本 |
| **当前 ISR 有 2 个成员** | 三份副本中，目前两份属于同步副本集合 |
| **某条消息已经有 2 份** | 这条具体消息目前已被两份副本写入 |

**配置三份副本，不代表每条新消息立即就有三份。** Follower 复制需要时间，也可能暂时故障或落后。

这里先弄清数量关系，暂不展开副本分配和故障选主。

“不能直接重发”可以进一步表述为：**重试需要有处理重复的机制。** 因为不重试也有风险——如果第一次确实没有写进去，这个事件就可能一直缺失。

| 实际发生的情况 | 生产者看到的结果 |
|---|---|

先看**生产者这一层的幂等**。假设消息 M 表示“给用户增加 100 积分”，没有去重保护时，重发可能使同一分区出现：

```text
offset 100：消息 M，增加 100 积分
offset 101：消息 M，增加 100 积分
```

这是**同一个业务事件，被追加成了两条不同的日志记录**。消费者即使每条记录只处理一次，也可能累计增加 200 积分。

Kafka 提供了**幂等生产者**机制：通过生产者身份、序列号等信息，识别生产者客户端内部重试的同一批数据，避免重复追加。具体字段和判断过程，后面在生产者实现章节展开。

这里有一个重要边界：**客户端内部自动重试，与业务代码重新调用一次 `send()`，需要区分。** 业务代码把相同内容再发送一次，Kafka 并不会仅凭“内容相同”就认定它是重复消息；生产者幂等不能自动消除这种应用层重发。[KafkaProducer 官方说明](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)

**重启后按之前提交的消费进度恢复，如果没有业务去重保护，积分还可能再增加 100 吗？**

**消费者主动拉取消息。** 它向 Broker 发送 `Fetch`（拉取）请求，指定分区和读取位置，Broker 再返回对应的一批数据。[官方消费模型](https://kafka.apache.org/41/design/design/#the-consumer)

你说的“分配”和“发送”，需要拆成两个动作：

| 动作 | 解决的问题 | 例子 |
|---|---|---|
| **分区分配** | 消费组里的谁负责哪个分区？ | C1 负责 P0，C2 负责 P1 |
| **消息拉取** | 负责这个分区的消费者，从哪里读取数据？ | C1 请求读取 P0，从 offset 100 开始 |

分区分配完成后，正常的数据读取过程是：

```text
消费者 C1                              Broker
    │                                    │
    │── Fetch：读取 P0，从 offset 100 开始 ─→│
    │                                    │
    │←── 返回一批消息，例如 100～109 ───────│
    │
    └─ 执行业务处理，再按处理结果提交进度
```

分区分配涉及 **Group Coordinator（消费组协调器）** 和分配协议，具体分工我们后面再展开。它确定分区的负责人；消息读取由消费者发起。

假设已提交进度是 100：

1. 消费者拉取 offset 100 的消息 M。
2. 数据库增加 100 积分，事务提交成功。
3. 消费者尚未提交进度 101，就崩溃了。
4. 重启后按已提交进度 100 恢复，**再次主动请求从 100 开始读取**。
5. Broker 返回仍保留在日志中的 M，于是业务可能再次加积分。

### 050 · 助手

接下来学习 **消费端幂等：同一个业务事件即使被处理多次，也只产生一次预期的业务效果。**

继续用“给用户增加 100 积分”的例子。我们先假设消费者逐条、顺序处理消息，涉及的数据都在同一个数据库中。

首先，需要能够识别**同一个业务事件**。可以给消息携带一个稳定的事件编号：

```text
event_id：E123
user_id：U8
操作：增加 100 积分
```

同一事件因超时而重新发送时，应当继续使用 `E123`。即使它被写成不同 offset 的两条消息，消费者仍能识别出它们对应同一次业务操作。

然后，在积分业务的数据库中保存“已处理事件记录”，把 `event_id` 设为主键。数据库的唯一性约束负责阻止同一个编号被重复插入；即使两个处理过程并发执行，也不能各自成功保存一份相同的记录。[数据库唯一性约束](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)

但仅有这张表还不够。**“记录 E123 已处理”和“增加 100 积分”必须放在同一个数据库事务中。**

处理流程可以设计成：

```text
收到事件 E123
    ↓
开启数据库事务
    ↓
尝试插入 E123 的处理记录
    ├─ 插入成功 → 增加 100 积分 → 提交数据库事务
    │
    └─ 确认 E123 已有成功提交的记录
                    → 结束本次事务，不再增加积分
    ↓
本条处理完成，再提交 Kafka 消费进度
```

这里的“已处理”记录，只有随事务成功提交后才正式生效。其他数据库错误仍需要按失败处理，不能一律当成“重复消息”跳过。

数据库事务提供的原子性，使这两个修改**一起提交，或者一起回滚**。[事务原子性说明](https://www.postgresql.org/docs/18/tutorial-transactions.html)

这样，之前的故障窗口就能被处理：

| 崩溃时刻 | 数据库状态 | 再次处理 E123 时 |
|---|---|---|
| 数据库事务尚未提交 | 处理记录和积分修改都未提交 | 可以重新执行 |
| 数据库事务已经提交，但 Kafka 进度尚未提交 | E123 的记录和积分修改都已提交 | 识别到重复，跳过加积分 |

消息仍可能再次被拉取，但已经提交的处理记录能够阻止它再次修改积分。

检查一个关键点：**如果把两个修改拆成独立事务，先提交“E123 已处理”，还没来得及增加积分就崩溃了，那么重试时会发生什么？**

这里的事务保证只覆盖同一个数据库内的修改；发送邮件、调用外部接口等副作用暂不展开。

- **消费端业务幂等**：处理事件被再次消费时可能产生的重复业务效果。

现在回到原来的学习主线，开始串起**一条消息的完整旅程**。第一步是：**生产者如何知道该连接哪个 Broker？**

假设 `orders` 有三个分区：

| 分区 | 当前 Leader 所在节点 |
|---|---|
| P0 | Broker 3 |
| P1 | Broker 1 |
| P2 | Broker 2 |

生产者的业务代码通常只指定 Topic、key 和消息内容。为了找到发送目标，客户端需要获取 **Metadata（元数据）**，其中包含分区信息、各分区的 Leader，以及 Broker 的连接地址。

但获取元数据之前，总得先知道一个可以连接的地址。这个入口由 **`bootstrap.servers`（初始连接地址列表）** 提供，例如：

```text
bootstrap.servers = broker1:9092,broker2:9092
```

客户端可以通过列表中可用的节点建立初始连接，发现集群中的其他 Broker，因此不需要在这里列出全部节点。配置多个入口，可以降低某个入口不可用对启动的影响。[官方配置说明](https://kafka.apache.org/41/configuration/producer-configs/#bootstrap.servers)

假设本次成功连接的是 Broker 1，消息最终被选入 P0，流程就是：

```text
① 生产者 → Broker 1
   请求 orders 的元数据

② Broker 1 → 生产者
   返回：P0 的 Leader 是 Broker 3，以及 Broker 3 的地址

③ 生产者 → Broker 3
   直接发送写入 P0 的 Produce（生产）请求
```

**负责回答这次元数据查询的节点，与实际接收这条消息的节点，可以不同。** 生产者根据分区的 Leader 信息，直接连接对应 Broker 发送数据。[官方生产者路由说明](https://kafka.apache.org/41/design/design/#the-producer)

检查一下这个关系：

**假设生产者配置的入口只有 Broker 1，却通过元数据发现 P0 的 Leader 在 Broker 3。要向 P0 发送消息，生产者是否还需要能够直接连接 Broker 3？**

### 054 · 助手

对，需要把请求发到对应的 Broker；准确地说，是**选择目标 Broker 对应的连接发送**。生产者可以同时维护多条 TCP 连接，并复用已有连接。[官方 Java 客户端连接实现](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/NetworkClient.java#L336-L355)

消息的路由关系是：

**消息 key → 根据分区策略确定 Partition → 查元数据找到该分区的 Leader → 使用对应 Broker 的连接。**

例如，假设这些 key 被分配到如下分区：

| 消息 key | 目标分区 | Leader 所在节点 | 使用连接 |
|---|---|---|---|
| 订单 A | P0 | Broker 3 | 到 Broker 3 的连接 |
| 订单 B | P1 | Broker 1 | 到 Broker 1 的连接 |
| 订单 C | P2 | Broker 3 | 到 Broker 3 的同一条连接 |
| 订单 A | P0 | Broker 3 | 继续复用到 Broker 3 的连接 |

发送第二条消息时，生产者可以保留与 Broker 3 的连接，同时使用与 Broker 1 的连接。第三条消息再发往 Broker 3 时，继续复用原有连接。

因此：

- **目标 Broker 不同**：使用各自的连接。
- **分区不同，但 Leader 在同一个 Broker**：可以复用同一条连接。
- **需要的连接尚未建立或已经断开**：客户端负责建立或恢复连接。

这些工作由客户端管理，业务代码通常继续调用同一个生产者的发送接口即可。

再往底层看，官方 Java 生产者会**按分区组织消息批次，再按目标 Broker 组织发送请求**。同一个 Produce 请求可以携带发往该 Broker 的多个分区的数据。[请求组织实现](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/Sender.java#L789-L819)

### 056 · 助手

**这里合并的是多条消息。每条消息仍然只指定一个 Topic，并最终进入其中一个 Partition。** [消息定义](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/ProducerRecord.html)

需要区分三个层次：

| 层次 | 含义 | 组织边界 |
|---|---|---|
| **消息，Record** | 一条业务数据，例如“订单 A 已付款” | 属于一个 Topic 的一个分区 |
| **批次，Batch** | 把多条消息组织在一起，便于批量传输和存储 | 批次内的消息属于**同一个 Topic、同一个分区** |
| **Produce 请求** | 生产者发送给某个 Broker 的一次写入请求 | 可以携带**多个分区的批次** |

“按分区组织消息批次”，就是先把准备发送到同一个分区的消息放在一起。它们的 key 可以不同，只要最终选中了同一个分区。

我们只用一个 Topic 来举例。假设连续发送五条消息：

| 消息 | Topic | 选中的分区 | Leader 所在节点 |
|---|---|---|---|
| A、B | orders | P0 | Broker 1 |
| C、D | orders | P1 | Broker 1 |
| E | orders | P2 | Broker 2 |

假设消息大小和发送时机允许，可以这样组织：

```text
发给 Broker 1 的一个 Produce 请求
└─ Topic：orders
   ├─ 分区 P0 的批次：[消息 A][消息 B]
   └─ 分区 P1 的批次：[消息 C][消息 D]

发给 Broker 2 的另一个 Produce 请求
└─ Topic：orders
   └─ 分区 P2 的批次：[消息 E]
```

这里总共是 **五条消息、三个批次、两个请求**。

A、B 在一个批次中，仍然是两条独立消息，写入后各自有自己的 offset。Broker 1 收到请求后，会把 P0 的批次追加到 P0 的日志，把 P1 的批次追加到 P1 的日志。[批次与请求配置说明](https://kafka.apache.org/41/configuration/producer-configs/#batch.size)

所以，你问的“一个请求包含多个分区”，**在所有消息都属于同一个 Topic 时就可以发生**，因为同一个 Broker 可以同时担任多个分区的 Leader。

一个请求也可以进一步携带**不同 Topic 的分区批次**，前提是这些批次都发往这个 Broker。例如，再带上一批 `payments-P0` 的消息。每条消息的 Topic 和 Partition 仍然分别记录在请求结构中。[请求组装实现](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/Sender.java#L789-L819)

这里先看组织关系，批次大小和何时发送下一步再讲。

### 058 · 助手

对，更准确地说：**当一个 Broker 是多个分区的 Leader 时，一次 Produce 请求可以携带这些分区的多个消息批次。**

你提出的时效问题，正是批处理需要解决的核心取舍。Kafka 的办法是：**给凑批设置有限的等待时间；批次满了可以提前发送，时间到了即使没满也可以发送。** 不需要提前知道第 n 条消息是否会到来。

以 Kafka 官方 Java 生产者为例，主要看两个参数：

| 参数 | 控制什么 |
|---|---|
| `batch.size` | 常规批次的容量，单位是**字节**，不是消息条数 |
| `linger.ms` | 为了让更多消息加入批次，允许主动等待的时间 |

例如，我们设置 `batch.size=16384`，即 16 KiB，`linger.ms=10`，即 10 毫秒。[官方配置说明](https://kafka.apache.org/41/configuration/producer-configs/#linger.ms)

先只看 P0 分区，假设连接正常，没有拥堵，也没有其他提前发送条件：

| 时间 | 发生的事情 | 当前批次 |
|---|---|---|
| 0 ms | 第一条消息 A 到来，创建批次，开始计时 | `[A]` |
| 2 ms | B 到来，还有空间，加入当前批次 | `[A, B]` |
| 7 ms | C 到来，还有空间，加入当前批次 | `[A, B, C]` |
| 10 ms | 等待时间达到 10 ms，批次满足发送条件 | 准备发送 `[A, B, C]` |
| 12 ms | 假设上一批已经发出，D 此时到来 | 创建下一批 `[D]` |

**批次包含多少条消息，是这一段时间里实际积累出来的结果。** 如果到 10 ms 仍然只有 A，那么这个批次就只带 A，也可以发送。

还有两个细节：

- **后续消息不会重新开始这次等待计时。** B 在 2 ms 加入，不会把截止时间推到 12 ms；C 加入也不会继续往后推。
- **如果批次提前满了，就不用等到 10 ms。** 例如 3 ms 时已经装满，便可以进入发送流程。[批次就绪判断实现](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/RecordAccumulator.java#L551-L584)

这确实会让较早到来的消息多等一会儿。在上面的理想时序里，A 为凑批等待约 10 ms，B 等待约 8 ms，C 等待约 3 ms。换来的收益是：多条消息可以一起传输，分摊请求处理等开销。

如果业务更关注低延迟，可以缩短 `linger.ms`；设为 0 表示不主动为了凑批而等待。不过，发送线程真正取走数据之前，仍可能已经积累了多条消息，因此仍可能形成批次。[生产者批处理说明](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)

本例省略了重试和拥堵；`linger.ms=10` 只约束主动凑批的等待，**不保证消息在 10 ms 内发送完成或收到 Broker 确认**。

### 060 · 助手

我们继续深入生产者内部：**业务代码调用 `send()` 后，消息通常先进入生产者的内存缓冲，再由后台线程发送。**

下面以官方 Java 生产者为例，先讨论非事务发送，并假设使用 `acks=all`。

生产者内部有两个主要的执行角色：

| 执行角色 | 主要职责 |
|---|---|
| **调用 `send()` 的业务线程** | 等待必要的元数据，将 key、value 序列化成字节，确定分区，把消息追加到缓冲中的批次 |
| **后台 Sender 线程** | 找出可以发送的批次，按目标 Broker 组织请求，通过网络发送并处理响应 |

它们通过 **`RecordAccumulator`（消息累积器）** 衔接。你刚才学到的“按分区组织批次”，就发生在这里。[累积器实现](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/RecordAccumulator.java#L57-L79)

可以把它的逻辑结构理解成：

```text
生产者进程的内存

RecordAccumulator
  ├─ orders-P0 → [批次 1：A、B] → [批次 2：C……]
  ├─ orders-P1 → [批次 1：D、E……]
  └─ orders-P2 → [批次 1：F……]
```

业务线程不断向对应分区的批次追加消息；后台 Sender 根据批次大小、等待时间、连接状态等条件，安排发送。前面讲过的批处理和多连接复用，就在这里连起来了。[Sender 实现](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/Sender.java#L71-L85)

**这里最重要的区别是：`send()` 返回，与发送最终成功，是两个时刻。**

在正常入队路径上：

```text
业务线程调用 send()
    ↓
消息进入本地内存缓冲
    ↓
send() 返回，业务线程可以继续工作
    ⋮
后台 Sender 发送消息
    ↓
Broker 满足 acks=all 的确认条件，返回成功
    ↓
客户端收到响应，通知业务代码发送成功
```

Java 客户端提供两种获知最终结果的方式：

- **Future（异步结果对象）**：`send()` 返回它，业务代码可以等待并检查结果。
- **Callback（回调函数）**：发送完成后，由客户端调用，告知成功或失败。

如果每发送一条就立刻等待结果，业务线程仍然会被等待过程挡住；异步接口允许业务代码先提交多条消息，再处理结果。[官方发送接口说明](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)

另外，**异步发送也可能在入队前等待**：例如暂时没有可用元数据，或者缓冲内存已经用完。这与“等待 Broker 确认”是不同的等待原因。

现在检查这个边界：**消息已经进入 `RecordAccumulator`，`send()` 已返回，但 Sender 尚未把它发送出去，此时生产者进程突然崩溃。即使配置了 `acks=all` 和三个副本，这条消息能靠 Kafka 的副本恢复吗？**

- 一个生产者可维护并复用多个 Broker 连接；同一 Broker 上不同分区的写入可以共用连接，无需每条消息都断开重连。
- 消息、批次、请求分层：每条消息进入一个 Topic 的一个分区；一个批次中的消息属于同一个 Topic、同一个分区；发往一个 Broker 的 Produce 请求可以携带多个分区的批次，也可以涉及不同 Topic。
- 批处理无需事先知道第 n 条消息何时到来。主要凑批条件是批次容量和 linger.ms 等待时间；后续消息不会重新开始同一首次发送批次的等待计时，时间到即使只有一条也可满足发送条件。linger.ms 不等于端到端发送或确认时限。

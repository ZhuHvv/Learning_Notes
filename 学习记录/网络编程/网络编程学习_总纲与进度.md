## 2. 学习方式与排序依据

- 延续 Redis 的学习节奏。先讲清一个具体过程，让学习者提问，再按需要选 1～2 道机制题，一次问一道。正常路径能复述后，每次只改变一个条件，例如客户端只发来半个帧头，或服务端已经提交操作但响应丢失。
- 按通用后端与游戏服务器岗位安排顺序。TCP 生命周期、字节流、非阻塞 I/O、HTTP/TLS 和长连接故障兼具面试价值和工程影响。先建立 socket 与字节流模型，再解释 epoll 通知了谁、服务端还需要读什么。UDP 的基本语义在首课对照，实时同步在后段结合玩法约束展开。
- 以 **Linux socket 语义和 Go 标准库**为主线。协议查 RFC，系统调用查 Linux man-pages，Go 示例记录工具链版本。讲解时分别标出协议保证、内核行为和应用约定；需要抓包时记录采集位置、连接四元组及对应日志。[TCP 规范 RFC 9293](https://datatracker.ietf.org/doc/html/rfc9293) · [Go net 包](https://pkg.go.dev/net#Conn)

## 3. 模块与建议顺序

“基础”建立后续共同使用的模型，“核心”覆盖常见面试追问和工程决策，“岗位重点”按实时游戏场景加深，“综合”要求用证据定位。顺序取决于前置知识和岗位价值，未统计题库频率。

| 编号 | 模块 | 学什么 | 主要前置 / 定位 |
|---|---|---|---|
| 01 | 一次请求、网络分层与 socket | 域名与 DNS 缓存、IP/端口、同网段和经网关转发、TCP 连接四元组；对照 TCP 字节流与 UDP 数据报；串起 socket/bind/listen/accept 与 connect | 起点 · 基础 |
| 02 | TCP 建连、关闭与状态机 | 用初始序号解释三次握手；Linux 半连接与已完成连接队列、accept 的位置；双向关闭、半关闭、FIN/RST、TIME_WAIT 和 CLOSE_WAIT | 01 · 核心 |
| 03 | 从字节流读出业务消息 | 内核收发缓冲区、短读与写入进度；定长、分隔符、长度前缀；处理帧头分段、连续多帧、异常帧长、EOF 与帧中断连 | 01～02 · 核心 |
| 04 | TCP 可靠传输与速度控制 | 序号、累计 ACK、乱序、超时与快速重传；接收窗口保护谁、拥塞窗口限制谁；RTT、慢启动、零窗口与慢接收方；追踪一次丢包如何影响后续字节交付 | 02～03 · 核心 |
| 05 | 阻塞、非阻塞与 I/O 多路复用 | 就绪与完成、EAGAIN；select/poll/epoll 各自维护什么、每次等待传什么；兴趣列表与就绪列表、LT/ET、读到暂时无数据、动态关注可写事件 | 02～03 · 核心 |
| 06 | 并发服务器、Reactor 与 Go netpoll | accept 循环、连接归属、事件循环与工作线程、耗时任务隔离；沿 Go 的 net.Conn.Read 追踪非阻塞 fd、goroutine 等待、就绪与重试 | 05 · 核心 |

| 08 | 长连接、心跳与背压 | 区分拨号、读写和业务超时；TCP keepalive 与应用心跳；慢客户端、发送队列上限、限速/合并/断连；重连后旧会话清理、优雅下线 | 03～06 · 核心 |
| 09 | RPC 超时、重试与结果未知 | 串起客户端、代理、服务端的超时预算；连接池与请求标识、取消传播、幂等键、重试退避；区分请求未发出、已到达、已提交但应答缺失 | 07～08 · 核心 |

| 11 | 推送与流式协议选型 | 比较 WebSocket、SSE 和 gRPC streaming 的方向、消息边界、取消、流控与代理支持；结合大厅通知、观战广播与服务间 RPC 选型；按需再看 QUIC/HTTP/3 | 07～10 · 岗位拓展 |

## 4. 阶段考察与最小实验

| 学完 | 代表问题 | 拟做的最小验证 |
|---|---|---|
| 01～02 | 服务端还没来得及 accept，客户端的 connect 能否已经成功？服务端大量 CLOSE_WAIT 时，应该查哪一端的哪一步？ | 在本机 Linux 或 WSL 的回环接口观察一次短连接。对齐握手、accept 返回、两端关闭与数据包的时序，在 ss 输出里找到相应 socket。 |
| 03～04 | 对端先送来 2 字节，随后送来剩余帧头、整个帧体和下一帧的一部分。当前能交付几条消息，哪些字节要保留？发送方收到 TCP ACK 后能推断到哪一步？ | 用固定输入分块喂给 Go 解码器，覆盖完整帧、过长帧和中途 EOF；按定长帧头读取时可用 `io.ReadFull`。再解释 TCP 如何把分段与丢包隐藏在应用读接口之下。 |
| 05～06 | epoll 报可读后，谁负责把字节读到用户缓冲区？ET 模式下只读取部分数据就再次等待，在什么条件下会停住？Go 的 Read 看起来可以等待，线程此时在做什么？ | 画出内核、事件循环和业务执行者，分别标注就绪、read、EAGAIN、再次等待。结合已有笔记对读 Go 的 `src/internal/poll/fd_unix.go` 与 `src/runtime/netpoll.go`。[Linux epoll 手册](https://man7.org/linux/man-pages/man7/epoll.7.html) |
| 07～09 | 游戏服已完成一次购买，网关却先超时。客户端重试时由哪一层识别同一笔操作？另一例中，旧连接的断开回调晚于新连接登录，怎样避免清理新会话？ | 给两次尝试标上业务请求号，给两条连接分别标上会话代次。沿时间线解释每个参与方当时能知道什么。可复用模拟面试第 7～10、32～33 题。[HTTP 语义 RFC 9110](https://www.rfc-editor.org/info/rfc9110/) · [模拟面试记录](../游戏服务器中级开发_模拟面试逐题整理_2026-11-16.md) |
| 10～12 | 同一玩家的旧位置晚于新位置到达，和“结算消息迟到”应如何分别处理？观战推送变慢时，怎样判断数据堆在网关写队列、内核发送队列，还是客户端处理环节？ | 先按消息语义设置可丢弃或必须确认的条件，再给不同位置各选一个观测指标，用同一连接或请求的时间线关联它们。 |

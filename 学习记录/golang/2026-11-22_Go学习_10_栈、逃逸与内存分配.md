# 10 栈、逃逸与内存分配

本轮环境为 **Go 1.26.0，windows/amd64**。判断一个值放在哪里，先分清变量本身和它指向的数据，再沿调用关系看谁需要使用它、用到什么时候。确定需要堆分配后，才需要看对象的大小和指针布局。

## 1. 进程内存里放着什么

| 常见区域 | 保存的内容 | 本轮例子 |
|---|---|---|
| 代码区（`.text`） | 编译后的机器指令 | 一万层递归执行同一份 `descend` 指令，每层调用有各自的栈帧。 |
| 只读数据区（`.rodata` 或 `.rdata`） | 程序运行时只读的数据 | 字符串字面量 `"ranked"` 的底层字节通常放在这里。 |
| 已初始化的可写数据区（`.data`） | 需要静态保存初值的全局数据 | 包级变量 `var maxPlayers = 100`。 |
| 零初始化数据（BSS） | 启动时内容全零的全局存储 | 包级 `var online int` 初值为 0，`var lastPacket []byte` 初值为 nil。 |
| goroutine 栈 | 活跃调用的栈帧，以及需要放在帧里的变量等 | `score` 等待递归返回时，自己的栈帧仍在。部分局部值也可以保存在寄存器里。 |
| Go 堆 | 由运行时分配、由 GC 管理的对象 | `receive` 返回后，仍被全局切片引用的数据包底层数组。 |

前四项描述程序装载时的代码和静态数据，栈和堆描述执行期间的内存用途。进程还可以映射动态库、文件等，具体段名和布局与平台有关。[Windows PE 格式](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) · [Go 链接器的数据布局](https://github.com/golang/go/blob/go1.26.0/src/cmd/link/internal/ld/data.go)

```go
var mode = "ranked"
var lastPacket []byte

func receive(n int) {
    buf := make([]byte, n)
    lastPacket = buf
}
```

`mode` 本身是可改写的全局字符串变量，保存数据指针和长度。执行 `mode = "casual"`，更新的是这两项。类似地，`lastPacket = buf` 把切片的数据指针、长度和容量复制到全局变量。函数返回后，`lastPacket` 仍引用同一块底层数组。

## 2. 栈增长时，指针为什么仍然有效

```go
package main

func descend(n int, p *int) {
    if n == 0 {
        *p += 5
        return
    }
    descend(n-1, p)
}

func score() int {
    x := 10
    descend(10000, &x)
    return x
}

func main() {
    println(score())
}
```

栈帧是一次函数调用在 goroutine 栈上使用的空间，调用返回后可以复用。最深层的 `descend` 执行 `*p += 5` 时，`score` 还在等待返回，每一层传下去的 `p` 都指向同一个 `x`。整个访问过程都落在这次 `score` 调用之内，因此 `x` 可以留在它的栈帧里。

栈空间不足时，Go 运行时先尝试把容量翻倍，放不下当前所需空间时继续倍增。运行时申请更大的连续栈，复制正在使用的部分，再根据编译器的指针信息等修正活跃指针。`x` 随栈帧搬到新位置后，`p` 仍指向它，旧栈可以释放。[栈增长](https://github.com/golang/go/blob/go1.26.0/src/runtime/stack.go#L1147-L1187) · [栈复制与指针修正](https://github.com/golang/go/blob/go1.26.0/src/runtime/stack.go#L900-L990)

**本机验证。** 以 `stack.go` 保存上例，`go run -gcflags=-l stack.go` 输出 `15`。关闭内联后，逃逸诊断（`-l -m=2`）给出 `p does not escape`。汇编（`-l -S`）中，`score` 从 `main.x+16(SP)` 取地址传给 `descend`，递归结束后从同一栈槽读值。结果和栈槽由运行、编译验证，实际搬栈次数未采集。

## 3. 逃逸分析与内联

**判断生命周期时，要看最后一次可能使用指针时，目标变量所在的栈帧还在不在。** 编译器在编译时分析指针可能流向哪里。取地址并传给别的函数，仍有机会使用栈存储。如果指针被存到全局，函数返回后还要访问它指向的局部变量，该对象就需要比这次调用活得更久。[Go FAQ 关于栈与堆](https://go.dev/doc/faq#stack_or_heap)

```go
func relay(p *int) *int { return p }

func score() int {
    x := 10
    q := relay(&x)
    return *q
}
```

即使关闭内联，`relay` 返回时，`x` 所属的 `score` 仍在运行。`score` 在返回前通过 `q` 读出整数，外部拿到的是值。如果改成把 `q` 存进包级的 `saved *int`，`score` 返回后仍可通过 `saved` 读取 `x`，这个版本的 `x` 需要堆存储。全局区保存的是指针 `saved`。

把 `x` 的声明移进返回指针的函数，再比较下面这个独立例子。

```go
func makeScore() *int {
    x := 10
    return &x
}

func score() int {
    return *makeScore()
}
```

| 本机编译条件 | 从 `score` 调用点观察到的结果 |
|---|---|
| 关闭内联（`-l`） | `score` 调用 `makeScore`。调用方解引用时 `makeScore` 已返回，后者的汇编中有 `CALL runtime.newobject`。 |
| 开启内联 | 诊断有 `inlining call to makeScore`。`score` 的汇编直接把整数 10 放入返回寄存器，省去了该调用点的对象分配。 |

单独编译的 `makeScore` 函数体仍可报告 `moved to heap: x`。判断一次调用的实际行为，要把逃逸诊断与**该调用点**的内联结果对应起来。栈增长发生在运行时，编译器选择堆存储的对象从分配时起就按堆对象处理。

## 4. 从一个指针找到两个待分配的对象

```go
type Packet struct {
    Body *[64]byte
}
```

假设 `Packet` 和目标数组都要在堆上分配。在 amd64 上，`*T` 指针值占 8 B，无论 `T` 是一个字节、一个大数组，还是另一个指针。指针宽度由目标架构决定，例如 386 上是 4 B。

| 对象 | 如何计算大小 | GC 标记这个对象后做什么 | 本例的槽位 |
|---|---|---|---|
| `Packet` 本身 | 唯一字段 `Body` 是指针，占 8 B | 读取 `Body`，沿指针继续追踪数组 | 8 B，`scan` |
| `Body` 指向的 `[64]byte` | 64 个字节连续存放，整个数组是一个 64 B 对象 | 数组内部没有指针，追踪到这里结束 | 64 B，`noscan` |

**`noscan` 指对象内部没有 GC 需要追踪的指针。** 其他对象仍可以指向它，GC 仍会标记它存活。标记回答“这个对象是否可达”，扫描负责找出“从它还能走到哪些对象”。[Go GC 指南](https://go.dev/doc/gc-guide#Tracing_garbage_collection)

## 5. 小对象怎样从 span 取到槽位

`span` 是一段连续的 Go 堆页，`mspan` 记录它的页范围、槽大小和分配状态等信息。“64 B 规格”指**每槽 64 B**。Go 1.26.0 中，8 B、16 B、64 B 这三种规格的 span 都占 8192 B。小对象的 `spanClass` 同时区分槽的大小和 `scan` / `noscan`。[大小类别表](https://github.com/golang/go/blob/go1.26.0/src/internal/runtime/gc/sizeclasses.go#L5-L13)

**槽数更正。** 课堂上把 8192 B 直接除以槽大小。实际创建 span 时，运行时先扣除放在 span 内部的 GC 元数据，再计算可分配槽数。以本机默认启用的 Green Tea GC 为例，16 B 和 64 B 的 `noscan` span 都预留 128 B，实际分别有 **504 个槽**和 **126 个槽**。64 B 这档的计算是 `(8192 − 128) / 64 = 126`。[实际槽数计算](https://github.com/golang/go/blob/go1.26.0/src/runtime/mheap.go#L1461-L1486) · [标记信息布局](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgcmark_greenteagc.go#L66-L71) · [适用条件](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgcmark_greenteagc.go#L252-L260)

以堆上的 `[64]byte` 为例：

1. **`mcache` 从当前 span 取一个槽。** 每个 P（执行 Go 代码的调度资源）有自己的 `mcache`。如果 64 B、`noscan` 类别的当前 span 还有空槽，本次分配在这里就能完成。
2. **`mcentral` 以 span 为单位补充。** 当前 span 用满时，`mcache` 找相同类别的 `mcentral`。运行时为每个 `spanClass` 分别维护 `mcentral`，其中区分还有空槽的 `partial` 和已满的 `full`，还会区分本轮是否已清扫。
3. **`mheap` 按页提供空间。** 如果 `mcentral` 在可用 span 和本轮尝试清扫的 span 中仍找不到空槽，就向 `mheap` 申请连续堆页组成新 span。堆内有足够的合适空闲页时可以直接利用，必要时才向操作系统扩充堆。[分配层次](https://github.com/golang/go/blob/go1.26.0/src/runtime/malloc.go#L19-L45) · [mcentral 取 span](https://github.com/golang/go/blob/go1.26.0/src/runtime/mcentral.go#L82-L202)

**为什么交给 `mcache` 的 span 可以是半满的？** 假设一个 64 B、`noscan` span 的 126 个槽曾经全部用完，后来常规清扫回收了其中 30 个对象。剩下的 96 个对象仍在原处，`mcentral` 可以将这个有 30 个空槽的 span 交给另一个 P。新 P 分配一个对象后还有 29 个空槽，之前指向存活对象的指针仍然有效。如果常规清扫后整个 span 都空了，页通常可以归还 `mheap`。[清扫后的 span 去向](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgcsweep.go#L786-L796)

## 6. tiny 块、普通小对象和大对象

| 独立申请的堆对象 | 分配与回收粒度 |
|---|---|
| `[8]byte` | 符合 tiny 条件。`mcache` 记录当前 16 B tiny 块的地址和偏移，对齐后有空间就从块内划出 8 B。两个这样的对象可以共用一个块。只要其中一个仍可达，整个块就保留。 |
| `[16]byte` | 普通 tiny 路径要求 **1～15 B 且无指针**。恰好 16 B 的数组走普通小对象分配，独占一个 16 B、`noscan` 槽。零大小对象有单独处理路径。 |
| `[64]byte` | 占用一个 64 B、`noscan` 槽。GC 清扫时可以单独回收这个槽，同一 span 里其他对象可以继续存活。 |
| `[64 * 1024]byte` | 数组占 64 KiB，走大对象路径，向 `mheap` 申请 8 个连续的 8 KiB Go 堆页，由这个数组独占一个 span。普通小对象 span 里的零散空槽不能拼给它使用。 |

因此，**tiny 块就是 16 B、`noscan` 规格 span 中的一个槽**。分配器再从这个槽里划出空间，满足多个独立的微小分配请求。选路径时按整个待分配对象看大小和指针布局。数组里的每个 `byte` 属于同一个数组对象。[tiny 分配条件与实现](https://github.com/golang/go/blob/go1.26.0/src/runtime/malloc.go#L1184-L1207) · [块内分配与申请新块](https://github.com/golang/go/blob/go1.26.0/src/runtime/malloc.go#L1270-L1342) · [大对象申请堆页](https://github.com/golang/go/blob/go1.26.0/src/runtime/mcache.go#L241-L260)

## 7. 口答与回访

| 题目 | 本人作答与纠正 |
|---|---|
| `relay` 把 `&x` 原样返回，`score` 再解引用，`x` 必须逃逸吗？ | 独立答对。最后一次解引用时 `score` 的栈帧还在，外部拿到整数值。 |
| 当前 64 B span 已满，同类 `mcentral` 有一个剩 30 槽的 span | 独立答对向 `mcentral` 取 span。随后厘清整段交接和空槽分配的区别。 |
| `Packet{Body *[64]byte}` 对应哪些规格？ | 答对字段占 8 B，也算对目标数组共 64 B。初答给数组选 16 B 槽，修正为整个数组占一个 64 B、`noscan` 槽。 |
| 64 KiB 接收缓冲区怎样分配？ | 独立答出向 `mheap` 申请若干页、由对象专用。8 个连续 Go 堆页是讲解时补充的计算。 |

# 11 GC、写屏障与内存目标

以 Go 1.26.0 为实现基线。前半篇沿着一个堆对象从被发现到被清扫的过程，后半篇用同一组数字推导 GC 的频率和 CPU 成本。

## 1. 从哪里开始找对象？有环怎么办？

Go 通过**可达性**判断普通堆对象是否仍然存活。从 GC 根出发，沿指针能走到一个对象，程序就仍有途径使用它。常见起点是全局变量中的指针，以及 goroutine 栈上仍活跃的参数或局部指针。局部变量即使还在词法作用域内，最后一次使用之后也可能已不再活跃。运行时还会扫描自身维护的某些堆外数据结构中的堆指针。[Go 1.26.0 根扫描](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgc.go#L29-L58)

假设房间持有房主对象，房主也持有当前房间。两处独立的入口都通向这个环：

```text
全局变量 currentRoom ──→ Room ⇄ Player
                          ↑
等待消息的 goroutine 中的 r ─┘
```

| 发生了什么 | GC 会怎样处理 |
|---|---|
| 从全局变量找到 Room，再从 Player 指回 Room | Room 已被标记，遍历到这个环就能收住，不会沿环无限扫描。 |
| 把 currentRoom 清空，但等待中的 goroutine 醒来后还要用 r | 活跃的栈指针 r 仍能到达 Room，两个对象都保留。 |
| 所有外部入口都已断开，随后开始下一轮标记 | 两者之间虽然仍有指针，GC 从任何根都走不到它们，本轮清扫即可回收。无需手动拆环。 |

**切片也是同一条规则。** 若全局变量 `lastHeader = packet[:32:32]`，从它仍能走到原来的 4 MiB 底层数组。限制容量只影响切片可扩展的范围。若只想保留头部，可以分配独立的 32 字节切片，复制头部并让 `lastHeader` 指向新切片；当原数组的所有引用都消失后，它就可以被回收。

## 2. 已经发现一个对象，为什么还要扫描它？

设 A 有三个字段：整数 Value 和两个指针 Left、Right。**类型的指针布局告诉 GC 去哪里读，字段的当前值告诉 GC 能走到谁。** 扫描 A 时，GC 跳过 Value，读取 Left、Right。若分别指向尚未标记的 B、C，就标记它们，并为其中还含指针的对象安排扫描。`nil` 结束这条路径；两个字段指向同一对象时，已有标记可以避免重复安排。[Go 1.26.0 堆对象指针布局](https://github.com/golang/go/blob/go1.26.0/src/runtime/mbitmap.go#L118-L157)

三种颜色描述的是**本轮标记进度**：

| 状态 | 含义 | 用 `根 → A → B` 推演 |
|---|---|---|
| 白 | 尚未发现 | 刚从根发现 A 时，B 可能仍是白色，尽管 B 已经可达。 |
| 灰 | 已发现，还有指针待扫描 | A 进入待扫描集合。之后扫描 A，才会沿字段发现 B。 |
| 黑 | 已标记，扫描工作已完成 | A 的指针都检查完就可以标黑，无需等 B 的子对象也扫完。 |

待扫描集合可用一个工作队列推演。先扫 B 或先扫 C 都可以，算法不依赖先进先出。三色是理解正确性的抽象；Go 1.26 的具体扫描组织可回看[三色标记、混合写屏障与 Green Tea](../../footprint/04_Go/14_Go_GC：三色标记、混合写屏障与_Green_Tea.md)。

## 3. 并发修改指针为什么需要写屏障？

假设 A 已经扫完，B 还没扫，只有 B.next 指向白色的 C。先假想没有写屏障：

```text
改动前    根 → A（黑）             根 → B（灰）→ C（白）
业务执行  A.next = B.next
          B.next = nil
改动后    根 → A（黑）→ C（白）    根 → B（灰）
```

第一步让程序可以从 A 访问 C。第二步切断 GC 原本能从 B 发现 C 的路径。此后扫描 B 只会读到 nil，而 A 已经扫过，**一个仍然可达的对象就可能漏标**。如果另一个待扫描对象也指向 C，这条路径仍能让 GC 发现它。

看一次具体赋值 `A.next = p`。假设旧的 A.next 指向 B，p 指向 C。屏障关注的是这次堆指针写入涉及的两个目标：

| 屏障 | 保护谁 | 写入 nil 时 |
|---|---|---|
| 删除部分 | 将被覆盖的旧指针指向 B，保护 B。前例清空 B.next 时，旧目标则是 C。 | 仍要考虑旧目标。 |
| 插入部分 | 即将写入的新指针指向 C，保护 C。若 p 是尚未扫描的栈上通向 C 的唯一入口，把它移入黑色 A 后又清空 p，就靠这一步避免漏标。 | 新值没有指向任何对象。 |

算法模型中，在写入新值前保护旧目标；当前 goroutine 的栈尚未扫描时，还需要保护新目标。实际常见写入路径会缓冲新旧指针记录，批量处理。保护白色目标意味着标记它，并为其尚待扫描的引用安排工作。假如 C 又指向 D，就要通过扫描 C 才能继续发现 D。普通整数字段更新无需 GC 指针写屏障。[混合屏障算法说明](https://github.com/golang/go/blob/go1.26.0/src/runtime/mbarrier.go#L20-L57) · [写屏障缓冲](https://github.com/golang/go/blob/go1.26.0/src/runtime/mwbbuf.go)

## 4. 业务不停分配，一轮标记怎样结束？

| 阶段 | 业务与 GC 各自在做什么 |
|---|---|
| 开始标记前的 STW | 暂停业务执行，完成上一轮清扫的收尾，开启写屏障并准备根扫描任务。所有 P 就绪后恢复业务。 |
| 并发标记 | GC 扫描根并追踪堆对象，业务可以继续执行。扫描某个 goroutine 的栈时会单独暂停它。 |
| 标记终止的 STW | 初步确认标记工作耗尽后暂停业务并复核。若仍有工作，可以恢复并发标记；确认完成后做收尾、关闭标记期写屏障，转入清扫。 |
| 并发清扫 | 业务继续运行。运行时根据本轮标记结果清扫，将未标记的普通堆对象占用的空间腾出来供后续分配。 |

**新分配和新引用是两件事。** 并发标记期间，新分配的堆对象直接标黑，刚分配时其指针字段为零值。业务不断往链表尾部接新节点，链表可以越变越长，本轮待扫描集合仍可以逐步清空。若后来向节点的字段写入一个已有的白色对象的地址，写屏障会保护相应目标。[Go 1.26.0 GC 阶段](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgc.go#L24-L83)

**某个工作者发现队列空了，还不能宣布结束。** 根任务和正在处理的扫描工作都要完成，运行时还要检查全局工作、各 P 的本地工作以及写屏障缓冲。刷新缓冲可能带来新的标记工作；进入 STW 后还要复核这段过渡期间的指针写入。[标记终止判定 gcMarkDone](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgc.go#L1015-L1125)

**已经标记、后来又不可达的对象叫浮动垃圾。** 以前例的 B 为例，若 `A.next = nil` 删去了最后一条引用，而删除屏障已保护 B，本轮清扫会保留它。如果下一轮它仍不可达，届时可以回收。房间和玩家构成的环在本轮标记后才失去最后一个入口，也遵循同样的规则。

## 5. GOGC、GOMEMLIMIT 和分配速率各影响什么？

沿用课堂数字：上轮**存活堆 100 MiB**，**根扫描量 20 MiB**。假设影响软限制预算的栈、运行时元数据等**其他开销约 40 MiB**。20 MiB 衡量扫描工作，40 MiB 用于估算运行时总内存中留给堆的份额。两者用途不同，即使部分对应同一块栈内存，也无须在一个公式里相加。

1. **先算 GOGC 给出的堆目标。** 允许增长量 ≈（上轮存活堆 + 根扫描量）× GOGC / 100。把允许增长量加回上轮存活堆，就得到堆目标。运行时根据分配和扫描速度提前启动标记，以便在堆增长到目标附近时完成标记。[GOGC 官方指南](https://go.dev/doc/gc-guide#GOGC) · [Go 1.26.0 GC 节奏控制](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgcpacer.go)
2. **再看软限制是否收紧目标。** GOMEMLIMIT 约束 Go 运行时管理的内存，统计口径是 `runtime.MemStats.Sys - runtime.MemStats.HeapReleased`。用软限制减其他开销，可以粗估留给堆的预算。实际运行时会预留余量；如果仅存活对象就已超出预算，调快 GC 也无法释放仍然可达的对象，运行时允许超过软限制。[内存软限制](https://go.dev/doc/gc-guide#Memory_limit)

| GOGC | GOMEMLIMIT | GOGC 给出的堆目标 | 软限制留给堆的预算（粗估） | 哪个先起作用 |
|---:|---:|---:|---:|---|
| 100 | 300 MiB | 100 + 120 = 220 MiB | 300 − 40 = 260 MiB | GOGC |
| 100 | 200 MiB | 220 MiB | 200 − 40 = 160 MiB | 软限制 |
| 200 | 200 MiB | 100 + 240 = 340 MiB | 仍约 160 MiB | 仍是软限制 |

**最后看分配速度。** 假设软限制没有收紧目标，GOGC=100，每轮可增长约 120 MiB。每秒分配 60 MiB，大约 2 秒一轮；每秒分配 120 MiB，大约 1 秒一轮。这里算的是相邻周期间隔。若玩家状态、根扫描量及对象结构都稳定，每轮扫描成本也大致稳定。优化临时消息分配使分配速率减半时，每秒 GC 轮数约减半，每秒消耗的 GC CPU 时间也会相应下降。[GC 成本模型](https://go.dev/doc/gc-guide#Additional_notes_on_GOGC)

## 6. 练习、纠正与续接

| 课堂问题 | 本人作答与纠正 |
|---|---|
| `packet[:32:32]` 能否释放原 4 MiB 数组？ | 正确指出容量变小，数据指针仍指向原数组。 |
| 指向 C 的引用从 B 移到已扫完的 A 后，程序和 GC 分别能否找到 C？ | 正确指出程序可通过 A.next 找到 C。补全理由：B 已失去通向 C 的边，A 已扫完。 |
| `A.next = p`，原指向 B，p 指向 C。两个屏障保护谁？ | 初答删除部分保护 p，纠正为旧目标 B。再问写入 nil，正确答出删除部分保护 B，插入部分没有目标。 |
| 已标记的 B 在本轮失去最后一个引用，还回收吗？ | 正确答出本轮保留，因为 B 已标记。 |
| 不断分配会导致标记无法结束吗？ | 初次复述把新分配与写入新引用混在一起。回访时区分对象分配时直接标黑、指针变更可能产生扫描工作。 |
| Room 和 Player 相互引用，删掉全局入口后能否回收？ | 已归纳出从所有根均不可达时可回收；追问后补充了等待中的 goroutine 仍持有活跃指针的情形。 |
| GOGC 从 100 调到 200，软限制仍是 200 MiB | 初答堆目标从 240 变为 380。按题设独立计算 GOGC 目标应为 220 → 340 MiB，两者都受约 160 MiB 的软限制预算约束。 |
| 软限制调到 300 MiB，其他开销约 40 MiB | 堆目标 220 MiB 答对，预算初算为 220 − 40。纠正为从软限制扣减，即 300 − 40 = 260 MiB。 |
| 玩家状态稳定，临时消息分配速率从 120 降到 60 MiB/s | 独立答出增长空间不变、GC 轮数减少；根扫描量和对象结构稳定，单轮工作量接近，因此每秒 GC CPU 时间下降。 |

**下次回访**：换一组数字，先算 GOGC 目标，再从 GOMEMLIMIT 扣除其他开销，最后判断哪一项约束堆增长。机制题可复述“新分配一个节点”和“把已有白色对象接入黑色节点”分别会给本轮标记带来什么工作。

**核验范围**：根扫描、指针布局、写屏障和标记终止已对照 Go 1.26.0 源码。堆目标和周期间隔按官方 GC 指南的稳态模型推导，本轮未运行性能实验。

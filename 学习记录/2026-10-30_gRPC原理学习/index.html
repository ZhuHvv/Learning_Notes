先把四个维度分开

前面的讨论连续切换对象、协程、数据格式和调用阶段，容易把它们当成一条层级链。它们其实是四个不同维度：

维度包含什么判断问题
对象与生命周期Stub、ClientConn、transport、RPC 状态、Stream、缓冲这份状态由谁持有，复用多久？
执行者G-call、连接 reader / writer、服务端 G-rpc现在是谁在运行代码？
数据形式对象 → Protobuf 字节 → gRPC 消息 → HTTP/2 帧 → TCP 字节当前操作对象、消息还是字节块？
阶段与状态建流、入队、写出、收到、解码、最终状态这一步完成究竟保证什么？

对象的粒度

对象生命周期 / 粒度职责与边界
生成的 Stub通常长期复用强类型方法包装，持有 ClientConnInterface。不是连接或协程。
ClientConn / gRPC Channel目标服务的长期逻辑通道解析、选择、管理连接。可以关联零条、一条或多条实际连接。
http2Client / http2Server连接级 transportHTTP/2 状态、活动流表、controlBuf、主要读写循环。
clientStreamWrapper / clientStream一次逻辑 RPC上下文、调用选项、发送接收、重试相关状态。
csAttempt一次尝试关联选中的 transport 和底层流。重试更换尝试及底层流。
transport.ClientStream / ServerStream某连接上某个 Stream ID双方各有独立对象，通过 Stream ID 对应，不跨进程共享对象。
recvBuffer每个传输流字节块和终止事件。内部 Go chan + backlog，不是 Protobuf 消息队列。
controlBuf每条连接writer 消费的数据及控制任务；writer 另有各流待发送项。
三个不同的“通道/流”：Go chan 是进程内同步结构；gRPC Channel 是访问远端的逻辑通道；HTTP/2 Stream 是连接中的逻辑传输流。

沿一次 GetUser 调用走完闭环

GetUser 是教学接口名。真实生成代码证据来自仓库的 Greeter.SayHello 示例；此处没有声称仓库里存在 GetUser 业务实现。

0

初始化供后续调用复用

B 注册服务名、方法描述与业务对象，再监听端口。A 创建 ClientConn 和 Stub。NewClient 本身不做网络 I/O；首次使用可触发建连。主图从连接可用开始，两端已有各自 transport 与主要 I/O 协程。

1

G-call 执行 Stub → Invoke → 建流

Stub 提供完整方法路径及输入输出对象。Invoke 经过客户端 Unary 拦截器，创建 RPC 状态；picker 选择 transport，为本次尝试创建底层流并提交请求 HEADERS。创建 Stream 不意味着新建 TCP 连接。

2

G-call 编码请求，提交发送任务

SendMsg 在调用方协程完成编码、可选压缩与 gRPC 消息封装。transport.write 检查本地 writeQuota，把带 Stream ID 的内部任务放入 controlBuf。内部 dataFrame 项可能还要拆成多个真正的 DATA 帧。

Unary 唯一请求结束客户端发送方向，但保留接收方向。SendMsg 成功不等于字节已到对端。

3

客户端 writer 组织并写出 HTTP/2 帧

G-cw 取任务，维护各流待发列表，检查流与连接级窗口，切分并交错发送。HEADERS 携带方法与 Metadata，DATA 携带 gRPC 消息。字节经 TCP 发送；配置 TLS 时还经过加密层。

4

服务端 reader 建流、调度和投递

HandleStreams 读取帧；operateHeaders 创建 ServerStream，保存路径、Metadata、deadline，放入 activeStreams 并默认调度 G-rpc。请求体此时可能未到齐。后续 DATA 按 Stream ID 入该流 recvBuffer。reader 不做 Protobuf 解码，也不执行 GetUser。

5

G-rpc 路由、读齐请求，进入业务

handleStream 拆出服务名和方法名，在注册表中找到描述，经 processRPC / wrapUnaryHandler 进入生成 handler。生成 handler 创建请求对象，调用解码函数；RecvMsg 从本流缓冲读齐消息头和 N 字节正文，解压、反序列化。

本版本 Unary 还确认请求方向 EOF、没有第二条请求，之后进入 Unary 拦截器和业务方法。调度开始不等于业务已经开始。

6

响应消息与最终状态分别入队

正常返回对象经服务端 SendMsg 编码入队；processRPC 再 WriteStatus。G-sw 按流顺序发出响应 HEADERS、DATA 和含 grpc-status 的 Trailers。业务错误可以不带响应消息，直接返回非 OK 状态。

7

客户端 reader 分开处理数据和状态

G-cr 用 activeStreams[StreamID] 找流。DATA 投入 recvBuffer；响应 HEADERS 设置 Metadata / 压缩信息并通知 headerChan；Trailers 先保存 status / trailer，再向流缓冲投入 EOF 并完成终止通知。不能把每个帧都当成业务消息。

8

原 G-call 解码并确认结果

G-call 沿 Invoke 进入 RecvMsg，按需等待本流头部或数据。取齐完整消息后解压、Unmarshal，填入 reply。clientStreamWrapper 对 Unary 再读一次，只有恰好一条响应且最终状态 OK 才成功；第二条响应或最终非 OK 均报错。

GetUser 返回后原业务协程继续执行。不是 reader 直接执行调用方后续代码。

谁在等待，谁让它继续

位置等待者等待内容推进或终止
选连接 / 建流G-call解析结果、可用 transport、流额度资源就绪或错误 / deadline / 取消；行为受配置影响。
SendMsg 提交G-call / G-rpc本流本地 writeQuotawriter 消耗待发数据并补额度，或流关闭。
HTTP/2 写出writer 管理待发流流 / 连接窗口及网络可写性流窗口不足时，其他有额度的流可继续；连接窗口不足时，全部流的 DATA 等待。底层写阻塞时，其他流也不能绕过该连接写出。

最终结局客户端 G-call响应结束与 grpc-statusTrailers 或流 / 连接错误；一个 DATA 不代表完成。

等待不是忙轮询，也不代表独占操作系统线程。Go 的 channel / 网络等待可挂起 goroutine，再由运行时调度继续。reader 不查询数据库，但仍可能等待网络、流控或框架资源，不能说它永远不阻塞。

容易混淆的边界

连接、Stream、goroutine 不能画等号

连接承载多条流，每流有独立状态及缓冲。多个 RPC 共享主要 I/O 协程；同一个 G-call 依次经过 Stub、Invoke、SendMsg、RecvMsg。服务端默认每 RPC 调度处理 goroutine。主要 I/O 是一读一写，但整个生命周期不只有两个 goroutine。

reader 解析帧；RecvMsg 解析消息

消息可以跨多个 DATA 帧；DATA 帧也可包含多条消息的数据。reader 按 Stream ID 分发；消息长度、解压、业务字段解码由消费本流的调用链处理。

对象 → Protobuf 字节 → [1 字节压缩标志 | 4 字节长度 | N 字节正文]
     → HTTP/2 DATA 帧 → TCP 字节流
接收端逆向解析；这些边界不是一一对应。
入队成功、收到消息、RPC 成功不同

SendMsg 成功只说明当前提交成功。解码一条响应后仍看最终状态。数据库成功但响应丢失时，客户端仍可能超时。重试要靠业务幂等或结果核对；Stream ID 不能替代业务请求 ID。

调度可以提前；Unary 业务需要完整请求

HEADERS 足以创建流、查表、调度处理。G-rpc 随后在 RecvMsg 等请求数据；本版本还确认请求发送方向结束，再调用生成 handler 后续的拦截器与业务方法。

取消与断线如何作用

客户端取消可关闭本流并发 RST_STREAM。服务端处理该帧或连接关闭时取消对应流 context；读写等待经关闭与错误路径解除。业务代码与驱动仍须配合取消，已提交事务不会自动回滚。连接断开可能影响其全部活动流。

三种发送限制

writeQuota 约束本流本地待发积压；HTTP/2 流窗口约束本流 DATA；连接窗口约束连接 DATA 总量。grpc-go 的接收流窗口和连接窗口做了解耦，避免慢流无必要地饿死其他流。应用持续 Recv 后塞无界队列，仍可能耗尽内存。

流式与 Unary 共享机制，完成条件不同

流式 RPC 可在一次调用中多次 Send / Recv；一个流可一发一收并行，同方向操作需串行。Unary 的消息数及结束检查由包装逻辑完成，流式不能每收一条消息就要求调用结束。

未覆盖与不应推导的结论

这不是所有语言通用的 goroutine 结构，也未混入 ServeHTTP 的另一套 HTTP/2 实现。没有测量吞吐或延迟，没有展开完整重试状态机。重试换 attempt 与底层流，已建立流不会迁移。TCP 跨流队头阻塞仍存在。

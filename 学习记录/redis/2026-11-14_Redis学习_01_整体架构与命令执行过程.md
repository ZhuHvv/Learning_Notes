## 1. 先建立完整脉络

理解 Redis 网络与执行模型，可以沿着以下问题推进：

1. **命令由谁执行？** 单个实例的常规数据命令，由主线程串行执行核心逻辑。
2. **一个线程怎样关注大量连接？** 通过 I/O 多路复用集中等待多个 fd 的就绪事件。
3. **处理某条连接时怎样避免一直等它？** 使用非阻塞 socket，暂时无法读写时及时返回。
4. **读到的数据怎样变成命令？** 先进入输入缓冲区，再按 RESP 协议解析边界。
5. **网络事件与定时任务怎样组织？** 由 `ae` 事件循环依次分发和执行。
6. **Redis 8.10.3 怎样使用 I/O 线程？** I/O 线程运行自己的事件循环，负责被分配连接的收发与解析，主线程执行命令。
7. **线程之间怎样交接？** 共享内存队列保存待处理客户端，通知 fd 在必要时唤醒接收线程。
8. **交接时怎样保护数据？** 队列操作使用互斥锁，客户端相关状态通过分阶段处理和交接避免并发修改。

## 2. “Redis 单线程”的准确含义

在一个 Redis 实例中，常规核心数据命令访问、修改键空间的执行逻辑由主线程串行完成。这个说法需要限定对象和阶段，不能扩展为“整个 Redis 进程只有一个线程”或“集群中只有一个线程执行命令”。

串行执行的主要收益：

- 减少多个命令同时修改字典、链表、跳表等共享结构所需的并发控制。
- 简化多个内部结构之间的一致性维护。
- 减少锁竞争、线程协调、上下文切换及跨核心缓存一致性等额外成本；实际收益取决于负载，本文没有测量。

代价是：单个实例的这部分执行无法直接依靠多个线程并行推进。一个持续占用主线程的耗时命令，会延迟后续请求和定时任务。

后台工作可以由其他线程或子进程承担。例如异步内存释放、部分 AOF 刷盘工作，以及持久化子进程。具体任务、线程与进程的分工，要在对应专题中继续核对；“命令串行执行”并不意味着它触发的所有后续工作也只能同步完成。

源码阅读时可以从命令执行链路中的 `call()` 找到对具体处理函数 `c->cmd->proc(c)` 的调用。该调用链用于理解命令执行位置，不能覆盖所有模块、阻塞及重入路径。

## 3. fd、epoll 与 Reactor 各负责什么

### 3.1 监听的是 fd 的就绪状态

“一个线程监听多个 I/O 端口”不够准确，应表述为：**一个线程通过多路复用机制关注多个文件描述符的就绪状态。**

fd 是程序访问打开对象的句柄。在本专题中，主要包括监听 socket、已建立连接的客户端 socket，以及线程间通知对象的 fd。

Redis 可以只监听一个 TCP 端口，但接受多个客户端连接后，会得到多个不同的客户端 fd。端口、连接和 fd 不是同一个层次的概念。

### 3.2 epoll 与 ae 的分工

| 层次 | 职责 |
|---|---|
| 非阻塞 socket | 暂时无法继续读写时，避免调用者一直等待该连接 |
| epoll | 集中关注 fd 的就绪状态，并向调用者返回就绪事件 |
| ae | 保存事件注册关系，组织等待、回调分发和时间事件处理 |
| 业务回调 | 接受连接、读取请求、解析命令、推进执行、发送响应等 |

Linux 下 Redis 使用 epoll；`ae` 也封装了其他平台的实现，不能把 epoll 当作所有平台的唯一后端。

Reactor 的核心是“等待就绪事件，再分发给处理函数”。这个模型本身不限定线程数量，也不意味着分发回调时一定要切换线程。`ae` 的文件事件分发是在运行该事件循环的线程中直接调用回调，回调内部再决定是否需要线程间交接。

### 3.3 注册信息与本轮就绪结果不同

| 数据结构 | 含义 |
|---|---|
| `eventLoop->events[fd]` | 该 fd 注册的事件类型、读写回调及上下文 |
| `eventLoop->fired[i]` | 本轮返回的第 i 个就绪 fd 及事件类型 |

`events` 是注册关系，不是“尚未就绪的连接集合”；`fired` 是本轮结果，不保存命令正文。

`epoll_ctl()` 用于维护内核中的关注关系。`epoll_wait()` 等待就绪事件，并在返回用户态之前由内核把结果写入调用者提供的 `events` 数组。Redis 随后将结果映射到自己的 `fired` 数组，再根据注册信息调用回调。

用户态程序无需在 `epoll_wait()` 返回后重新遍历全部连接来判断谁就绪。内核维护就绪状态的更底层机制，本轮没有展开。

参考：[Redis 8.10.3 ae.c](https://github.com/redis/redis/blob/8.10.3/src/ae.c)、[Linux epoll_wait 手册](https://man7.org/linux/man-pages/man2/epoll_wait.2.html)。

## 4. 集中等待为什么仍需配合非阻塞读写

### 4.1 比较的是一个 fd 与一组 fd

| 等待位置 | 等待对象 | B 可读时的影响 |
|---|---|---|
| 阻塞在 A 的 `read()` | A 这一个 fd | 不会因为 B 可读就让 A 的读取返回 |
| 阻塞在 `epoll_wait()` | 注册在这个 epoll 实例中的一组 fd | 若关注 B 的可读事件，就可以使等待返回 |

不能概括为“epoll 等待 fd，read 等待连接”：连接也是通过 fd 访问的。关键是等待范围与返回条件。

### 4.2 非阻塞不等于线程永不等待

假设连接正常，当前没有可读数据：

- 阻塞读取可能停在这条连接上等待。
- 非阻塞读取返回 `-1`，通过 `EAGAIN`／`EWOULDBLOCK` 表示暂时无法读取。

事件循环因而可以统一在 `epoll_wait()` 中等待，在处理具体连接时使用非阻塞操作，避免被单个客户端拖住。socket 的非阻塞属性需要设置；使用 epoll 不会自动完成这件事。

一次可读通知不保证后续每次读取都有数据。例如第一次读取拿到了前 30 字节，之后再次读取时，后续数据可能尚未到达。非阻塞读取可以及时返回，让线程继续处理其他工作。

这个例子用于解释非阻塞的作用，不代表 Redis 一定循环读取到凑齐完整命令。实际处理中，协议解析发现数据不足时，会保留输入数据和解析状态，退出本次处理。

还要区分：

- `read()` 不理解 Redis 命令边界。
- 即使是阻塞 `read()`，也不保证填满指定缓冲区才返回。
- 可读还可能对应 EOF 等情况；`EAGAIN`、读取返回 0 和真正错误的区别，后续继续复习。
- 非阻塞写也可能只写入一部分数据，或者因暂时没有发送空间而返回 `EAGAIN`；未发送内容需要保留进度并稍后继续。

参考：[Redis 8.10.3 socket.c](https://github.com/redis/redis/blob/8.10.3/src/socket.c)。

## 5. 从 TCP 字节流到完整命令：输入缓冲区与 RESP

### 5.1 socket 可读不等于收到完整命令

一次读取可能得到：半条命令、一条命令、多条命令，或者多条完整命令加下一条的一部分。TCP 提供字节流，命令边界由应用层协议识别。

Redis 的处理思路是：

```text
读取字节，追加到客户端 querybuf
    ↓
尝试按协议解析
    ├─ 不完整：保留数据及解析状态，后续继续
    └─ 完整：准备进入命令执行／线程交接流程
```

解析函数返回 `C_ERR` 在相关路径中可能表示数据暂时不完整，也可能涉及真正的协议错误，必须结合具体返回分支和错误状态判断，不能仅凭这个宏名称下结论。

### 5.2 RESP 怎样描述命令

RESP 是 Redis Serialization Protocol。普通命令请求通常表示为“由 bulk string 组成的数组”，第一个元素是命令名，后面是参数。

以 `SET name Tom` 为例，其编码可以写成：

```text
*3\r\n$3\r\nSET\r\n$4\r\nname\r\n$3\r\nTom\r\n
```

这里 `\r\n` 是回车和换行两个实际字节的书面表示。

| 片段 | 含义 |
|---|---|
| `*3\r\n` | 数组有 3 个元素，包含命令名 |
| `$3\r\nSET\r\n` | 3 字节的内容 `SET` |
| `$4\r\nname\r\n` | 4 字节的内容 `name` |
| `$3\r\nTom\r\n` | 3 字节的内容 `Tom` |

**`*` 后是元素数量，`$` 后是内容的字节长度，不是字符数。**

### 5.3 为什么要记录长度

没有长度字段，也可以设计分隔符协议；问题在于内容本身可能包含分隔符，此时需要额外的转义等规则。

bulk string 通过长度明确内容范围。例如内容是 `ab\r\ncd`，共 6 字节：

```text
$6\r\nab\r\ncd\r\n
```

解析器先读取长度 6，再将后续 6 个字节作为内容，其中的回车换行也是内容，最后消费外层结束符。参数因此可以包含换行、空字节等二进制内容。

### 5.4 源码入口及版本区别

阅读入口为 `readQueryFromClient()`、`processInputBuffer()`、`processMultibulkBuffer()`。

在早期讨论的 7.2.0 路径中，`multibulklen` 表示还剩多少个元素未解析，`bulklen` 表示当前元素长度，`argv` 保存解析出的命令名及参数。数据不足时保存状态，下次接着解析。

8.10.3 的 `processInputBuffer()` 还涉及 `pendingCommand`、`pending_cmds` 和命令预解析等组织方式，不能把 7.2.0 的字段使用和调用细节逐字套用过来。这些新结构本轮未逐字段展开。

参考：[RESP 官方规范](https://redis.io/docs/latest/develop/reference/protocol-spec/)、[7.2.0 networking.c](https://github.com/redis/redis/blob/7.2.0/src/networking.c)、[8.10.3 networking.c](https://github.com/redis/redis/blob/8.10.3/src/networking.c)。

## 6. ae 一轮循环到底做什么

`ae` 是事件库和事件循环逻辑，不是一个额外的“ae 线程”。主线程可以运行它，8.10.3 的 I/O 线程也可以分别运行各自的循环。

`aeMain()` 持续调用 `aeProcessEvents()`。正常路径的主要顺序是：

```text
beforeSleep
    ↓
计算本轮等待超时
    ↓
aeApiPoll → Linux 下的 epoll_wait
    ↓
afterSleep
    ↓
遍历 fired[]，调用注册的文件事件回调
    ↓
processTimeEvents：检查并执行到期时间事件
    ↓
下一轮
```

这里展示的是正常主循环的顺序，省略特殊标志、加载、脚本超时和重入路径。

### 6.1 等待前后钩子

主线程的 `beforeSleep()` 会推进待处理工作，例如线程间客户端交接、待写响应、AOF 缓冲写出，以及按条件执行维护操作。具体顺序和分支随版本变化。

`afterSleep()` 在多路复用返回后、文件事件分发前执行，处理更新时间缓存、模块相关同步等工作。

函数名中的 Sleep 不表示每轮一定休眠：就绪事件已经存在，或者超时设为 0 时，多路复用调用可以立即返回。

8.10.3 的 I/O 线程注册的是自己的 `IOThreadBeforeSleep()`、`IOThreadAfterSleep()`，不要与主线程同名阶段的具体职责混淆。

### 6.2 命令执行在哪里

命令执行可以由文件事件回调路径推进，也可以由主线程处理 I/O 线程交来的客户端时推进。不存在一个对所有情况都适用的“全部网络事件处理完，再统一执行全部命令”的固定阶段。

用于定位常规执行入口的简化链路是：

```text
processCommandAndResetClient
  → processCommand
  → call
  → 具体命令处理函数
```

普通读取路径可以由 `readQueryFromClient()`、`processInputBuffer()` 进入；I/O 线程解析出的请求则先交给主线程。命令执行与网络读写的线程归属应结合当前版本和配置判断。

一轮循环没有固定时长。网络负载、回调耗时和等待时长都会影响它；`server.hz` 不能解释为整个事件循环每秒只运行多少轮。

参考：[8.10.3 ae.c](https://github.com/redis/redis/blob/8.10.3/src/ae.c)、[server.c](https://github.com/redis/redis/blob/8.10.3/src/server.c)、[iothread.c](https://github.com/redis/redis/blob/8.10.3/src/iothread.c)。

## 7. 时间事件怎样设置、检查和触发

### 7.1 时间事件记录的是执行时刻和回调

`aeTimeEvent` 保存到期时间 `when`、回调 `timeProc` 和上下文 `clientData` 等信息。

注册 `serverCron` 时的代码为：

```c
aeCreateTimeEvent(server.el, 1, serverCron, NULL, NULL);
```

其中 1 表示首次延迟约 1 毫秒。内部根据当前单调时钟和延迟计算到期时刻，使用微秒保存。

执行回调后，返回的延迟毫秒数用于安排下一次执行；返回 `AE_NOMORE` 表示不再调度。`serverCron()` 返回 `1000 / server.hz`。例如当前值为 10，就请求在本次回调完成后约 100 毫秒再执行。

这不是严格定时承诺。动态频率、线程调度和主线程耗时工作都可能影响实际执行时刻。

### 7.2 到期不是独立线程来执行回调

正常事件循环中，`processTimeEvents()` 遍历时间事件链表，比较当前时间与各事件的 `when`，到期才调用回调。

8.10.3 中仍使用无序时间事件链表。一轮正常循环通常涉及两次遍历：

1. 等待前，`usUntilEarliestTimer()` 找最近的有效到期时间，决定等待上限。
2. 文件事件处理后，`processTimeEvents()` 检查并执行到期任务。

若时间事件数量为 T，两次扫描本身均为 O(T)，不包含回调执行耗时。不是每一轮都执行所有时间事件。

### 7.3 为什么时间事件和 epoll 有关系

要分清两个时间：

| 时间 | 谁决定 | 用途 |
|---|---|---|
| Redis 任务的到期时刻 | ae 注册与回调重调度逻辑 | 决定任务何时具备执行条件 |
| `epoll_wait()` 的超时 | Redis 根据最近任务计算并传入 | 防止主线程没有网络事件时无限等待 |

主线程要依次执行“等待网络事件、处理文件事件、检查时间事件”。如果任务还有 100 毫秒到期，而没有网络请求，Redis 可令 `epoll_wait()` 最多等待约 100 毫秒。

```text
主线程计算最近任务还有多久
    ↓
进入 epoll_wait 等待
    ↓
网络事件到来，或等待超时
    ↓
线程恢复运行，系统调用返回
    ↓
Redis 自己检查时间并调用到期回调
```

内核处理的是这一次等待的超时，不知道 Redis 的 `serverCron` 业务含义。Redis 的时间回调也不会因此抢占一个正在执行的普通长命令。

如果网络事件提前到来，主线程处理事件后再检查时间；下一轮重新计算剩余时长。不是第一次传入的超时还会在后台独立倒计时、到点另行执行 Redis 回调。

`serverCron` 承担周期维护入口的职责，例如客户端维护、数据库维护、复制检查和持久化任务管理。不同子任务可能有自己的执行条件和频率，并不是每次都做同样的完整工作。

参考：[8.10.3 ae.c](https://github.com/redis/redis/blob/8.10.3/src/ae.c)、[server.c](https://github.com/redis/redis/blob/8.10.3/src/server.c)、[epoll_wait 手册](https://man7.org/linux/man-pages/man2/epoll_wait.2.html)。

## 8. 接受新连接也是 ae 文件事件

| fd | 所属用途 | 可读时的典型处理 |
|---|---|---|
| 监听 socket fd | 等待新连接 | 调用 accept 接受待处理连接 |
| 客户端 socket fd | 某条连接的通信 | 读取请求字节，或识别关闭、错误等情况 |

Redis 将监听 fd 的 `AE_READABLE` 注册到主线程的 `server.el`。普通 TCP 接入链路为：

```text
监听 socket 可读
  → 主线程的 ae 分发文件事件
  → connSocketAcceptHandler
  → anetTcpAccept，得到新的客户端 fd
  → 初始化客户端
  → 配置允许时分配给 I/O 线程
```

监听 fd 继续留在主线程处理后续连接；新产生的客户端 fd 用于该连接的通信。不是把监听 fd 本身交给 I/O 线程，也不是 accept 回调直接读取一条完整命令。

参考：[8.10.3 server.c](https://github.com/redis/redis/blob/8.10.3/src/server.c)、[socket.c](https://github.com/redis/redis/blob/8.10.3/src/socket.c)。

## 9. Redis 8.10.3：主线程与 I/O 线程的分工

下表限定为：已经启用多线程 I/O，且普通客户端已经分配到 I/O 线程的典型路径。

| 阶段 | 负责线程 |
|---|---|
| 接受新连接、分配客户端 | 主线程 |
| 关注客户端 socket 的就绪事件 | 该客户端所在的 I/O 线程 |
| 读取请求、解析协议 | I/O 线程 |
| 执行常规数据命令、生成响应内容 | 主线程 |
| 将响应写入 socket | I/O 线程 |

**生成响应内容与通过网络发送响应是不同阶段。** I/O 线程接收了请求、识别出命令，也不代表它负责执行键空间操作。

每个工作 I/O 线程有自己的事件循环：`IOThreadMain()` 注册该线程的前后置回调，然后运行 `aeMain(t->el)`。因此，“所有 ae 事件都只有主线程处理”不适用于这里。

没有启用多线程 I/O 时，网络工作仍由主线程处理。特殊状态的客户端也可能需要留在主线程；不要把“除了执行命令都是 I/O 线程”作为无条件结论。

源码入口：[8.10.3 iothread.c](https://github.com/redis/redis/blob/8.10.3/src/iothread.c)、[networking.c](https://github.com/redis/redis/blob/8.10.3/src/networking.c)。

## 10. 请求怎样交给主线程：队列交付与 fd 通知

### 10.1 两种机制各司其职

| 机制 | 承担的职责 |
|---|---|
| 共享内存中的待处理队列 | 保存要由主线程处理的客户端对象引用 |
| 专门注册的通知 fd | 必要时让等待中的主线程返回，提示它处理队列 |

同一进程内的线程共享地址空间，解析好的命令和参数已经在客户端相关结构中。交接不需要通过通知 fd 再发送一遍命令正文。

可以把通知 fd 理解为门铃，队列保存的是要处理的工作。不能只说“通过 fd 交付请求”，应说：**通过队列交付任务，通过 fd 通知接收方。**

### 10.2 典型交接过程

1. I/O 线程解析出命令，标记客户端存在待执行命令。
2. 暂停该客户端的读写处理，将客户端加入本线程的待交接列表。
3. 提交时，在互斥锁保护下将列表合并到主线程的共享待处理队列。
4. 必要时通过 `triggerEventNotifier()` 触发通知。
5. 主线程的 epoll 返回通知 fd 的可读事件，ae 调用 `handleClientsFromIOThread()`。
6. 主线程处理通知，并通过 `processClientsFromIOThread()` 取出客户端、推进命令执行。
7. 处理后再交回 I/O 线程，由后者继续网络读写。

实际实现包含批量交接和通知合并，不是每条命令都单独写一次通知 fd。主线程运行时也会在 `beforeSleep()` 中检查待处理客户端，避免不必要的通知。

通知器内部如何使用具体系统设施，以及运行状态与入睡之间怎样避免漏唤醒，本轮没有完成逐行核对，留待回访。

### 10.3 为什么“加锁”还需要细分

共享队列的合并和取出需要互斥，但队列锁只保护队列结构，不会自动保护取出后对客户端对象的所有访问。

Redis 还通过客户端处理阶段的交接来约束双方访问。I/O 线程准备交出客户端时，会清除 `CLIENT_IO_READ_ENABLED` 和 `CLIENT_IO_WRITE_ENABLED`，暂停这个客户端的读写处理；其他客户端仍可继续处理。

主线程完成处理并交回后，I/O 线程再恢复该客户端的读写。共享队列锁并非一直持有到命令执行完毕。

因此要分别回答：

- 谁保护入队、出队和列表合并？共享队列的互斥锁。
- 谁防止双方同时处理同一个客户端的相关状态？交接协议、处理标志和相应同步机制。

以上是正常交接路径的解释，不意味着整个 Redis 实现都不需要其他锁或原子变量。

源码入口：[8.10.3 iothread.c](https://github.com/redis/redis/blob/8.10.3/src/iothread.c)，重点看 `enqueuePendingClientsToMainThread()`、`sendPendingClientsToMainThreadIfNeeded()`、`processClientsFromIOThread()` 和 `processClientsFromMainThread()`。

## 11. 本轮重点纠正速查

| 容易混淆的说法 | 更准确的理解 |
|---|---|
| Redis 是单线程程序 | 常规核心数据命令串行执行；进程还存在其他线程、任务和子进程 |
| I/O 多路复用监听多个端口 | 关注多个 fd 的就绪状态 |
| epoll 等 fd，read 等连接 | 一个等待一组 fd，一个操作特定 fd；连接也通过 fd 访问 |
| 可读就是收到完整命令 | 就绪、读取字节、协议解析完成是不同阶段 |
| 使用 epoll 就不需要非阻塞 | epoll 关注就绪，非阻塞控制实际操作暂时无法推进时的返回行为 |
| 非阻塞意味着线程不能休眠 | 可以在 epoll 中集中等待，在单连接读写时避免无期限等待 |
| 没有长度就无法识别边界 | 还可设计分隔符等协议，但要处理内容与分隔符冲突 |
| 时间到了就有线程执行 Redis 回调 | 正常路径中，由运行事件循环的线程主动检查到期并调用回调 |
| epoll 管理 Redis 的定时任务 | epoll 只接受本次等待超时；任务及回调由 ae 管理 |
| 每轮检查时间事件就是每轮执行全部任务 | 遍历检查全部候选，只执行已到期的事件 |
| 接受连接发生在 ae 循环之外 | 监听 socket 的可读事件由主线程 ae 循环处理 |
| Redis 8 所有 ae 回调都在主线程执行 | 工作 I/O 线程也有各自的事件循环 |
| I/O 线程通过通知 fd 传输完整命令 | 队列交付客户端引用，fd 用于通知 |
| 队列加锁就保护了客户端全部数据 | 出队后的对象访问还需要处理权交接等同步保证 |

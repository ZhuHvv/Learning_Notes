# 07. 淘天Agent工程师

### 一、RAG 系统模块

#### Q1：HyDE 查询扩展在做什么工作？

参考答案：

HyDE（Hypothetical Document Embeddings）的核心思想是解决用户查询和文档之间的语义鸿沟问题。

传统 RAG 的检索流程是把用户的短查询直接转成向量，然后去向量库里做相似度搜索。问题在于，用户问的是一句话，而文档库里存的是长段落，两者在长度、结构和表达方式上差异很大，导致"问题-to-文档"的匹配效果不理想。

HyDE 在中间加了一步：先让大模型根据用户查询生成一个"假设性回答文档"——这个文档不需要事实正确，但在结构和语义上更接近真实文档。然后用这个假设文档的向量去检索，变成"文档-to-文档"的匹配，命中率大幅提升。

整个流程是：用户查询 → LLM 生成假设文档 → 对假设文档做 Embedding → 用这个 Embedding 去向量库检索 → 拿到真实文档 → 送给 LLM 生成最终回答。

需要注意的是 ，HyDE 会引入额外的一次 LLM 调用延迟，且如果 LLM 对该领域完全没有知识，生成的假设文档质量会很差，反而影响检索效果。所以在实际使用中需要评估：如果领域非常垂直且 LLM 缺乏先验知识，HyDE 可能不如直接用 query rewriting 效果好。

回答策略 ：先讲 why（传统 RAG 的问题），再讲 what（HyDE 的做法），最后讲 trade-off（延迟和适用边界），展示出你对这个技术不是只知道概念，而是有落地判断。

#### Q2：稠密召回和稀疏召回的权重怎么配比的？

参考答案：

我们采用的是混合检索策略，稠密检索（向量检索）和稀疏检索（BM25）各有优势：稠密检索擅长语义匹配，能理解同义词和语义相近的表达；稀疏检索擅长关键词精确匹配，在专有名词、型号等精确查询上更可靠。

权重配比方面，我们的做法是：

1. 初始比例 ：一般从稠密 0.7 + 稀疏 0.3 起步，因为大部分场景下语义检索更重要。

2. 基于验证集调优 ：我们构建了一个标注过的检索评测集（包含 query 和对应的 ground truth 文档），在这个集合上用 grid search 遍历不同权重组合（步长 0.1），找到 Recall@K 最优的配比。

3. 场景差异 ：对于术语密集的技术文档场景，稀疏检索的权重会调高到 0.4~0.5；对于自然语言问答场景，稠密检索的权重可以拉到 0.8。

最终我们用 RRF（Reciprocal Rank Fusion）做融合排序，RRF 本身是一个不需要调权重的融合算法——它只看排名位次，不看分数，这样就避免了两路召回分数量纲不同的问题。

回答策略 ：给具体数字，说清楚你是怎么决定这个数字的（方法论），而不是拍脑袋。提到 RRF 可以自然衔接下一个问题。

### 二、多智能体架构模块

#### Q3：你的 DeepResearch 是主从架构吗？

参考答案：

是的，整体是一个 Orchestrator-Worker 的主从架构。主 Agent（Orchestrator）负责三件事：

1. 任务分解 ：接收到用户的研究请求后，将复杂问题拆解为多个子研究任务。

2. 任务分发 ：根据子任务的类型，调度不同的 Worker Agent 去执行——比如搜索 Agent 负责检索信息，分析 Agent 负责提取关键观点，写作 Agent 负责生成最终报告。

3. 结果汇总 ：收集各 Worker 的返回结果，做去重、冲突消解和综合摘要，最终输出给用户。

Orchestrator 本身也是一个 LLM 驱动的 Agent，它通过 prompt 中定义的角色描述和工具列表来决定调用哪个子 Agent。子 Agent 对 Orchestrator 来说就是一个"工具"，调用方式和调用普通函数工具没有本质区别。

回答策略 ：用 1-2-3 的结构说清楚主 Agent 的职责，然后点出关键设计决策——子 Agent 作为工具暴露给主 Agent。

#### Q4：各 Agent 之间的记忆是隔离的吗？有独立记忆吗？

参考答案：

记忆分两层来看：

工作记忆（短期）是隔离的。 每个 Worker Agent 都有自己独立的对话上下文，它只能看到 Orchestrator 分配给它的子任务描述和自己执行过程中的中间结果。Agent A 看不到 Agent B 的工作过程，这样做是为了避免上下文污染——如果所有 Agent 共享同一个上下文，token 消耗会爆炸，而且不同任务的信息互相干扰会降低每个 Agent 的执行质量。

共享记忆（长期）是连通的。 我们有一个全局的共享状态对象（State），Orchestrator 和各 Worker 都可以读写。Worker 完成任务后，会把关键结果写入这个共享状态。Orchestrator 从共享状态中读取各个 Worker 的产出来做汇总。但 Worker 之间一般不直接读取彼此的状态，而是通过 Orchestrator 中转。

这种设计既保证了各 Agent 执行时的上下文纯净度，又能在需要时共享关键信息。

回答策略 ：分"工作记忆"和"共享记忆"两层回答，然后解释为什么这样设计，展示你对系统设计权衡的理解。

#### Q5：递归调用时上下文会不会超出模型窗口？你怎么处理的？

参考答案：

这是一个非常实际的问题，确实会超出。在 DeepResearch 的场景下，每一轮 research 循环都会产生新的搜索结果和分析内容，如果不加处理，prompt 会线性增长，很快就会撞到 context window 的上限。

我们的处理策略是多层的：

第一层：增量摘要压缩。 每完成一轮研究循环，不是把原始搜索结果全量保留，而是让 LLM 做一次摘要，把这一轮的关键发现压缩成几百 token 的摘要。下一轮循环只携带摘要而非原始内容。

第二层：滑动窗口 + 重要性标记。 对于对话历史，我们维护一个滑动窗口，只保留最近 N 轮的完整交互。更早的交互会被压缩或丢弃。但对于被标记为"关键发现"的内容，即使超出窗口也会保留。

第三层：递归深度限制。 设置了最大递归深度（比如 5 层），避免无限循环。每一层递归时，Orchestrator 会评估"是否已经收集到足够信息来回答原始问题"，如果是，则提前终止。

第四层：上下文预算监控。 在每次调用 LLM 前，先估算当前 prompt 的 token 数。如果接近窗口上限（比如达到 80%），触发一次强制压缩——对整个上下文做一次全局摘要，释放 token 空间。

回答策略 ：这是本场面试最关键的工程问题。分层回答（压缩、窗口、限制、监控）展示系统性思维，每一层都是一道防线。

#### Q6：记忆处理时怎么保证不丢失细节？

参考答案：

坦白说，做摘要压缩一定会丢失细节，关键是控制丢什么、保留什么。我们的做法是：

1. 结构化提取 ：压缩时不是简单的"请总结以下内容"，而是要求 LLM 按预定义的 schema 提取信息——比如"关键事实"、"数据点"、"来源引用"、"待确认问题"。这样即使内容被压缩了，关键的结构化信息不会丢。

2. 分级存储 ：原始搜索结果存一份完整的到外部存储（比如文件或数据库），上下文里只放摘要。如果后续某个 Agent 需要深入某个细节，可以回查原始数据。

3. 关键信息锚定 ：对于用户明确提到的关键词、数据和实体，在压缩时强制保留，不允许被摘要掉。

本质上是在"上下文长度"和"信息完整性"之间做 trade-off，我们选择牺牲叙述的连贯性来保留事实的准确性。

回答策略 ：先承认问题的客观存在（摘要一定丢细节），再给出你的缓解策略，展示工程上的务实态度。

#### Q7：记忆有借助外存吗？

参考答案：

有的。我们用了两种外部存储：

1. 向量数据库 （比如 FAISS 或 Milvus）：存储研究过程中积累的知识片段。每条知识会带上元数据（来源、时间戳、置信度）。当新一轮研究需要回溯已有发现时，Agent 可以通过语义检索快速找到相关的历史知识，而不需要全部塞进上下文。

2. 结构化存储 （如 JSON 文件或 SQLite）：存储任务状态、已完成的子任务列表、研究大纲等结构化信息。这部分数据量小但访问频繁，用 KV 形式存取比放在 prompt 里更高效。

这样做的好处是把 LLM 的上下文窗口当作"工作台"，只放当前任务需要的信息；而外部存储是"档案柜"，需要时再取。这和人类的工作方式很类似——你不会把所有资料都铺在桌上，而是需要什么去柜子里拿什么。

回答策略 ：给出具体的存储方案选型，最后用一个类比收尾让面试官印象深刻。

### 三、框架与前沿概念模块

#### Q8：怎么用 LangGraph 实现 ReAct？

参考答案：

LangGraph 的核心是一个有状态的图编程模型，用它实现 ReAct 的思路是：

1. 定义 State ：创建一个 TypedDict，包含 messages （对话历史）和其他需要跨节点传递的状态字段。

2. 定义节点 ：

◦

agent 节点：调用 LLM，让它决定下一步是调用工具还是直接回答。LLM 绑定了可用的工具列表（通过 bind\_tools ）。

◦

tools 节点：执行 LLM 选择的工具，返回工具结果。

3. 定义边 ：

◦

从 agent 节点出发，设置一个条件边：如果 LLM 的输出包含 tool\_call，就路由到 tools 节点；否则路由到 END。

◦

从 tools 节点回到 agent 节点，形成循环。

这样就构成了 ReAct 的"思考 → 行动 → 观察"循环：LLM 思考后决定用工具（行动），工具返回结果（观察），结果回到 LLM 继续思考，直到 LLM 决定不再调用工具而是直接给出最终答案。

相比纯 LangChain 的 AgentExecutor，LangGraph 的优势在于：图的结构是显式的、可调试的，你能清楚看到每个节点的输入输出；而且可以很方便地加入人机交互节点、并行分支等复杂控制流。

回答策略 ：用具体的实现步骤来回答，而非泛泛而谈概念。提到和 AgentExecutor 的对比说明你理解演进脉络。

#### Q9：Context Engineering 和 Harness Engineering 了解吗？

参考答案：

这两个是最近 Agent 工程领域的热门概念，它们描述的是"除了模型本身之外，你围绕模型构建的一切"。

Context Engineering 关注的是单次 LLM 调用层面——你给模型看什么、按什么顺序组织、怎么在有限的 context window 里放进最有价值的信息。它包括 prompt 的结构设计、检索增强、上下文压缩、关键信息的优先级排列等。可以理解为"精心策划每次 LLM 调用的输入"。

Harness Engineering 是更上一层的概念。Agent = Model + Harness，Harness 是模型之外的所有工程基础设施——工具调度、状态管理、记忆持久化、错误恢复、权限控制、多步骤编排等。一个好的类比是：模型是引擎，Context Engineering 是燃油和仪表盘的优化，Harness 是整辆车——方向盘、刹车、车道边界、保养计划全都算。

Mitchell Hashimoto 在 2026 年初正式提出了 Harness Engineering 这个术语，核心理念是：每当 Agent 犯了一个错误，不要指望模型下次自己变好，而是要在工程系统层面修复这个问题，让同类错误不可能再发生。这是一种把"模型可靠性"从"希望模型更强"转变为"让系统设计来保障"的思路。

回答策略 ：说清楚两者的层级关系（Context Engineering ⊂ Harness Engineering），用类比帮面试官快速理解，然后提到具体人物和时间节点展示你在跟踪前沿。

#### Q10：OpenClaw 相比 Manus 有什么改进？

参考答案：

OpenClaw 和 Manus 代表了两种截然不同的 Agent 架构哲学：

OpenClaw（开源、本地优先）的核心特点：

1. 本地执行 ：Agent 运行在你自己的机器上，数据不离开本地环境（除了 LLM API 调用），数据主权完全可控。

2. Skill 系统 ：它有一套 SKILL.md 范式，每个 Skill 是一个可复用的能力单元，通过 ClawHub 共享。Agent 可以动态发现和加载 Skill，这使得能力扩展非常灵活。

3. 持久化 Agent ：通过 HEARTBEAT.md 实现定时任务调度，Agent 可以 7×24 自主运行，主动推送消息到 Slack、Telegram 等平台，不需要用户主动发起交互。

4. 完全可审计 ：MIT 开源协议，所有代码、所有 API 调用都可以审查。

相比 Manus 的优势：

Manus 更像一个"托管服务"——你描述目标，它在云端沙箱里完成，体验流畅但黑盒。OpenClaw 更像"给你一个工程师"——你完全控制它怎么工作，可以深度定制，但需要技术能力来维护。

核心区别在于：Manus 优化的是"用起来简单"，OpenClaw 优化的是"构建起来灵活"。对于需要深度集成到已有工作流、需要数据隐私保障、或需要高度定制的团队，OpenClaw 更合适。

回答策略 ：不要简单说"哪个更好"，而是对比两者的设计哲学差异。面试官问这个问题是想看你是否真正理解了这些框架，而不是只看过一篇推文。

#### Q11：Skill 编写有什么注意范式或格式约束？

参考答案：

OpenClaw 的 Skill 采用 SKILL.md 的格式规范，主要约束包括：

1. YAML Frontmatter ：每个 Skill 文件顶部需要有 YAML 元数据，包括 name （技能名称）、 description （触发描述——Agent 根据这个描述决定什么时候调用这个 Skill）等字段。

2. 自然语言指令 ：Skill 的主体内容是自然语言的操作指南，告诉 Agent 在调用这个 Skill 时应该如何操作。这不是传统意义上的代码，而更像是写给 Agent 的 SOP。

3. Description 的质量至关重要 ：因为 Agent 是根据 description 来判断何时触发这个 Skill 的，所以描述必须清晰准确地说明适用场景和不适用场景。写得太泛会导致误触发，写得太窄会导致该用的时候没被调用。

4. 模块化设计 ：一个 Skill 应该聚焦于一个具体能力，不要把太多功能塞到一个 Skill 里。好的实践是"一个 Skill 解决一类问题"。

5. 三级层次 ：Skill 支持 built-in（内置）、project-level（项目级）、user-level（用户级）三个层级，优先级从低到高。

回答策略 ：如果你真的写过 Skill，给出具体例子会非常加分。如果没写过，至少要能描述出文件结构和关键设计原则。

#### Q12：MCP（Model Context Protocol）了解吗？

参考答案：

MCP 是 Anthropic 推出的一个开放协议，目标是标准化 LLM 与外部工具/数据源的连接方式。

用一个类比来说：MCP 之于 AI Agent 就像 USB 之于电脑外设。在 MCP 之前，每个 Agent 框架都有自己的工具集成方式，开发者需要为每个框架单独写适配代码。MCP 定义了一套标准的通信协议，让工具提供方只需要实现一次 MCP Server，就能被所有支持 MCP 的 Agent 框架调用。

MCP 的核心架构是 Client-Server 模式：Agent 是 MCP Client，工具/数据源是 MCP Server。Server 暴露出可用的工具列表和调用接口，Client 通过标准协议发现和调用这些工具。

在实际使用中，比如你想让 Agent 访问 Google Calendar，只需要接入一个 Google Calendar 的 MCP Server，而不需要在 Agent 代码里硬编码 Google API 的调用逻辑。这大大降低了工具集成的开发成本，也使得工具生态可以跨 Agent 框架共享。

回答策略 ：用 USB 类比快速建立直觉，然后说清楚 Client-Server 架构。如果面试官的团队在做 ML 自动化平台，MCP 很可能是他们关注的集成方案。

### 四、AI 编程实践模块

#### Q13：用 AI 编程出了问题，你怎么排查和定位？

参考答案：

我的排查流程大致分三步：

第一步：隔离问题范围。 先确定是 AI 生成的代码有 bug，还是我给的需求描述不清晰导致 AI 理解错了。方法很简单——重新读一遍自己的 prompt 和 AI 的输出，看 AI 的理解是否和我的意图一致。如果意图理解对了但实现有 bug，那是代码层面的问题；如果意图本身就理解错了，那要回去改 prompt。

第二步：传统调试手段。 AI 生成的代码和人写的代码没有本质区别，该加 print/log 加 print/log，该断点调试就断点调试。我不会把报错信息直接甩给 AI 让它"修复"，而是先自己理解错误原因，再决定是自己改还是让 AI 改。

第三步：增量验证。 对于复杂功能，我会让 AI 分步生成，每一步都跑通了再往下走，而不是一口气让它生成几百行代码然后一起调试。这样出了问题能快速定位到是哪一步出的。

核心原则是： AI 是工具，人是决策者。 我需要理解 AI 生成的每一行代码在做什么，而不是把它当黑盒。如果我不理解某段代码，我会先让 AI 解释清楚，确认合理后再继续。

回答策略 ：展示你是"驾驭 AI"而非"被 AI 带着走"。强调你有独立的技术判断力。

#### Q14：如果 AI 解答的方向偏了呢？

参考答案：

方向偏了比代码 bug 更危险，因为它可能意味着你在错误的方向上走了很远才发现。我的应对策略是：

事前预防：

- 在给 AI 任务之前，我会先自己想清楚大致的技术方案方向，至少有一个粗略的判断。这样 AI 给出的方案如果和我的预期差距很大，我能立刻警觉。

- 复杂任务先让 AI 出方案而非直接出代码——"你打算怎么实现这个功能？先给我思路，不要写代码。"确认方向对了再让它动手。

事中纠偏：

- 如果发现方向偏了，不要在原来的对话上下文里继续纠正。因为此时上下文已经被错误方向的信息污染了，AI 会受到锚定效应的影响。更好的做法是开一个新的对话，重新描述需求，但这次在 prompt 里明确排除掉错误方向——比如"不要用 XX 方案，因为 YY 原因"。

- 提供更多约束和参考：给 AI 看相关的文档、代码片段、或技术文章，缩小它的搜索空间。

事后复盘：

- 把这次"方向偏了"的经验沉淀到项目的规范文档里（比如 Claude Code 的 CLAUDE.md 或类似的上下文文件），这样后续的 AI 对话都能带上这些经验教训，避免同样的错误。

回答策略 ：这道题和 Harness Engineering 的理念一脉相承——把 AI 的失败转化为系统性的改进。面试官反复问 Vibe Coding，你要展示的是你有成熟的方法论，而不只是"让 AI 写完了 copy 过来"。

#### Q15：项目编排的创建逻辑是规则式的吗？

参考答案：

在我的 DeepResearch 项目中，编排逻辑是 规则式和 LLM 决策混合 的：

规则式的部分：

- 整体流程的阶段划分是固定的（任务分析 → 子任务分解 → 并行研究 → 结果汇总 → 报告生成），这个大框架不会变。

- 子 Agent 的类型和职责是预定义的，不会在运行时动态创建新类型的 Agent。

- 异常处理和重试逻辑是硬编码的规则。

LLM 决策的部分：

- Orchestrator 决定"这个研究问题应该拆成哪些子问题"是 LLM 动态决定的。

- 每一轮研究循环后，是否需要继续深入、还是已经收集到足够信息，这个判断由 LLM 做出。

- 多路召回结果的优先级排序和冲突消解也是 LLM 来完成的。

这种混合式设计是有意为之的——框架用规则保障可靠性和可预测性，在需要智能判断的环节才引入 LLM 决策。纯规则太死板，纯 LLM 决策太不可控，混合是目前最务实的方案。

回答策略 ：面试官问这个问题是想了解你在"可控"和"智能"之间怎么取舍。把两种方式混合使用并说清楚边界，比简单回答"是"或"不是"要好得多。

### 总结：回答面试问题的通用策略

1. 先讲 Why，再讲 What，最后讲 Trade-off ：不要上来就背概念，先说"为什么需要这个技术/这样设计"，再说"具体怎么做"，最后说"有什么局限性或替代方案"。

2. 给具体数字和方案 ：面试官问权重配比，你就说"0.7:0.3 起步，通过 grid search 调优"；问递归深度，你就说"最大 5 层"。具体的数字比泛泛的描述更有说服力。

3. 展示系统性思维 ：每个问题尽量从多个层面回答（比如上下文管理的四层防线），而不是只给一个点。

4. 承认局限性 ：不要假装所有问题都完美解决了。"坦白说摘要压缩一定会丢细节"这种诚实反而加分。

5. 连接前沿概念 ：回答工程问题时自然地带出前沿概念（比如从"排查 AI 编程问题"引申到 Harness Engineering），展示你的知识是成体系的。

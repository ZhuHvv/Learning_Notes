# 稠密向量、稀疏向量与多向量表示及检索

> 所属分类：LLM / Transformer  
> 修订版本：v11  
> 核心问题：文本可以怎样表示成可检索的数值结构，不同表示为何对应不同检索能力？

## 1. 总体性概念

在检索系统中，“向量表示”不是只有一种。常见方案可分为三类：

| 表示方式 | 一个对象如何表示 | 主要捕获的信息 | 典型检索方式 |
|---|---|---|---|
| 稠密向量 Dense Vector | 固定维度、绝大多数维度非零的浮点向量 | 语义相似、上下文含义 | 向量近邻检索 ANN |
| 稀疏向量 Sparse Vector | 维度很高、只有少数维度非零 | 关键词、术语、精确词项匹配 | 倒排索引、BM25、稀疏向量检索 |
| 多向量 Multi-Vector | 一个文档或查询由多个向量共同表示 | 局部语义、token/片段级匹配 | Late Interaction、MaxSim、多字段召回 |

三者并不是“先进方案取代落后方案”。它们针对的信号不同：稠密表示擅长“意思相近但用词不同”，稀疏表示擅长“术语必须精确命中”，多向量表示擅长“长文本里只有局部与问题高度相关”。

## 2. 原理性解释

### 2.1 稠密向量：把整体语义压缩到固定维度空间

Embedding 模型接收一句话或一个 chunk，输出一个固定维度向量：

```text
"Kafka 中 ISR 的作用是什么？"
             ↓ Embedding Encoder
[0.021, -0.338, 0.517, ..., 0.084]   # 例如 768/1024/1536 维
```

模型训练会让语义相近的文本在向量空间中距离更近。检索时通常计算余弦相似度、点积或欧氏距离：

```text
cos(q, d) = (q · d) / (||q|| ||d||)
```

它的关键优势是能够跨越表面词汇差异。例如查询使用“消息积压”，文档使用“consumer lag”，两者没有完全相同的中文词，但语义模型可能仍能把它们拉近。

局限也来自“压缩”：一个长文档被压成单个向量后，细粒度术语、数字、版本号、类名可能被弱化。查询“FULLRESYNC”和查询“Redis 全量同步”对人而言相关，但如果模型没学好该术语，召回可能不稳定。

#### 2.1.1 Embedding 模型的两条架构路线

经典路线是双向 encoder（BERT 衍生的 BGE/GTE 类小模型）：每个 token 都能双向看到整段文本，得到的整体表示天然适合“理解这段文本是什么”，而不是预测下一个 token。这类模型参数量小、推理成本低，生产中仍被广泛使用。但“RAG Embedding = Encoder-only 模型”的说法已经过时：2024 年后 MTEB 榜单头部的 embedding 模型（Gemini Embedding、Qwen3-Embedding、NV-Embed、E5-Mistral 等）多以 decoder-only LLM 为底座，通过取末位 token 的 hidden state 或 latent pooling 得到句向量，效果上限更高，代价是参数量与推理成本也更高。两条路线按成本/效果取舍：海量文档、低延迟、低成本建库偏向双向 encoder 小模型；追求检索质量上限时考虑 LLM 底座的 embedding 模型。无论哪条路线，目标一致：不是生成下一个 token，而是把语义压缩成可比较的向量，让语义相近的文本在向量空间中距离更近。

#### 2.1.2 工程提示：chunk 切分粒度与 metadata

稠密召回质量不只取决于 embedding 模型本身，chunk 切分粒度影响显著：chunk 太大，单个向量混入过多噪声、语义被稀释；chunk 太小，语义不完整、上下文丢失。此外应为每个 chunk 保留 metadata（如 source、page、section），用于检索时过滤和生成时引用溯源：

```python
for chunk in split(doc):
    vector_db.insert(embed(chunk.text), metadata={"source": chunk.source})
hits = vector_db.search(embed(query), top_k=5)
```

### 2.2 稀疏向量：用词项维度保留精确匹配信号

稀疏表示的维度通常对应词表中的词项。假设词表为：

```text
[Kafka, ISR, Redis, offset, leader, consumer, ...]
```

文档可以表示为：

```text
Kafka ISR leader 选举
→ [Kafka: 1.8, ISR: 2.4, leader: 1.2, 其它维度: 0]
```

绝大多数维度为 0，因此称为稀疏向量。传统 BM25 直接根据词频、逆文档频率和文档长度计算相关性；SPLADE 等神经稀疏模型则由模型学习词项权重，还可能扩展出原文没有但语义相关的词项。

稀疏检索的本质是：**保留可解释的词项匹配，并通过倒排索引快速找到包含这些词项的文档。**它特别适合：

- 类名、函数名、错误码、协议字段；
- 人名、产品名、版本号；
- 用户明确要求包含某个关键词的检索；
- 语义模型不熟悉的行业术语。

### 2.3 多向量表示：不把所有局部信息强行压成一个向量

多向量表示允许一个文档保存多个向量。例如：

```text
文档 D
├─ token 向量 d1
├─ token 向量 d2
├─ token 向量 d3
└─ ...
```

ColBERT 一类 Late Interaction 方法会分别编码查询 token 和文档 token，然后对每个查询向量寻找文档中最相似的局部向量：

```text
score(q, d) = Σ_i max_j sim(q_i, d_j)
```

含义是：查询中的每个重要部分，都可以在文档中寻找自己的最佳匹配位置，而不是要求整个文档只用一个全局向量表达。

另一类工程化多向量方案是：一个文档按标题、摘要、正文 chunk、表格描述分别建立多个向量；召回任一子向量后，再映射回同一个父文档。它能提升长文档召回，但会增加索引空间、检索计算和去重成本。

### 2.4 三种检索不是同一个维度上的简单强弱关系

可以把它们理解为三种不同的证据通道：

```text
Dense：这两段话“意思像不像”
Sparse：这两段话“关键字是否准确对应”
Multi-vector：查询中的每个局部点“能否在文档局部找到匹配”
```

真实 RAG 常采用混合召回：稠密检索负责语义召回，BM25/稀疏检索兜住术语和标识符，多向量检索用于复杂长文本，再通过 RRF 或 reranker 融合。

## 3. 机制流程

### 3.1 建库流程

```text
原始文档
  ↓ 清洗、切分、保留 metadata
  ├─ Dense Encoder → dense vector → ANN 索引
  ├─ 分词/稀疏模型 → term weights → 倒排索引
  └─ Token/字段/子块编码 → multiple vectors → 多向量索引
```

### 3.2 查询流程

```python
def hybrid_retrieve(query: str):
    dense_hits = dense_index.search(dense_encoder(query), top_k=50)
    sparse_hits = sparse_index.search(query, top_k=50)
    multi_hits = multi_vector_index.search(query, top_k=50)

    candidates = rrf_merge([dense_hits, sparse_hits, multi_hits])
    candidates = deduplicate_by_parent_doc(candidates)
    return cross_encoder_rerank(query, candidates)[:8]
```

### 3.3 结果融合要解决的两个问题

第一，不同检索器的原始分数不可直接比较。BM25 可能返回 12.6，余弦相似度可能是 0.83，这并不意味着 12.6 更相关。RRF 使用排名而不是绝对分数，可以绕开尺度差异。

第二，多向量检索可能从同一父文档命中很多子向量。必须先做父文档聚合或去重，否则一个文档会占满 topK。

## 4. 类比理解

- 稠密检索像根据“文章主旨”找相似内容。
- 稀疏检索像在书的关键词索引中查精确术语。
- 多向量检索像让查询里的每个问题点分别去长文档中寻找对应段落。

## 5. 应用举例 / 代码或伪代码

### 5.1 简化的稠密检索

```python
import numpy as np


def cosine(a: np.ndarray, b: np.ndarray) -> float:
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))


def dense_search(query, docs, encoder, top_k=3):
    q = encoder(query)
    scored = [(doc_id, cosine(q, vec)) for doc_id, vec in docs.items()]
    return sorted(scored, key=lambda x: x[1], reverse=True)[:top_k]
```

### 5.2 简化的 late interaction

```python
def maxsim_score(query_vectors, doc_vectors):
    total = 0.0
    for qv in query_vectors:
        # 查询中的每个 token，在文档所有 token 中找最佳匹配
        total += max(cosine(qv, dv) for dv in doc_vectors)
    return total
```

### 5.3 选型案例

假设知识库同时包含技术文档和业务制度：

- “如何处理消费者积压？”：语义表达很多，Dense 很重要；
- “`KAFKA_PROCESS_ROLES` 是什么？”：配置字段必须精确命中，Sparse 很重要；
- “报告中分别提到了收入、留存和转化，哪一段解释转化下降？”：长文档局部匹配，多向量更有价值。

## 6. 你在讨论中的理解推进

- 起点：你先把 Embedding 理解为“把文本转成一个向量”。
- 推进：你进一步区分了稠密向量、稀疏向量和多向量表示，意识到它们保留的信息粒度不同。
- 关键修正：稀疏向量不等于“维度少”，而是维度可能非常高、但非零元素少；多向量也不是“向量维度更大”，而是一个对象拥有多个向量。
- 最终连接：表示方式决定索引结构和检索算法；RAG 的召回质量来自多种互补信号，而不是只依赖一种 Embedding。

## 7. 常见误区与排查思路

- **误区：向量检索一定优于关键词检索。** 技术术语、编号、专有名词往往仍需要稀疏检索。
- **误区：多向量只是把多个向量平均。** 平均后又退化为单向量；多向量价值在于保留局部交互。
- **误区：混合检索就是把分数相加。** 不同分数尺度必须归一化或使用 RRF。
- **排查：** 分别记录 dense/sparse/multi-vector 的命中来源、父文档去重结果和 rerank 前后排名。

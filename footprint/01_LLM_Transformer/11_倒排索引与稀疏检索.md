# 01.11 倒排索引与稀疏检索

## 1. 总体性概念

倒排索引（Inverted Index）是一种从“词项”反向映射到“包含该词项的文档”的索引结构。

普通文档视角是：

```
Doc1 → [Kafka, ISR, leader]
Doc2 → [Redis, replication]
```

倒排索引把方向反过来：

```
Kafka → [Doc1]
ISR   → [Doc1]
Redis → [Doc2]
```

因此查询 `Kafka ISR` 时，不需要扫描所有文档，只需读取 `Kafka` 和 `ISR` 的 postings list（倒排列表），再做交集、并集或相关性打分。

## 2. 原理性解释

### 2.1 倒排索引的三个核心组成

1. **词典 Term Dictionary**：记录系统中有哪些词项，并定位其倒排列表。
2. **倒排列表 Postings List**：记录包含该词项的文档 ID。
3. **附加统计信息**：词频、词位置、字段、文档长度等，用于排序和短语查询。

一个更完整的倒排项可能是：

```
"kafka" → [
  (doc=3, tf=4, positions=[5, 18, 32, 50]),
  (doc=9, tf=1, positions=[7])
]
```

其中：

- `doc`：文档编号；
- `tf`：该词在文档中出现次数；
- `positions`：出现位置，可用于短语查询和高亮。

### 2.2 为什么叫“倒排”

正排结构是“文档 → 词项”，适合读取一篇文档包含什么；倒排结构是“词项 → 文档”，适合回答哪些文档包含这个词。

```
正排：给定 doc，找 terms
倒排：给定 term，找 docs
```

数据库 B+ 树索引和倒排索引解决的问题不同。B+ 树通常按某个字段值排序，适合范围查找；倒排索引面向文本中大量词项，适合全文搜索和相关性排序。

### 2.3 查询如何通过倒排列表执行

查询：

```
Kafka AND ISR
```

分别得到：

```
Kafka → [1, 3, 8, 10]
ISR   → [3, 8, 11]
```

两个有序列表做线性归并交集：

```
结果 → [3, 8]
```

如果是 OR 查询，则求并集；如果是短语查询，还需要检查 positions 是否相邻。

### 2.4 BM25 为什么建立在倒排索引之上

倒排索引负责高效提供候选文档和词频统计，BM25 负责根据以下因素打分：

- 查询词在文档中出现得越多，通常越相关，但收益递减；
- 一个词在整个语料中越少见，区分能力越强；
- 文档过长时需要长度归一化，避免长文档因词多而天然得高分。

简化表达：

```
BM25(q, d) = Σ IDF(term) × TF_saturation(term, d) × length_norm(d)
```

因此倒排索引是“候选定位和统计基础”，BM25 是“相关性评分函数”。

### 2.5 构建索引时发生了什么

```
文档输入
  ↓ 分词 Tokenization
  ↓ 规范化：大小写、词形、停用词等
  ↓ 为词项分配 term id
  ↓ 追加 doc id、词频、位置到 postings
  ↓ postings 排序、压缩、持久化
```

大型搜索系统还会使用分段索引、跳表、块级压缩和缓存，减少磁盘 I/O 与 postings 解码成本。


### 2.6 大规模索引为什么需要分段、压缩与跳跃

实际语料中，一个高频词可能对应数百万个 doc id。倒排列表如果按普通整数直接存储，会占用大量空间。由于 doc id 通常递增，可以存相邻 doc id 的差值（delta encoding），再使用变长整数或块压缩；小差值通常只需少量字节。

索引更新也不会每写入一篇文档就重写整个大文件。搜索引擎通常先生成不可变的小 segment，查询同时访问多个 segment，后台再逐步 merge。删除操作可先记录删除标记，在合并时真正清理。

对超长 postings list，跳表或块级最大分数可以帮助查询跳过不可能进入 topK 的区段：

```yaml
postings: 1, 3, 8, 20, 21, 35, 80, ...
            └──── skip pointer ────→ 35
```

这些优化不改变倒排索引“term → docs”的逻辑，却决定了它能否支撑大规模低延迟检索。

## 3. 机制流程

### 3.1 最小构建流程

```python
from collections import defaultdict


def build_inverted_index(documents):
    index = defaultdict(dict)
    for doc_id, text in documents.items():
        positions = defaultdict(list)
        for pos, term in enumerate(tokenize(text)):
            positions[term].append(pos)
        for term, pos_list in positions.items():
            index[term][doc_id] = {
                "tf": len(pos_list),
                "positions": pos_list,
            }
    return index
```

### 3.2 AND 查询

```python
def intersect_sorted(a, b):
    i = j = 0
    result = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            result.append(a[i])
            i += 1
            j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return result
```

### 3.3 RAG 中的稀疏检索流程

```
用户查询
  ↓ 分词/关键词权重
  ↓ 查询倒排索引
  ↓ BM25 或稀疏点积打分
  ↓ 返回 topK chunk
  ↓ 与 dense hits 融合
  ↓ rerank
```

## 4. 类比理解

倒排索引类似书末的关键词索引：你先查“ISR”对应哪些页码，再直接翻到相关页，而不是从第一页开始逐行寻找。

正排索引像“查看第 100 页有哪些词”；倒排索引像“查看某个词出现在哪些页”。

## 5. 应用举例 / 代码或伪代码

### 5.1 为什么精确字段适合倒排索引

用户查询：

```
protoc-gen-go source_relative
```

这些是高区分度的技术词项。稠密模型可能把它们泛化成“Go 代码生成”，而 BM25 能直接奖励同时包含两个精确词项的文档。

### 5.2 混合检索示例

```python
def retrieve(query):
    lexical = bm25.search(query, top_k=50)
    semantic = vector_db.search(embed(query), top_k=50)
    fused = rrf_merge([lexical, semantic])
    return reranker.rank(query, fused)[:10]
```

### 5.3 字段级倒排

业务文档可以为 `title`、`body`、`tags` 建立不同字段索引，并赋予不同权重：

```
score = 3.0 × title_match + 1.0 × body_match + 2.0 × tag_match
```

这比把所有文字拼成一段更可控。


### 5.4 短语查询与位置索引

查询 `consumer group` 不一定等于同时包含 `consumer` 和 `group`。如果要求两个词相邻且顺序一致，需要读取 positions：

```python
def phrase_match(pos_a, pos_b, distance=1):
    b_set = set(pos_b)
    return any((p + distance) in b_set for p in pos_a)
```

位置索引会增加存储量，却支持短语搜索、邻近度打分和命中高亮。工程上可只为需要精确短语能力的字段保存 positions。

## 6. 你在讨论中的理解推进

- 起点：你问“倒排索引是什么”，最初容易从数据库普通索引角度理解。
- 推进：你明确了它不是“把数组倒着存”，而是把映射方向从“文档到词”翻转为“词到文档”。
- 关键修正：在混合检索中，BM25 是稀疏召回通道，不是 Reranker；倒排索引负责定位包含词项的候选，BM25 负责对候选打分。
- 进一步连接：稀疏向量的非零维度对应词项，倒排索引只需存储非零词项及其文档列表，因此两者天然匹配。
- 最终理解：BM25、全文检索和 RAG 的 sparse retrieval 都依赖同一类核心结构，但评分模型和词项权重可以不同；Contextual BM25 也不改变这一分工，只是把“上下文说明 + 原始 Chunk”作为被索引文本。

## 7. 常见误区与排查思路

- **误区：倒排索引等同于 BM25。** 倒排索引是数据结构，BM25 是打分方法。
- **误区：倒排索引只能做是否包含。** postings 可以保存词频、位置、字段，从而支持相关性、短语和高亮。
- **误区：用了向量库就不需要倒排索引。** 精确术语、标识符、过滤条件仍常由稀疏检索兜底。
- **排查：** 检查分词是否一致、大小写是否归一、专有词是否被错误切分、字段权重是否合理。

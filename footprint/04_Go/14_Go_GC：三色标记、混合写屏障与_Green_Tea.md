# 04.14 Go GC：三色标记、混合写屏障与 Green Tea

> 所属主线：Go Runtime 与内存  
> 难度：深入  
> 前置知识：逃逸分析、堆与 span 分配  
> 后续知识：GC 调优、内存限制与性能分析

## 1. 三色标记表示什么

Go 使用并发标记清扫 GC，三色是解释标记正确性的抽象；并不意味着每个对象头中永久存着三种颜色。下面的实现说明以 **Go 1.26.0** 为参考。

| 颜色 | 含义 |
|---|---|
| 白色 | 本轮尚未被标记，是否可达还不能据此判断 |
| 灰色 | 已标记，但其引用尚未扫描完成 |
| 黑色 | 已标记，且已完成其引用的扫描 |

从栈、全局变量等根开始，发现对象后将其标灰；扫描灰色对象时继续发现其指向的白色对象，再把已完成扫描的对象标黑。**标记过程中白色不等于垃圾；正确完成标记后，仍未标记的普通对象才可在清扫时回收。** 终结器等特殊生命周期机制另有处理。

“尚未扫描”不能直接等同于白色，因为灰色对象也可能尚未扫描。已经标记后才变得不可达的对象，可能形成浮动垃圾，留到后续 GC 回收。[GC 总体流程](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgc.go)

## 2. 为什么并发标记需要写屏障

GC 扫描时，业务 goroutine 仍会改变引用关系。以下是没有屏障时的一种漏标过程，假设 C 没有其他可被 GC 发现的路径：

```text
初始：Root → A（黑）       Root → B（灰） → C（白）

业务在 GC 扫描 B 前执行：
    A.next = B.next       // 给已经扫描过的 A 增加指向 C 的引用
    B.next = nil          // 删除尚待扫描的 B 指向 C 的引用

结果：Root → A（黑） → C（白）       Root → B（灰）
```

GC 后续扫描 B 找不到 C，又不会按普通扫描流程重新扫描 A，C 就可能一直保持白色而被误回收。

**仅有“黑色对象指向白色对象”并不足以断言漏标**：如果仍有灰色对象可沿引用链发现 C，它仍能被扫描。危险在于程序同时把对象移到已扫描区域，并删除或隐藏了其余可发现路径。

写屏障是在相关指针写入时，由编译器插入、运行时执行的额外逻辑，用于记录或标记受影响对象。它关注引用变化，例如 `a.next = b`；普通整数赋值 `a.count = 3` 不需要 GC 指针写屏障。[混合屏障设计](https://github.com/golang/proposal/blob/master/design/17503-eliminate-rescan.md)

## 3. 插入屏障、删除屏障与混合屏障

### 3.1 一次赋值包含删除和插入

把 `a.next` 从 old 改成 new，同时删除了旧引用、插入了新引用。两种屏障分别保护这两个目标：

| 机制 | 在指针写入前保护谁 | 在上一节例子中的作用 |
|---|---|---|
| 插入屏障 | 新引用指向的对象 | `A.next = C` 时保护 C |
| 删除屏障 | 被覆盖的旧引用指向的对象 | `B.next = nil` 时保护旧目标 C |

“删除”是删除引用，不是释放对象；`a.next = nil` 和 `a.next = other` 都可能删除旧引用。这里的保护用 `shade(x)` 表示：目标若是白色，就标记并安排后续扫描；已经灰色或黑色则不需要重新变灰，也不意味着立即递归扫描完整子图。[屏障语义](https://github.com/golang/go/blob/go1.26.0/src/runtime/mbarrier.go)

经典插入屏障可通过写前保护新目标，维持**强三色不变式：黑色对象不直接指向白色对象**。混合屏障的正确性可用较弱的条件解释：即使存在黑到白的引用，也必须有灰色对象经白色引用链保护该白色对象，使 GC 仍能发现它；不能把所有屏障都解释成必须满足强不变式。[三色不变式](https://github.com/golang/proposal/blob/master/design/17503-eliminate-rescan.md)

### 3.2 Go 的混合屏障算法模型

源码中的逻辑模型如下，属于说明算法的伪代码，不是业务 API：

```text
writePointer(slot, new):
    shade(*slot)                  // 保护旧目标
    if 当前 goroutine 的栈尚未扫描:
        shade(new)                // 保护新目标
    *slot = new
```

`slot` 是指针字段地址，例如 `&a.next`，`*slot` 是覆盖前的旧值。**屏障的记录/保护发生在指针写入发布之前**，不能写成“先赋值，之后再随意补一次屏障”。[算法与写入顺序](https://github.com/golang/go/blob/go1.26.0/src/runtime/mbarrier.go)

栈需要特别处理，是因为 Go 希望省去普通栈写入的屏障，又不在标记结束时重扫所有已扫描的栈。两部分分别防止：

- **堆 → 已扫描的栈**：程序把白色对象的引用读到局部变量，然后删掉堆上的引用。删除屏障在删堆引用时保护旧目标，防止它仅藏在不再重扫的栈中。
- **尚未扫描的栈 → 已扫描的堆对象**：程序把白色对象引用从栈移到黑色堆对象，再清除栈上的引用。插入屏障在写入堆引用时保护新目标。

栈扫描完成后，栈中的目标都已被标记；后续若把未标记目标从堆转移进栈，删除堆引用时仍会受到保护。配合**标记期间新分配的堆对象直接标黑**，混合屏障使已扫描的栈不必在标记结束时再次集中扫描，但不代表 GC 完全没有 STW。[栈重扫消除方案](https://github.com/golang/proposal/blob/master/design/17503-eliminate-rescan.md)

### 3.3 实现中的缓冲与省略

算法模型中的栈颜色条件，不等同于每次写入都执行一次栈颜色判断。编译器生成的常见路径可概括为：

```text
if 写屏障已启用:
    将 new 记录到写屏障缓冲区
    将 *slot 的旧值记录到写屏障缓冲区
*slot = new
```

实现保守记录新旧目标，并在可证明安全时省略不必要的记录，例如旧值已知为零。编译器能够确定目标是当前栈上的地址时可省略屏障；无法确定位置的间接指针写入仍可能生成屏障，向全局变量写入堆指针也需要处理。不能把它理解为“所有赋值都触发”或“任何栈写入都绝对不触发”。[编译器写屏障处理](https://github.com/golang/go/blob/go1.26.0/src/cmd/compile/internal/ssa/writebarrier.go)

每个 P 的写屏障缓冲区用于批量处理指针记录，刷新时完成必要标记并安排扫描。因此，概念上的“写入时标灰”不要求每次赋值都当场扫描对象；缓冲中的待处理记录也属于尚未完成的标记工作。[写屏障缓冲实现](https://github.com/golang/go/blob/go1.26.0/src/runtime/mwbbuf.go)

## 4. 写屏障处于 GC 的哪个阶段

```text
STW：完成清扫终止，准备标记并开启写屏障
    ↓
并发标记：处理根、扫描对象，同时处理屏障产生的工作
    ↓
确认标记工作与相关缓冲均已处理，完成终止协调
    ↓
STW：标记终止，关闭标记期写屏障
    ↓
并发清扫：回收本轮未标记对象占用的槽位或 span
```

屏障工作可以在并发标记期间多次被处理，不是等所有对象扫描完后才统一处理一次。扫描某个 goroutine 的栈时还需要暂停该 goroutine；这与暂停整个程序的 STW 不同。常规 GC 周期有开始与结束两处短 STW。[GC 阶段说明](https://github.com/golang/go/blob/go1.26.0/src/runtime/mgc.go)

## 5. Green Tea 改变了什么

Go 1.25 将 Green Tea 作为实验引入，Go 1.26 默认启用。它通过改善小对象标记与扫描的内存局部性及 CPU 可扩展性降低开销。官方对大量使用 GC 的真实程序给出的预期是 GC 开销减少约 10–40%，具体收益依工作负载而异，不能当作本项目已经测得的收益，也不等于程序整体性能提高同样比例。

三色抽象与混合写屏障仍然用于理解可达性和并发修改的正确性；不要把 Green Tea 简化成“整个标记清扫算法改成按 span 扫描”。[Go 1.26 发布说明](https://go.dev/doc/go1.26#runtime)

## 6. 边界与排查

- GC 写屏障保障对象不会因并发引用变化被漏标，**不能代替锁、原子操作或其他同步机制**，也不等同于 CPU 内存屏障。
- 写屏障可能保守保留一些对象，本轮没有回收不等于内存泄漏；还要检查程序是否长期持有引用。
- 内存占用高需区分存活堆、分配速率、碎片、runtime 保留页；具体空间复用与归还见[内存分配器笔记](13_Go_内存分配器：mcache、mcentral、mheap_与_mspan.md)。
- 调优先观察 `GODEBUG=gctrace=1`、runtime metrics 和 pprof，再评估 `GOGC` 或内存限制；不能只根据一次 GC 后进程内存是否下降判断 GC 是否正常。[Go GC 指南](https://go.dev/doc/gc-guide)

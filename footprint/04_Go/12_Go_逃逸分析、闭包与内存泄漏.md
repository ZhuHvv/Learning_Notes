# 04.12 Go 逃逸分析、闭包与内存泄漏

> 所属主线：Go Runtime 与内存  
> 难度：进阶  
> 前置知识：闭包、指针与对象生命周期  
> 后续知识：内存分配器与垃圾回收

## 1. 总体性概念

逃逸分析决定变量在栈还是堆；内存泄露是对象不再需要却仍被引用。二者不是一回事。


## 2. 原理性解释

- 返回局部变量指针通常会使该变量逃离当前函数栈帧；最终存储位置以编译器逃逸分析结果为准。
- 闭包捕获外层变量可能逃逸。
- 赋给全局变量可能逃逸。
- 逃逸增加 GC 压力但不是泄露。
- 泄露通常由长期引用导致。

### 逃逸分析决定变量放栈还是堆

返回局部变量指针、把局部变量赋给全局变量、闭包捕获外部变量，都可能让变量生命周期超过当前函数栈帧。编译器必须为它安排足够长的安全存储期，常见结果是移动到堆；经过内联和跨函数分析后，具体结果可能变化。逃逸不是语言错误，只是堆分配通常会增加 GC 压力。

内存泄漏则不同：泄漏是对象已经不再需要，但仍被引用导致无法回收。逃逸是分配位置变化；泄漏是生命周期管理错误。

## 3. 机制流程

1. 编译器分析生命周期。
2. 函数内使用放栈。
3. 跨函数生命周期放堆。
4. GC 回收不可达堆对象。

### 逃逸排查流程

```bash
go build -gcflags='-m' ./...
```

```go
func makePtr() *int {
    x := 10
    return &x // 引用离开当前函数；用编译器输出确认实际分配位置
}
```

优化时不要盲目追求“零逃逸”。先看 pprof、分配热点和延迟指标，再决定是否通过减少闭包捕获、复用 buffer、避免大对象接口装箱等方式优化。

## 4. 类比理解

逃逸像文件被带出办公室；泄露像没用的文件仍锁在柜子里。

## 5. 应用举例 / 代码或伪代码

```go
func Ptr() *int {
    x := 10
    return &x // 生命周期越过当前函数栈帧
}

func Counter() func() int {
    n := 0
    return func() int { n++; return n }
}
```

## 6. 边界与排查

- 逃逸分析是编译器优化，不是 Go 语言承诺的固定分配位置。
- 堆分配变多不等于内存泄漏；只要对象不可达，GC 仍可回收。
- 内存持续增长时，同时检查长期 map/slice、缓存无上限、闭包持有大对象、未停止的 timer/ticker 和 goroutine 泄漏。
- 使用 `go build -gcflags='all=-m=2' ./...` 查看原因，再用 benchmark、pprof 和实际延迟验证优化价值。

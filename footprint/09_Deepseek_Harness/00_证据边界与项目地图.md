# DeepSeek Harness：证据边界与项目地图

审查日期：2026-08-15

源码基线：`47f943859bef60e4160492346772ded9b24f765a`

## 1. 先给结论

DeepSeek Harness（`dsh`）是一个由 Cordis 驱动的 TypeScript Agent Harness。它把模型适配、提示词组装、工具注册和执行、会话日志、持久化、沙箱、Web 界面乃至默认 Agent Loop 都做成可配置的插件，而不是把它们固定在一个不可替换的核心类里。

对学习者最重要的思维转换是：不要把 dsh 只看作“模型调用加工具循环”。它是一个以**可组合运行时**和**可回放会话事件**为两条主线的 Agent 产品底座。

## 2. 本笔记的证据等级

本专题遵循从强到弱的证据顺序：

1. **源码与可执行配置**：TypeScript、`cordis.patch.yml`、`agent.cordis.yml` 是当前实现的最高证据。
2. **测试与快照**：说明项目主动固定的可观察行为；不能自动证明未覆盖路径。
3. **仓库架构文档与生成目录**：用于定位和解释；遇到冲突时回到源码和配置。
4. **官方 GitHub 页面和产品文档**：可说明发布状态、使用约定和公开承诺，不能替代本地版本的实现证据。
5. **第三方文章**：只用作提问和比较的视角，绝不用于断言 dsh 的内部类、算法、常量或路线图。

每个专题都会区分“代码事实”“基于事实的解释”和“尚不能证明的事”。例如，`token-meter` 出现缓存读写 token 字段，只能证明 dsh 会记录/投影提供方给出的用量；不能据此推出某个 provider 的前缀缓存淘汰策略。

## 3. 先识别项目的五个对象

```text
Profile（一个产品运行时）
  └─ Bundle patch（把插件行叠加成产品）
       └─ Cordis Context（服务、事件、effect 的运行树）
            └─ Agent（一个有 inbox、scope、session 的活跃执行者）
                 └─ Session（追加式事件日志及其派生视图）
```

- **Profile** 决定启动哪一套产品组合。CLI 将 bundle、用户 patch 和命令行 overlay 叠加后启动 Loader。
- **Cordis Context** 是插件协作的容器。插件贡献 service、typed event 和可撤销 effect；它们不是全局单例的随意堆叠。
- **Agent** 是实时执行实体；拥有 inbox、当前 loop 状态、agent scope 和一个 session。
- **Session** 是跨进程、UI、回放和持久化都可以理解的事实流；模型消息历史从它导出。

## 4. 目录不等于调用方向

`packages/` 按能力域组织，不是传统三层 Web 架构。阅读时先按下表聚类：

| 域 | 主要问题 |
| --- | --- |
| `core/` | Agent 如何存在、prompt 如何组成、工具如何调度、日志如何记录？ |
| `llm/` | 如何定义消息/流并接入不同 provider？ |
| `fs/`、`shell/`、`web/`、`skill/`、`subagent/`、`workflow/`、`code-runtime/`、`mcp/` | Agent 能调用哪些外部能力，谁提供这些能力？ |
| `sandbox/`、`interaction/`、`guard/` | 哪些操作允许、询问、超时或被阻断？ |
| `session/`、`session-query/`、`context/`、`compaction/` | 如何保存、检索、注入、度量和缩短上下文？ |
| `attachment/`、`spill/` | 图片和过大文本如何以日志外对象保存，再由 durable reference 指向？ |
| `goal/`、`plan/`、`todo/`、`schedule/`、`feedback/` | 目标、协作状态、提醒与用户反馈如何进入产品？ |
| `settings/`、`credentials/`、`storage/`、`workspace/` | 用户配置、密钥引用、领域数据与工作区记录由谁持有？ |
| `bundle/`、`preset/`、`boot/` | 一套运行时和一个 Agent 的能力集合如何被组合？ |
| `host/`、`client/`、`api/`、`apps/cli` | 如何把同一 runtime 暴露为 Web 或 Headless 产品？ |

`packages/README.md` 是各组责任的索引；`docs/module-graph.md` 是由依赖元数据生成的包依赖图。不要仅从目录名推断一个包是否已挂载：真正运行的集合由 profile patch 决定。

这一区别对 MCP 尤其重要：仓库已有 `mcp-client`，可通过 stdio 或 Streamable HTTP 把外部 MCP server 的 tools 注册为 `mcp__<serverName>__<rawName>`，但 base bundle 和随附 Agent preset 都没有默认挂载它；当前桥接范围也只有 tools，不含 MCP resources 或 prompts。类似地，Terminal、LSP、Schedule 等包或示例存在，也不等于默认模型工具面已经包含它们。

## 5. 当前默认产品组合的可证实事实

`packages/bundle/base/cordis.patch.yml` 是所有 profile 的基础层。它显式插入 LLM、Session、Agent、默认模型、JSONL 持久化、子进程、本地 sandbox、审批、文件工具、技能、命令、目标、压缩、子代理等插件行。

其中默认 Agent 模型路由配置为 `deepseek-official` / `deepseek-v4-flash`，但 provider 和模型是 composition/config 的值，不是 Agent Loop 的写死依赖。Web 和 Headless 在 base 之上分别追加自己的 bundle patch：前者加入 Host、HTTP、API gateway 和浏览器插件；后者加入一次性任务 runner。

## 6. dsh 与通用 Agent 基础概念的对应

| 通用概念 | dsh 中可读的实现落点 |
| --- | --- |
| Prompt | `SystemPrompt` 的 sections、variables、contexts、tool schemas |
| 短期上下文 | `Session.deriveMessages()` 导出的模型历史和本次 runtime context |
| 持久记忆/轨迹 | 追加式 `SessionEvent`、JSONL/SQLite 持久化、projection、查询 |
| Tool use | Tools registry 与 `pre-execute → execute → post-execute` 管线 |
| Agent Loop | `ReactLoopAgent` 的 turn/step 状态机 |
| 人类在环 | approval、commands、plan、ask-user、Web UI |
| 多 Agent | subagent provider、session lineage、后台 continuation/workflow |
| 可观测性/评估 | durable log、telemetry、invariant、keyless snapshot、e2e |

注意“记忆”在此不是一个单独的向量数据库包名。当前源码能直接证明日志、指令文件、投影、SQLite 全文检索与 session reference；不能把这些直接描述为已实现的通用语义向量记忆系统。

## 7. 推荐阅读顺序

1. `docs/architecture.md`：先建立术语。
2. `apps/cli/src/bin.ts` 与 `apps/cli/src/profile-boot.ts`：理解实际启动。
3. `packages/bundle/base/cordis.patch.yml`：看默认树由什么组成。
4. `packages/core/agent-loop/src/agent.ts`：追踪一次 turn。
5. `packages/core/session/src/types.ts`：理解 durable data。
6. 按目标进入 tool、context、subagent、Web 等专题。

## 8. 常见误区

- “Everything is a Plugin”不等于任意插件都安全或互不影响；服务依赖、scope、effect 生命周期和配置顺序仍然决定行为。
- “Session 有日志”不等于所有进程内瞬态状态都自动持久化；只有明确写入 event 的事实才能重放。
- “有 Web UI”不等于 Agent Loop 属于浏览器；Loop 位于共享 host runtime，Web 是一个产品表面。
- “有 DeepSeek 默认模型”不等于项目只能接 DeepSeek；LLM adapter 是一个 capability seam。

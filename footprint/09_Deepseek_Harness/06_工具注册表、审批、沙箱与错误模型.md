# DeepSeek Harness：工具注册表、审批、沙箱与错误模型

## 1. 一句话结论

dsh 的工具安全不是一个布尔开关：`ctx.tools` 负责注册、可见性、参数/输出校验与执行管线，`tools/pre-execute` 和 monotonic guard 决定单次调用能否进入 dispatch，`ctx.approval` 处理一次性人类授权，`sandboxPolicy` 解析每次调用的文件权限，具体 Shell/FS provider 才负责真正执行或 fail closed；错误最终被归一成可记录、可回放的 tool result，而不是靠异常文本随意传播。

## 2. 源码调用链与数据流

### 2.1 注册与可见性

```text
tool plugin
  → ctx.tools.register(ToolDefinition)
  → 注册层：global / preset / agent scope
  → schemas(agent) 按 scope shadow + restrict 计算
  → SystemPrompt assembly
       ├─ native function definitions
       ├─ code: run_code + generated SDK
       └─ both
```

`register()` 要求工具声明 input schema、canonical output schema、renderer，可选 `timeoutMs`、并发安全分类、最终内容修整和 UI presentation。相同 scope layer 的重名会 load-time 失败；近 scope 可 shadow 远 scope。`restrict()` 是 agent 可见性组合，不是安全 authority boundary；真正的权限决策仍必须发生在执行路径。

### 2.2 完整执行管线

```text
ctx.tools.execute(input)
  → lossless JSON snapshot + freeze arguments
  → pre-abort / unknown / hidden / code-only 检查
  → tools/pre-execute waterfall
      allow | deny | ask
  → ask 时 ctx.approval.request()
  → ctx.tools.guard() 的 monotonic deny
  → tools/execute around wrapper
      timeout / retry / metrics 可在此包裹 body
  → ToolDefinition.execute(args, exec)
  → canonical output snapshot + schema validation
  → output.render()
  → tools/post-execute
      accept / replace value / replace content / block / additionalContexts
  → definition.finalizeContent()
  → tools/result（live observe-only）
  → Agent Loop 追加 tool/result（durable Session event）
```

注意 `tools/result` 与 `tool/result`：前者是进程内观察事件，后者才是 Session durable event。工具抛错、policy listener 抛错、schema 不合规、取消和 timeout 都被规范化成 `ToolExecutionResult { isError: true, error, content }`；`HarnessError` 的稳定 `{ name, code }` 可进入内部 error info，模型通常看到 `Error: <message>`。

### 2.3 审批链

`tools/pre-execute` 的 `ask` 不是直接弹 UI。registry 先寻找 `ctx.approval`：

```text
PreToolDecision.ask
  → 无 approval service / 无 owning agent：deny
  → approval policy = never：不触发 answerer，直接 rejected
  → policy = ask：approval/request waterfall
  → allowed-once | rejected | cancelled | unavailable
  → durable approval/asked + approval/decided 审计对
  → allowed-once 仅放行本次调用
```

审批只允许发生在 open agent turn。服务本身不提供 UI answerer；Web/ACP 等 front door 负责安装 responder。缺失、失败、取消均 fail closed。当前没有 allow-always、记忆规则或 grant store。

### 2.4 沙箱链

```text
tool call
  → sandboxPolicy.resolve({ session, approved mode? })
      explicit approved mode
        > session 最后 sandbox/mode
        > deployment default
  → 得到 { mode, workspaceRoot, sessionId? }
  → danger-full-access：consumer 绕过 confine，直接执行
  → read-only / workspace-write：ctx.sandbox.confine(argv, policy)
  → provider 返回 replacement argv + enforcement + stderr dialect
  → consumer spawn replacement argv
```

`ctx.sandbox` 只定义同一 host/kernel 世界中的文件效果约束。`read-only`、`workspace-write` 是 confined mode；`danger-full-access` 是 consumer 明确绕过 confinement。没有可用 backend 时抛 `SANDBOX_UNAVAILABLE`，不能静默无沙箱执行。返回的 `enforcement` 可能是 `full` 或 `partial`；denial signatures 表示沙箱正常工作并拒绝文件操作，runner-failure rules 表示 runner 本身没能启动命令，两者不能混为一类。

### 2.5 默认 composition

`dsh-base` 默认挂载：

- `sandbox-local`、`sandbox-policy`，默认从 `DSH_PERMISSION_MODE` 或 `workspace-write` 解析；
- POSIX `bash-sandbox` 或 Windows `pwsh-sandbox`；
- `user-approval`，默认 confined mode 下为 `ask`，`danger-full-access` 下为 `never`；
- permission presets：`read-only + ask`、`workspace-write + ask`、`danger-full-access + never`；
- Shell/FS tool consumer 在需要更宽 mode 时发起单次 escalation，审批通过后只重做那次 call。

permission preset 是把 sandbox 与 approval 两个旋钮按会话固定下来。默认设置只影响新 session；已有 session 的 durable knob events 不会被后来修改的用户默认反向改写。

## 3. 设计取舍

- 工具 schema、canonical value 与模型展示分离：程序化 consumer 不必解析文本，UI replay 只依赖持久化 presentation metadata。
- pre-policy 可扩展，guard 单调拒绝：允许插件排序和询问，但 owner 的最终安全拒绝不能被后续 listener 重新放行。
- approval 与 sandbox 分离：审批是授权协议；沙箱是执行机制。批准不等于实现约束，约束也不等于已得到用户同意。
- per-call policy 而非 provider 全局切换：并发 session 可以使用不同 workspace root 与 mode，一次 escalated retry 不污染后续调用。
- fail closed：需要 confinement 时 backend 不可用就失败，避免“为了可用性”偷偷扩大权限。
- cooperative cancellation：same-process promise 无法硬杀；工具 body 必须观察/转发 signal，真正硬终止要由 subprocess/worker provider 实现。

## 4. 不能推出的结论

- `tools.restrict()` 不能证明安全隔离；它主要控制 agent 能看见和调用哪些全局工具。
- `read-only` 不能推出网络、进程、syscall、设备或凭据隔离；当前 sandbox vocabulary 只承诺文件效果。
- `enforcement: partial` 不能当作 `full`，也不能因为存在 sandbox provider 就宣称跨平台完全等价。
- approval audit 不能推出人类看见了工具完整参数；当前 request 只携带 tool name、reason 和可选 call id。
- tool result 为 `isError` 不总是“命令失败”：例如 Shell 的非零 exit 是正常 `ShellRunResult`，模型应检查 exit marker；基础设施失败才成为 tool error。
- Web 的 Host/Origin fence 是可达性策略，不是用户认证；不能把本地浏览器边界描述成多租户 auth。

## 5. 常见误区

- 把 `approval: never` 理解为自动允许：它表示不弹审批，所有需要 approval 的动作直接拒绝。
- 把 `danger-full-access` 理解为一种 sandbox backend：它是 consumer 明确跳过 `ctx.sandbox`。
- 在 tool body 内自行吞掉异常并返回貌似成功的文本：会丢失结构化 code，也破坏统一错误路径。
- 只看 tool 是否注册，不看当前 agent 的 scope、preset、restriction 与 presentation mode。
- 把 stderr 中类似“permission denied”的任何文字都当沙箱拒绝：consumer 应使用当前 backend 返回的 dialect 和 runner-failure rules 分类。

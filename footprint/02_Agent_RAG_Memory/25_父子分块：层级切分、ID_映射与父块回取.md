# 父子分块：层级切分、ID 映射与父块回取

## 1. 总体性概念

父子分块（Parent-Child Chunking，也常称 Parent Document Retrieval）解决的是 RAG 中两种需求之间的冲突：

- 小块语义集中，向量不容易被多个主题稀释，更适合精确检索；
- 大块上下文完整，更适合交给 LLM 理解、引用和生成答案。

它的核心不是把原文独立切出一套大块和一套小块后，再临时猜测对应关系，而是**层级切分**：

```
原始文档
  ↓ 父级切分器
父块 P1、P2、P3
  ↓ 在每个父块内部使用子级切分器
P1 → C1、C2、C3
P2 → C4、C5、C6
P3 → C7、C8
```

每个子块创建时便记录所属父块的稳定 ID：

```python
child.metadata["parent_id"] = parent.id
```

查询时只检索子块，再通过 `parent_id` 回取父块：

```
用于匹配的单位：子块
用于返回上下文的单位：父块
连接二者的方式：parent_id
```

父子关系在**入库阶段**建立并持久化，不是在查询命中后根据文本相似度、字符重叠或位置关系临时计算。

## 2. 原理性解释

### 2.1 大小块怎样产生

假设一篇文档约有 8000 Token，配置为：

```python
parent_chunk_size = 2000
parent_chunk_overlap = 200
child_chunk_size = 400
child_chunk_overlap = 50
```

第一步先切父块：

```
原始文档 D1
├─ P1：0～2000
├─ P2：1800～3800
├─ P3：3600～5600
└─ P4：5400～7400
```

父块之间可以有 overlap。第二步不是再次独立切原文，而是在每个父块内部切子块：

```
P1
├─ C1：P1 的 0～400
├─ C2：P1 的 350～750
├─ C3：P1 的 700～1100
└─ ...

P2
├─ C6：P2 的 0～400
├─ C7：P2 的 350～750
└─ ...
```

这样 `C1、C2、C3` 天然属于 `P1`，`C6、C7` 天然属于 `P2`。即使父块或子块有 overlap，所属关系也不会含糊。

### 2.2 为什么不能从原文独立切两次

下面的做法虽然能得到两套大小不同的块，却没有自动建立父子关系：

```python
parents = parent_splitter.split_documents(raw_documents)
children = child_splitter.split_documents(raw_documents)
```

父块和子块的边界分别从原文独立产生，还必须额外回答：

```
这个子块落在哪个父块中？
```

存在 overlap 时，一个独立产生的子块还可能横跨两个父块边界。此时按包含关系、最大重叠长度或最近边界进行归属都会增加歧义和实现复杂度。

标准做法是：

```python
parents = parent_splitter.split_documents(raw_documents)

for parent in parents:
    children = child_splitter.split_documents([parent])
    for child in children:
        child.metadata["parent_id"] = parent.metadata["parent_id"]
```

这使父子映射成为建库数据的一部分，而不是查询阶段的推断结果。

### 2.3 父块与子块保存的内容

典型记录如下：

```python
parent = {
    "id": "P001",
    "text": "上下文较完整的大块",
    "metadata": {
        "source": "manual.md",
        "parent_index": 0,
    },
}

child = {
    "id": "C001",
    "text": "语义集中的小块",
    "embedding": [0.013, -0.284, ...],
    "metadata": {
        "parent_id": "P001",
        "child_index": 0,
        "source": "manual.md",
    },
}
```

通常：

- 父块保存正文和来源信息，不一定生成向量；
- 子块保存正文、`parent_id` 和检索向量；
- `child.parent_id → parent.id` 必须稳定、可批量查询且可校验。

父块也可以生成向量，但这不是父子检索的必要条件。

### 2.4 为什么检索子块而不是直接检索父块

一个父块可能同时介绍安装、网络配置、启动错误和日志系统。整个父块的单一向量会混合多个主题。

子块若只包含：

```
启动失败时检查 config.yaml、配置目录和端口占用。
```

那么查询“为什么服务启动失败”时，它通常比整个父块更容易得到高相似度。

但只把这句话交给 LLM，可能缺少：

- 前置条件；
- 完整操作步骤；
- 异常分类；
- 配置文件位置；
- 后续处理说明。

因此系统使用子块提高召回精度，再返回它所属的父块恢复完整语境。

## 3. 机制流程

### 3.1 离线建库流程

```
原始文档
  ↓ 父级切分
父块
  ↓ 生成 parent_id
父块以 parent_id 为 key 写入文档存储
  ↓ 在每个父块内部切子块
子块写入相同 parent_id
  ↓ 对子块生成 Embedding
子块正文 + 向量 + parent_id 写入向量索引
```

离线阶段的两个逻辑存储是：

```
Vector Store
  └─ child_id、child_text、child_embedding、parent_id、metadata

Document Store
  └─ parent_id → parent_text、metadata
```

它们不一定是两个物理数据库，可以是：

- 向量数据库与 PostgreSQL/Redis 的组合；
- 同一数据库中的两个 collection；
- 同一数据库中的两张表；
- 同一 collection 中用 `chunk_type` 区分父块和子块。

物理位置不是关键，稳定的 ID 映射才是关键。

### 3.2 在线查询与回取流程

```
用户问题
  ↓
生成 Query Embedding
  ↓
在向量索引中检索子块
  ↓
按子块排名读取 metadata.parent_id
  ↓
parent_id 去重
  ↓
从文档存储批量读取父块
  ↓
控制父块数量与上下文预算
  ↓
交给 LLM
```

例如子块命中结果为：

```
Top 1：C7  → parent_id=P2
Top 2：C8  → parent_id=P2
Top 3：C2  → parent_id=P1
Top 4：C15 → parent_id=P4
```

按首次出现顺序去重后得到：

```
P2、P1、P4
```

最终返回三个父块，而不是重复返回四个子块所对应的父块。

### 3.3 父块排序

最简单的实现让父块顺序由排名最高、最先出现的子块决定：

```
子块排名：
C7(P2)  0.92
C8(P2)  0.89
C2(P1)  0.87
C9(P3)  0.85

父块排名：
P2
P1
P3
```

生产系统也可以聚合同一父块的多个子块分数：

```python
parent_score = max(child_scores)
```

或者：

```python
parent_score = sum(sorted(child_scores, reverse=True)[:n])
```

`max` 强调父块中最相关的局部证据；`top-n sum` 会奖励同一父块包含多个相关子块。分数聚合属于排序优化，不是父子检索成立的必要步骤。

## 4. 类比理解

父子分块像一本技术手册的“索引卡片 + 完整章节”：

- 子块像索引卡片，只写一个集中主题，方便快速命中；
- 父块像索引卡片所指向的完整章节，保留前因后果；
- `parent_id` 像索引卡片上的章节编号。

检索系统不会在命中卡片后重新比较整本书，猜它来自哪个章节；章节编号在制作卡片时就已经写好。

## 5. 应用举例 / 代码或伪代码

### 5.1 不依赖框架的父子分块实现

下面用字符切分展示父子关系。真实项目可将 `split_text` 换成 Token、递归、Markdown 结构或语义切分器，但映射原则不变。

```python
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any
from uuid import uuid4


@dataclass
class Document:
    page_content: str
    metadata: dict[str, Any] = field(default_factory=dict)


def split_text(
    text: str,
    chunk_size: int,
    chunk_overlap: int,
) -> list[str]:
    if chunk_size <= 0:
        raise ValueError("chunk_size 必须大于 0")
    if chunk_overlap < 0:
        raise ValueError("chunk_overlap 不能小于 0")
    if chunk_overlap >= chunk_size:
        raise ValueError("chunk_overlap 必须小于 chunk_size")

    chunks: list[str] = []
    start = 0

    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunk = text[start:end]

        if chunk.strip():
            chunks.append(chunk)

        if end == len(text):
            break

        start = end - chunk_overlap

    return chunks


def build_parent_child_documents(
    raw_documents: list[Document],
    parent_chunk_size: int = 2000,
    parent_chunk_overlap: int = 200,
    child_chunk_size: int = 400,
    child_chunk_overlap: int = 50,
) -> tuple[dict[str, Document], list[Document]]:
    parent_store: dict[str, Document] = {}
    child_documents: list[Document] = []

    for raw_doc_index, raw_doc in enumerate(raw_documents):
        parent_texts = split_text(
            text=raw_doc.page_content,
            chunk_size=parent_chunk_size,
            chunk_overlap=parent_chunk_overlap,
        )

        for parent_index, parent_text in enumerate(parent_texts):
            parent_id = str(uuid4())
            parent_document = Document(
                page_content=parent_text,
                metadata={
                    **raw_doc.metadata,
                    "raw_doc_index": raw_doc_index,
                    "parent_index": parent_index,
                    "parent_id": parent_id,
                },
            )

            # 父块进入普通文档存储。
            parent_store[parent_id] = parent_document

            # 子块只在当前父块内部产生。
            child_texts = split_text(
                text=parent_text,
                chunk_size=child_chunk_size,
                chunk_overlap=child_chunk_overlap,
            )

            for child_index, child_text in enumerate(child_texts):
                child_documents.append(
                    Document(
                        page_content=child_text,
                        metadata={
                            **raw_doc.metadata,
                            "parent_id": parent_id,
                            "parent_index": parent_index,
                            "child_index": child_index,
                        },
                    )
                )

    return parent_store, child_documents
```

使用方式：

```python
raw_documents = [
    Document(
        page_content="这里是一篇很长的技术文档……" * 1000,
        metadata={
            "source": "system_manual.md",
            "title": "系统使用手册",
        },
    )
]

parent_store, child_documents = build_parent_child_documents(
    raw_documents=raw_documents,
    parent_chunk_size=2000,
    parent_chunk_overlap=200,
    child_chunk_size=400,
    child_chunk_overlap=50,
)

first_child = child_documents[0]
parent_id = first_child.metadata["parent_id"]

print("父块数量：", len(parent_store))
print("子块数量：", len(child_documents))
print("子块所属父块：", parent_id)
print("对应父块：", parent_store[parent_id].page_content)
```

### 5.2 命中子块后回取父块

```python
def retrieve_parent_documents(
    query: str,
    vector_store,
    parent_store: dict[str, Document],
    child_top_k: int = 8,
    parent_top_k: int = 4,
) -> list[Document]:
    matched_children: list[Document] = (
        vector_store.similarity_search(
            query,
            k=child_top_k,
        )
    )

    # 保留首次命中顺序，同时去重。
    parent_ids: list[str] = []
    seen: set[str] = set()

    for child in matched_children:
        parent_id = child.metadata.get("parent_id")

        if parent_id is None:
            raise ValueError("子块缺少 parent_id，无法回溯父块")

        if parent_id not in seen:
            seen.add(parent_id)
            parent_ids.append(parent_id)

    parent_documents: list[Document] = []

    for parent_id in parent_ids[:parent_top_k]:
        parent = parent_store.get(parent_id)

        if parent is not None:
            parent_documents.append(parent)

    return parent_documents
```

生产系统更适合用 `mget(parent_ids)` 批量读取，并记录缺失的父块 ID；不能静默假设每个子块都一定有可用父块。

### 5.3 聚合父块分数

```python
from collections import defaultdict


def aggregate_parent_scores(child_hits):
    """
    child_hits: list[tuple[Document, float]]
    """
    scores: dict[str, list[float]] = defaultdict(list)

    for child, score in child_hits:
        parent_id = child.metadata["parent_id"]
        scores[parent_id].append(score)

    parent_scores = {
        parent_id: max(child_scores)
        for parent_id, child_scores in scores.items()
    }

    return sorted(
        parent_scores.items(),
        key=lambda item: item[1],
        reverse=True,
    )
```

### 5.4 LangChain 中的对应配置

在 LangChain 1.x 的当前包结构中，经典 retriever 通常从 `langchain_classic` 导入：

```python
from langchain_classic.retrievers import ParentDocumentRetriever
from langchain_core.documents import Document
from langchain_core.stores import InMemoryStore
from langchain_text_splitters import RecursiveCharacterTextSplitter


vectorstore = your_vectorstore
parent_store = InMemoryStore()

parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size=2000,
    chunk_overlap=200,
)
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=400,
    chunk_overlap=50,
)

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=parent_store,
    parent_splitter=parent_splitter,
    child_splitter=child_splitter,
    id_key="doc_id",
    search_kwargs={"k": 8},
)

documents = [
    Document(
        page_content="一篇很长的技术文档……",
        metadata={"source": "manual.md"},
    )
]

retriever.add_documents(documents)
parents = retriever.invoke("系统启动失败应该检查什么？")
```

旧版本教程中常见的导入方式是：

```python
from langchain.retrievers import ParentDocumentRetriever
```

LangChain v1 精简了 `langchain` 命名空间，并将这类经典组件移入 `langchain-classic`；应按项目实际安装版本选择导入路径，不能混用新旧教程。

`add_documents` 内部的逻辑可概括为：

```
原始文档
  → parent_splitter
  → 为父块生成 ID
  → child_splitter
  → 子块 metadata[id_key] = 父块 ID
  → 子块写入 vectorstore
  → 父块以该 ID 为 key 写入 docstore
```

若不提供 `parent_splitter`，父文档可以直接是传入的原始文档本身。此时要特别评估原文长度，避免回取内容一次占满 LLM 上下文窗口。

## 6. 你在讨论中的理解推进

- 起点：你已经正确抓住“小块语义集中、适合检索；大块上下文完整、适合生成”的动机。
- 核心追问一：大小块究竟怎样产生？
- 关键修正：不是从原文独立切两遍后再做归属，而是先切父块，再在每个父块内部切子块。
- 核心追问二：命中小块后怎样找到大块？
- 最终理解：子块创建时写入 `parent_id`，检索后按该 ID 去文档存储回取父块；映射在入库阶段确定，不靠查询时的文本匹配。
- 进一步连接：子块检索结果需要先按 `parent_id` 去重，父块排序可以继承最佳子块排名，也可以聚合多个子块分数。
- 与后续讨论的连接：父子分块分离“检索单元”和“返回单元”；Late Chunking 改善 Chunk 向量的上下文化方式，二者解决不同问题并可以组合。

## 7. 常见误区与排查思路

### 7.1 常见误区

1. **把原文分别切成大小两套块，就认为父子关系已经存在**  

两套边界独立产生时仍缺少稳定映射，overlap 会进一步增加歧义。

1. **命中后再用相似度寻找父块**  

父块归属是结构关系，不是语义相似关系；应使用显式 ID。

1. **父块和子块都必须放在两个独立数据库中**  

物理存储可以相同或不同，必要条件只是 `child.parent_id → parent.id` 可稳定读取。

1. **父块也必须生成 Embedding**  

标准父子检索只需要索引子块；父块向量可用于多路召回，但不是回取的前提。

1. **多个子块命中同一父块时重复返回父块**  

必须先按 `parent_id` 去重，再进行父块数量与上下文预算控制。

1. **直接把完整原文当父块，不考虑长度**  

原文过长会把检索精度问题转化为上下文超限、噪声稀释和成本问题。

1. **只删除父块或只重建子块索引**  

两侧版本不一致会产生悬空 `parent_id`、旧正文或权限元数据错配。

1. **认为父子分块等于 Late Chunking**  

父子分块改变检索对象与返回对象；Late Chunking 改变 Chunk Embedding 的生成时机。

### 7.2 排查顺序

```
父子切分效果异常
  ↓
检查是否先切父块、再在父块内部切子块
  ↓
检查每个子块是否有 parent_id
  ↓
检查 parent_id 是否能在 docstore 中批量命中
  ↓
检查父块和子块的 source、版本、权限 metadata 是否一致
  ↓
检查子块召回排序和 child_top_k
  ↓
检查 parent_id 去重与父块分数聚合
  ↓
检查 parent_top_k、父块长度和总上下文预算
  ↓
使用 Recall@K、答案忠实度和人工样例评估
```

建库完成后至少应验证：

```python
assert all("parent_id" in child.metadata for child in child_documents)
assert all(
    child.metadata["parent_id"] in parent_store
    for child in child_documents
)
```

生产环境还应对父子记录使用同一文档版本号或索引批次号，以支持原子切换、回滚和孤儿记录检查。

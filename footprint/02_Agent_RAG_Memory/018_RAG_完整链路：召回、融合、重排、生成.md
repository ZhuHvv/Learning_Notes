# RAG 完整链路：召回、融合、重排、生成

> 所属分类：Agent / RAG / Memory  
> 修订版本：v10 LLM/RAG 评估增量版  
> 核心问题：如何把文档处理、查询增强、多路检索、重排、生成和评估组织成一条可定位问题的工程链路？

## 1. 总体性概念

RAG（Retrieval-Augmented Generation）不是“向量库搜索 + LLM”两个步骤，而是一条由离线建库、在线检索、上下文构建、受证据约束生成和评估组成的系统。

它主要补足模型参数知识的边界：训练数据可能不包含最新、私有或特定领域资料，模型在证据不足时还可能生成貌似合理但不符合事实的内容。RAG 在请求时检索外部资料，让回答能够利用当前、受权限控制且可引用的证据；它能降低幻觉风险，但不能保证模型绝不出错。

```text
离线：文档 → 解析 → 切分 → 表示 → 索引
在线：问题 → 查询理解/增强 → 召回 → 融合 → 重排 → 上下文 → 生成 → 引用
评估：检索指标 + RAGAS/人工评审 + 运行监控
```

RAG 的最终质量受最弱环节限制。正确资料没有进入索引，后续模型再强也找不到；正确 chunk 已经召回却被重排压低，则问题在排序；证据都正确但回答编造，则问题在生成忠实度。

## 2. 原理性解释

### 2.1 离线建库决定“系统有什么可以找到”

建库需要处理：

- 数据采集：网页、PDF、数据库和业务系统等来源；
- 数据清洗：删除噪声、无关内容和重复项，统一编码与版本；
- 文档解析：正文、标题、表格、代码块、页码；
- chunk 切分：保持语义完整，处理 overlap 和父子层级；
- metadata：来源、权限、项目、时间、版本；
- 表示方式：稠密向量、稀疏词项、多向量；
- 索引：ANN、倒排索引、图谱或混合索引。

常见切分方法包括固定 token 大小并设置 overlap、按段落/章节等语义边界切分，以及递归地按多级分隔符缩小文本。固定大小简单但可能割裂语义；语义边界更完整，但要处理超长章节；递归切分用于在结构完整性与尺寸约束间折中。

切分太小会丢上下文，太大会稀释主题并占用上下文窗口。常见方案是 [父子分块：层级切分、ID 映射与父块回取](025_父子分块：层级切分、ID_映射与父块回取.md)：先切父块，再在每个父块内部切子块；子块通过 `parent_id` 与父块建立稳定映射。查询命中细粒度 child chunk 后，先对父 ID 去重，再从文档存储回取更完整的 parent section。文本块通常由 Embedding 模型编码为向量并写入向量索引；查询必须使用兼容的表示模型和预处理方式。

如果独立编码小 Chunk 会丢失代词、实体继承或章节语境，可以评估 [Late Chunking：全文上下文化、Mean Pooling 与边界对齐](024_Late_Chunking：全文上下文化、Mean_Pooling_与边界对齐.md)：先对全文或长窗口生成 Token 上下文化向量，再按 Chunk 边界池化。它改变建库时的 Chunk 向量生成，不替代分块器、父子回取或在线检索链路。

### 2.2 查询增强决定“从哪些入口找”

原始 query 可能依赖多轮上下文、用词口语化或包含多个方面。可选择：

- Query Rewrite：恢复实体和约束；
- HyDE：生成假设文档帮助 dense retrieval；
- Multi-Query：从多个角度检索；
- 问题分解：复杂问题拆为多个子问题。

这些方法不是默认全部启用。应根据查询分类和离线评估选择触发条件。

### 2.3 多路召回决定“候选覆盖面”

```text
Dense retrieval：语义相似
Sparse/BM25：精确词项
Multi-vector：局部 token/字段匹配
Graph retrieval：实体关系
```

Dense retrieval 常用余弦相似度、点积或基于距离的度量；欧氏距离、曼哈顿距离是否可用以及分数方向取决于向量库配置。Sparse / 全文检索通常通过倒排索引按关键词或词项权重查找。不同分数不能在未经归一化或排序融合的情况下直接比较。

召回阶段追求的是“正确证据进入较大的候选集合”，通常 topK 较大。它允许一些噪声，因为后续还有融合和重排。

### 2.4 融合与重排承担不同职责

融合将多路候选合并，常用 RRF 避免分数尺度不一致；重排则用更昂贵的 Cross-Encoder 或 LLM 判断 query 与候选 chunk 的细粒度相关性。

```text
Recall：宁可多找一些，避免漏掉正确证据
Rerank：在候选中把真正有用的内容排到前面
```

### 2.5 上下文构建不是简单拼接 topK

需要处理：

- 父文档去重；
- 相邻 chunk 合并；
- token budget；
- 引用 ID；
- 权限过滤；
- 冲突版本；
- 长文档压缩。

上下文顺序也会影响模型注意力。应优先放高相关且互补的证据，而不是重复片段。

### 2.6 生成阶段必须显式 grounding

Prompt 应要求：

- 只根据提供证据回答；
- 证据不足时明确说明；
- 为关键结论附来源；
- 区分事实和推断；
- 不把检索 query、HyDE 文本或模型记忆伪装成证据。

### 2.7 评估要分层定位

- Retrieval：Recall@K、MRR、nDCG、正确 chunk 排名；
- Context：precision、recall、重复率、token 利用率；
- Generation：faithfulness、answer relevancy、事实覆盖；
- System：延迟、成本、失败率、缓存命中率。

Ground Truth 的来源和 RAGAS 指标见 `023_RAGAS_评估指标与_Ground_Truth_来源.md`。

## 3. 机制流程

### 3.1 离线 Pipeline

```python
def index_document(document):
    parsed = parser.parse(document)
    chunks = semantic_split(parsed, max_tokens=500, overlap=80)

    for chunk in chunks:
        metadata = build_metadata(document, chunk)
        dense_index.upsert(chunk.id, dense_encoder(chunk.text), metadata)
        sparse_index.upsert(chunk.id, tokenize_and_weight(chunk.text), metadata)
        parent_store.save(chunk.parent_id, chunk.parent_text)
```

### 3.2 在线 Pipeline

```python
def rag_answer(question, history, user):
    rewritten = rewrite_if_needed(question, history)
    query_variants = build_query_variants(rewritten)

    hit_lists = []
    for q in query_variants:
        hit_lists.append(dense_search(q, top_k=40, user=user))
        hit_lists.append(sparse_search(q, top_k=40, user=user))

    candidates = rrf_merge(hit_lists)
    candidates = permission_filter(candidates, user)
    candidates = deduplicate_and_expand_parent(candidates)
    ranked = cross_encoder_rerank(question, candidates)[:10]
    context = pack_context(ranked, token_budget=6000)

    answer = grounded_llm(question=question, context=context)
    return attach_citations(answer, ranked)
```

### 3.3 排查顺序

```text
1. 索引中是否存在正确文档？
2. 原 query/增强 query 的 topK 是否出现正确 chunk？
3. 融合后是否被去重或过滤掉？
4. rerank 是否把它排到可用位置？
5. context pack 是否真正放进 prompt？
6. 模型是否忠实使用证据？
```

不要一看到错误答案就直接修改 Prompt；先确定失败层级。

## 4. 类比理解

RAG 像开卷考试：

- 建库是整理资料和目录；
- 查询增强是把题目转换成可查的关键词和检索角度；
- 召回是从图书馆搬来候选资料；
- 重排是筛出最相关的几页；
- 上下文构建是把资料按顺序摆在桌面；
- 生成是根据资料作答；
- 评估是区分“没找到资料”还是“找到却答错”。

## 5. 应用举例 / 代码或伪代码

### 5.1 可观测的候选记录

```python
@dataclass
class RetrievalHit:
    chunk_id: str
    parent_id: str
    route: str              # raw_dense / bm25 / rewrite / hyde / multi_query
    raw_rank: int
    raw_score: float
    rrf_score: float | None
    rerank_score: float | None
    metadata: dict
```

保存这些字段后，可以回答“正确文档是在哪一步丢掉的”。

### 5.2 权限过滤必须尽早执行

```python
filter_expr = {
    "project_id": user.project_id,
    "visibility": {"$in": user.allowed_scopes},
}
hits = vector_db.search(query_vector, filter=filter_expr, top_k=50)
```

只在生成前过滤可能造成越权数据进入日志、缓存或 reranker。

### 5.3 召回已正确但答案不完整

可能需要：

- 增加 parent chunk；
- 合并相邻段落；
- 删除重复 chunk；
- 明确要求逐项覆盖 reference facts；
- 调整上下文顺序和 token budget。

这不是继续增加 Multi-Query 就能解决的问题。

## 6. 你在讨论中的理解推进

- 起点：你从 Embedding、Milvus、UploadFile、RAGFlow 等局部组件理解 RAG。
- 推进：逐步加入 BM25、RRF、reranker、metadata 过滤、Query Rewrite、HyDE 和 Multi-Query，形成完整检索链路。
- 进一步推进：通过 RAGAS 的标准答案问题，你开始把“系统是否好用”拆成检索覆盖、上下文质量、回答忠实度和答案相关性。
- 最终理解：RAG 是一个可观测、可评估的检索与生成系统，而不是单纯调用向量数据库。

## 7. 常见误区与排查思路

- 只做 dense retrieval，忽略精确术语和稀疏信号；
- 所有 query 无条件 Rewrite/HyDE/Multi-Query，成本高且噪声大；
- 只看最终答案，不保存召回和重排轨迹；
- metadata 只用于显示，不用于权限过滤；
- 把 HyDE 文本当事实证据；
- 用被测 Answer 当 Ground Truth。

> 后续阅读：[Task 聚合、取消、超时与 asyncio.wait](08_Task_聚合、取消、超时与_asyncio.wait.md)、[FastAPI 请求参数、Depends 与生命周期](11_FastAPI_请求参数、Depends_与生命周期.md)

## 1. 一张关系图先分清层级

进程解决资源隔离，线程是操作系统调度的执行单位，协程是运行时在一个或多个线程中调度的轻量任务：

```text
操作系统
├─ 进程 A：独立地址空间、文件描述符、资源边界
│  ├─ 线程 1：栈、寄存器、程序计数器
│  │  ├─ 协程 a
│  │  ├─ 协程 b
│  │  └─ 协程 c
│  └─ 线程 2
└─ 进程 B
```

这是常见模型，不是所有运行时的唯一映射。Python `asyncio` 默认通常是一条事件循环运行在一个线程上；Go runtime 则把大量 goroutine 映射到较少的 OS 线程（M:N 调度）。

| 概念 | 调度者 | 主要资源/状态 | 典型代价与边界 |
| --- | --- | --- | --- |
| 进程 | OS | 独立虚拟内存、文件描述符、网络与系统资源 | 隔离最强；跨进程需 IPC |
| 线程 | OS | 共享进程堆和全局资源；各自有栈、寄存器与 PC | 可并行；共享可变状态要同步 |
| 协程 | 用户态 runtime / Event Loop | 执行位置、局部变量等运行时状态 | 切换轻；协作式模型要求主动让出 |

不同进程默认不能直接读取彼此内存；需要 Pipe、Socket、共享内存、消息队列、Redis 或 Kafka 等 IPC。线程共享同一进程的堆、全局变量、文件描述符和连接对象，因此会出现竞态条件，需要锁、信号量、原子操作或消息传递。

## 2. 同步/异步与并发/并行是两组不同的概念

- **同步/异步**：等待一个依赖结果期间，当前执行单元能否推进其他工作。
- **并发（concurrency）**：多个任务在一段时间内交错推进；单核也能实现。
- **并行（parallelism）**：多个任务在不同 CPU 核上真正同时执行；通常需要多线程、多进程或运行时调度到多核。

```text
单线程同步：A 等 I/O ──闲置──→ B 等 I/O
单线程异步：A 等 I/O → 运行 B → B 等 I/O → 运行 C
多核并行：  Core 1 运行 A，同时 Core 2 运行 B
```

因此 `async != 多线程 != 多核并行`。异步的关键收益是把**等待时间重叠**，而不是让某个外部数据库或 API 自身变快。

## 3. CPU 密集与 I/O 密集决定优化手段

判断口诀：任务慢的时候，CPU 是在算，还是在等？

| 类型 | 主要耗时 | 常见例子 | 优先手段 |
| --- | --- | --- | --- |
| CPU 密集 | 本机 CPU 真正在计算 | 图片/视频编码、加密、排序、矩阵计算、本地模型推理 | 算法优化、多核进程、原生实现、GPU |
| I/O 密集 | 等数据库、网络、磁盘或外部服务 | MySQL/Redis、HTTP、LLM API、文件、Kafka、Socket | 原生异步 I/O、并发控制、连接池、超时与背压 |

把 CPU 密集函数放进 `async def` 不会自动加速：没有真正的挂起点时，它会占住事件循环线程。对纯 Python CPU 工作，线程也常受 GIL 限制；应评估进程池或独立 worker。相反，调用远程 LLM API 时，本服务大部分时间是在等网络和对端推理，`await` 很适合避免线程空等。

## 4. 异步如何影响服务容量与 RPS

异步不会增加客户端向服务器发送请求的速度；它改善的是服务器的**并发处理能力**，并可能在 I/O 密集场景显著提高完成吞吐量（RPS）。

假设每个请求需 10 ms CPU 处理和 90 ms 数据库等待：

```text
单线程同步：每个请求约 100 ms → 理想上约 10 RPS
单线程异步：等待期间可处理其他请求 → 上限更接近 CPU 的 10 ms 部分
```

这只是容量直觉，不是可承诺的实际数字。真实瓶颈还包括 CPU、连接池、数据库/上游 API 配额、网络、内存、序列化、队列长度、限流与框架开销。异步服务也必须设置并发上限和背压；无限创建协程会把等待从线程池转移到连接池、内存或下游服务。

同步 worker 模型在 I/O 等待时会长期占住有限工作线程；异步模型可由少量线程维护大量等待中的协程。若请求主体变成 CPU 密集，二者都受 CPU 核数限制，异步切换反而可能增加少量开销。

## 5. FastAPI/Agent 的落地判断

```python
async def research() -> str:
    search = await search_web()       # I/O：适合 await
    profile = await query_database()  # I/O：适合 await
    return await call_llm(search, profile)  # I/O：适合 await


async def bad_handler() -> int:
    return expensive_local_compute()  # CPU：仍会阻塞事件循环
```

对后者可选择进程池或可靠的队列 worker；对暂时无法替换的短时同步 I/O，可谨慎使用 `asyncio.to_thread()`，同时确认线程安全、取消语义和线程池容量。关于 `await` 如何挂起、Future 如何唤醒 Task，见 [async、await 与协程调度](07_async、await_与协程调度.md)。

## 6. 常见误区与复习问题

- **协程一多就能并行**：协程提升 I/O 并发，不自动获得多核计算能力。
- **`async def` 内一定不会阻塞**：同步 SDK、同步文件/数据库操作和 CPU 循环都能阻塞事件循环。
- **异步会让请求本身更快**：它主要提高资源利用率和吞吐；单个请求的下游等待通常仍存在。
- **线程共享资源所以无需通信**：共享可变状态正是竞态、死锁与线程安全问题的来源。

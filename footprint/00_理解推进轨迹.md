# 00 理解推进轨迹

本文件保留你在讨论中的核心理解推进，按主题压缩整理。

## 1. Transformer / LLM

- 起点：你把 Q/K/V 理解为“关注什么、提供什么、具体信息值”。
- 修正：Q 更像当前 token 发出的查询，K 是其它 token 可匹配的索引，V 是被加权聚合的信息内容。
- 推进：进一步区分 Encoder、Decoder、Decoder-only、Causal Mask、Cross Attention 与 RAG Embedding 的不同用途。

## 2. Agent / ReAct / Reflection / Memory

- 起点：你将 Agent 理解为 LLM 端到端完成任务。
- 推进：你逐步区分了 ReAct、Plan-and-Execute、Multi-Agent、Reflection、Memory、IterResearch。
- 修正：ReAct 不是所有 Agent 的统称；Reflection 不是重新回答，而是基于执行轨迹复盘；长期记忆不是简单保存聊天记录，而是结构化检索和筛选。
- 已补充：Generative Agents 文件包含 memory stream、relevance/recency/importance 检索、reflection 和 insight 写回。

## 3. Python / FastAPI / 异步

- 起点：你理解 async 只是把函数变成异步函数。
- 推进：进一步明确 await 才是让出控制权的关键；UploadFile 与 bytes 的区别在于内存占用和流式处理；上下文管理器的 yield 只有进入/消费时才执行。
- 新连接：Go 异步讨论帮助你把 Python async/await 与 Go goroutine 模型进行对比。
- 基础输入补充：从 `sys.stdin` 逐行文本推进到 `split()` 的空白折叠、`map` 的惰性转换和 `range(start, stop, step)` 的半开区间语义。

## 4. Go / Gin / Context / 并发

- 起点：你通过 Gin Handler、BasicAuth、Session、闭包注入理解后端接口。
- 推进：进一步理解 Context 取消、超时、WithValue、闭包、逃逸分析、GC、mcache/mcentral/mheap 等运行时机制。
- 今日新增 1：围绕 goroutine 数量与性能，理解 Go 的轻量并发不是无限并发，必须考虑调度成本、CPU 核数、下游资源和 goroutine 泄露。
- 今日新增 2：通过 channel 关闭、只读 channel、select default、关闭 channel 后无限循环等问题，理解 channel 的关闭语义和“读就绪”。
- 今日新增 3：从 `sync.Mutex.Lock()` 与 `TryLock()` 推进到悲观锁、乐观锁、CAS 和数据库 version 字段的并发控制模型。
- 今日新增 4：把 Python async/await 与 Go 的 goroutine/channel/select/context 进行对比，明确 Go 没有 async 关键字，但有完整的运行时并发机制。

## 5. 数据库 / Redis

- 起点：你询问 Redis 时间存储、HyperLogLog、SQLite、索引等概念。
- 推进：逐步形成 SQL、MongoDB、Redis、向量库分工意识，并理解 Redis Cluster、Sentinel、复制、IO Threads、限流与临时状态映射。
- 新连接：乐观锁/悲观锁知识可以延伸到数据库事务、version 字段、Redis Lua 原子扣减和分布式状态控制。

## 6. 消息队列 / Kafka / RabbitMQ

- 起点：你从“消息分发是什么”开始，先理解生产者、队列、消费者、消费组这些基本角色。
- 推进 1：你明确 Kafka 的 offset 属于 partition，不同 consumer group 对同一 topic 有各自独立 offset；同一 group 内同一 partition 通常只由一个 consumer 处理。
- 推进 2：你进一步追问“一条消息会不会被多个 consumer 处理”，最终形成判断：不同 group 会各自处理；同一 group 正常不并发重复，但崩溃、rebalance、offset 未提交会导致重复处理。
- 推进 3：你把 consumer 业务失败与 consumer 断连区分开：断连由 group coordinator 和 offset 恢复处理；业务失败需要 consumer 端主动设计 retry topic、DLQ 和幂等。
- 推进 4：你追问 leader broker 挂掉后的机制，进一步区分了 partition leader/follower、ISR、KRaft controller 元数据管理、follower fetch 进度和新 leader 从 ISR 选举。
- 推进 5：补充 key 与热分区后，你把 partition 理解为顺序性、并行度和负载均衡的共同边界。
- RabbitMQ 方向：你已理解 vhost、exchange、queue、binding、routing key/binding key 共同决定业务消息路由。

## 7. 后端部署 / 网络 / 可观测性

- 起点：你从 Docker Desktop、Compose、DNS、代理、SSE 等具体问题切入。
- 推进：逐步形成服务运行时视角：请求进入服务，经由应用层、数据层、异步层、部署层和监控层共同完成稳定运行。


## 8. RPC / 服务治理

- 起点：你把 RPC 总结为“客户端代理接收调用请求并编码/组包，发送给服务端代理；服务端代理解码/解包后调用真实服务，结果再反向返回”。
- 今日新增 1：动态代理与字节码生成解释了“客户端代理从哪里来”。动态代理是在运行时生成代理对象并拦截接口方法；字节码生成则可以直接生成代理类，提高执行效率并减少反射样板。
- 今日新增 2：心跳与服务注册解释了“客户端代理如何知道服务端在哪里、服务是否还活着”。服务启动时注册实例，运行中周期性心跳续约，注册中心根据 TTL 或健康检查维护可用实例列表。
- 最终连接：RPC 主调用链解决“怎么调用”；动态代理解决“如何让调用看起来像本地方法”；服务注册、心跳和服务发现解决“调用谁、谁可用”。

## v8 今日新增：Go Protobuf / go_package / import 路径

- 起点：你从 `.proto` 中的 `option xxx` 问起，想弄清楚它到底改变什么。
- 推进：你遇到 `protoc-gen-go: unable to determine Go import path`，由此明确 Go 插件必须知道生成代码的 Go import path。
- 关键修正：`package msg;` 是 protobuf 命名空间，`option go_package = "rpc-learn/proto;msg"` 才是 Go 代码生成的导入路径与包名配置。
- 工程化深化：你把 `go.mod module rpc-learn`、生成目录、`main.go import msg "rpc-learn/proto"` 放在一起比较，意识到 Go import 按 module path + 真实目录查找包，而不是按 `.pb.go` 文件名查找。
- 报错归纳：`inconsistent names` 来自同一 Go import path 下生成包名不一致；`command-line-arguments is not a main package` 来自被运行文件不是 `package main` 或缺少 `func main`。


## v9：昨日与今日新增知识推进

### Go 接口、方法集与 gRPC 注册

- 你的问题从“指针接收器实现接口时结构体是否算实现接口”开始，推进到 Go 方法集规则：值接收器方法同时属于 `T` 和 `*T`，指针接收器方法通常只属于 `*T`。
- 随后你把该规则放入 gRPC 生成代码中理解：`RegisterTradeServer` 接收接口，`new(Trade)` 返回 `*Trade`，能否传入取决于 `*Trade` 是否实现生成的 `TradeServer` 接口。
- 你进一步理解了 `UnimplementedTradeServer` 的作用：它不是业务实现，而是为了未实现方法兜底和 proto 演进兼容。

### RabbitMQ 延时、TTL、惰性队列与 Federation

- 你先总结 TTL + 死信队列实现延时消息，随后修正为“过期消息进入死信交换机，再路由到死信队列”。
- 你追问不同 TTL 消息是否需要每条一个计时器，推动出“过期检测不等于独立计时器”以及普通 FIFO 队列的队头阻塞问题。
- 你对惰性队列的理解从“消息尽可能落盘”推进到“消息主体磁盘化，内存保留索引、队列位置、投递状态和 unacked 集合”。
- 你把 Redis 惰性删除与 RabbitMQ TTL 检测联系起来，形成了“过期不一定准时物理删除/触发，而是在访问、扫描或调度点判断”的跨系统理解。
- 你询问 Federation exchange / queue 解决什么问题，最终区分出：联邦交换机偏事件转播，联邦队列偏跨 broker 队列拉取，二者都不是强一致集群。

## v10：Embedding、RAG 查询增强、评估与推理范式

### Embedding 表示与检索

- 你先把 Embedding 理解为把文本转成一个向量，随后进一步区分稠密、稀疏和多向量表示。
- 关键修正：稀疏向量不是“维度较少”，而是维度高但非零元素少；多向量不是简单增大 hidden size，而是一个查询或文档保留多个局部向量。
- 你通过倒排索引明确了 sparse retrieval 的物理基础：从词项映射到 postings list，并由 BM25 等方法完成相关性排序。
- 最终连接：Dense 负责语义，Sparse 负责术语和精确匹配，Multi-Vector 负责局部细粒度匹配，三者可在 RAG 中混合召回。

### Query Rewrite、HyDE 与 Multi-Query

- 起点：你观察到三者都在检索前改变输入，因此追问它们的区别。
- 修正：Query Rewrite 生成一个更清晰、自包含的问题；HyDE 生成一段假设文档并只将其作为向量检索桥梁；Multi-Query 生成多个检索视角以扩大覆盖。
- 关键边界：HyDE 文本不是事实来源；Multi-Query 结果必须融合、去重并以原始问题统一重排；Query Rewrite 不能引入用户未提供的事实假设。
- 最终连接：三者分别解决上下文缺失、query-document 表达差距和单一查询覆盖不足，是否启用必须通过 Recall@K 等指标验证。

### RAGAS 与 Ground Truth

- 你能理解 question、retrieved contexts 和 answer 来自被测 RAG 流程，但进一步追问“标准答案从哪里来”。
- 核心澄清：Ground Truth/Reference 通常在评估前由专家、人工标注、已有数据集、历史审核答案或“LLM 合成 + 人工审核”准备，不应直接复制被测系统输出。
- 你进一步区分：Faithfulness 重点检查 Answer 是否被 Context 支持；Context Recall 更依赖 Reference 中应覆盖的必要事实；并非所有指标都强制依赖标准答案。

### Extended Thinking 与 ReAct

- 你的初始判断是：Extended Thinking 是否把 ReAct 中显式的 Thought 内化到模型内部。
- 保留的正确部分：模型确实可以在单次调用内部完成更多任务分解、方案比较和自检。
- 关键修正：ReAct 的核心是 Thought/Decision 与真实 Action、Observation 之间的外部闭环；内部推理不能替代搜索、数据库和代码执行带来的新信息。
- 最终理解：Extended Thinking 增强每一轮“怎么想”，ReAct 规定多轮“怎么行动、观察和继续”，两者可以组合。

## 2026-07-21：Claude Code Prompt Cache 与流式恢复专题

### Prompt 前缀缓存

- 起点：把 Claude Code 的 System prompt、Project context、Conversation 理解为三个独立缓存层。
- 关键修正：三者首先是按稳定性排列的上下文层，底层依赖从请求开头开始的精确前缀匹配，并不存在任意片段分别命中的保证。
- 原理追问：你进一步追问后续内容是否会改变旧 token 的注意力计算。
- 最终理解：因果注意力禁止旧 token 看见未来 token，因此追加内容不会改变旧前缀的隐藏状态和 K/V；新 token 则会用自己的 Query 注意旧前缀。

### 流式输出上限与恢复

- 起点：一度混淆 Context window 总空间与单次响应的 max output tokens。
- 关键修正：服务端逐 token 计数并执行 `max_tokens`；网络 chunk 只是传输分片，Claude Code 不靠累计 chunk 数量判断触顶。
- 协议推进：`message_delta` 携带整条响应的 `stop_reason` 和最终 usage，`message_stop` 表示事件流正式结束。
- 恢复机制：首次触顶且允许扩容时，从原输入重新生成；扩容后仍触顶，则保留截断内容并追加内部恢复消息，用新一次调用的输出预算从断点继续。
- 最终连接：Claude Code 把流式协议事件转化为 Agent Loop 的状态迁移，并用 Prompt Cache 降低相同前缀重试或续写时的重复输入计算成本。

## 2026-07-25：Claude Code 检索、缓存命中与上下文压缩

### ripgrep 与 grep

- 起点：两者都被理解为按行搜索文本的命令。
- 关键推进：`rg` 面向代码仓库默认递归，并主动遵循 ignore、隐藏文件和二进制过滤；优势不仅是更快，也在于减少送入 Agent 上下文的噪声。
- 边界修正：`grep` 在 Shell 管道、精简服务器和可移植脚本中仍然更普遍；`rg` 搜不到时应先检查过滤规则，而不是直接认定内容不存在。

### Prompt Cache 命中

- 深化：缓存对象按 `tools → system → messages` 组成完整前缀，断点不是只缓存所在 block。
- 查找机制：缓存只在断点写入；读取时最多向前检查 20 个 content block，并寻找此前真正写入过的前缀项。
- 可观测性：通过 `cache_creation_input_tokens` 与 `cache_read_input_tokens` 区分创建、命中和未实际缓存，不能只凭响应速度判断。

### Microcompact 与全量压缩

- 起点：把旧工具结果的占位符理解为新生成的简短元数据摘要。
- 关键修正：所讨论版本只替换 `tool_result.content`；工具名和参数来自保留下来的 `tool_use`，占位符本身不包含摘要。
- 进一步区分：Microcompact 清理原始载荷，全量 Compact 总结旧消息语义；压缩后规则、最近文件、异步任务和 Skills 等从磁盘或运行时状态重新恢复。
- 状态来源：摘要回答“发生过什么”，附件与重注入回答“现在是什么状态”；最近文件的当前内容来自重新读取磁盘，不一定等于压缩前看到的版本。
- 缓存连接：摘要请求若要共享主会话 Prompt Cache，就要尽量保持模型、system、tools 和 thinking 配置一致；单独设置较低输出上限可能间接改变 thinking 配置，所以特定版本把 20K 硬上限留给无法共享完整前缀的回退路径。

## 2026-07-26：Claude Code Subagent、Agent Teams 与状态机

### Subagent 通信与隔离

- 起点：把 Subagent 的最终回复统一理解为“XML 包装后的用户消息”。
- 关键修正：前台结果首先是 `Agent` 工具的结构化 `tool_result`；后台任务先返回 `async_launched`，完成后再产生 `task_notification`。Claude API 用 `user` role 承载客户端工具结果，并不表示消息来自真实用户。
- XML 边界：特定版本内部 transcript 会使用 `<task-notification>`，但 Agent SDK 已提供 `SDKTaskNotificationMessage` 和 `origin.kind = "task-notification"`，集成代码应依赖结构化字段而非内部 XML 文本。
- 隔离推进：普通 Subagent 有独立上下文、system prompt 和 transcript，但默认共享主会话 checkout；只有显式 `isolation: worktree` 才建立代码目录隔离。

### 后台执行、恢复与状态判断

- 起点：把长时间任务理解为执行到一定时长后自动升级成后台 Subagent。
- 关键修正：前台/后台是主会话是否等待结果的调度选择，没有公开的按耗时切换阈值；当前版本默认偏向后台，主 Agent 立即依赖结果时仍可前台执行。
- 恢复价值：主 Agent 只获得压缩后的最终报告，旧 Subagent transcript 仍保留完整工具调用和结果；高上下文重合的追问适合按 `agentId` 恢复，独立复核和新领域更适合新建。
- 状态来源：主 Agent 依赖运行时任务注册表、`task_updated` 和 `task_notification` 等结构化事件，而不是扫描自然语言回复猜测。

### Agent Teams 与 Coordinator Mode

- 起点：把 Agent Teams 理解为没有主从关系的若干完全平级 Agent。
- 关键修正：官方架构有生命周期内固定的 Team Lead；Teammate 虽能直接通信、自领任务和维持独立上下文，但团队管理、生成 Teammate 和最终综合仍具有明确的权力不对称。
- 通道区分：Team mailbox 和共享 task list 属于 Agent Teams；当前普通 Subagent 也支持 `SendMessage` 中途修正和完成后恢复，但依赖 Agent ID 与独立 transcript，不等于写入 Team mailbox。
- 模式对比：Agent Teams 是公开实验功能，强调 Lead、Teammate、直接消息和共享任务；内部 Coordinator Mode 受 feature gate 与环境变量共同控制，使用严格中心化 Coordinator/Worker 拓扑，其具体 prompt、工具白名单和阶段属于版本相关实现。
- 状态机连接：状态机由状态、事件、合法迁移和副作用组成。Team task 的 `pending → in_progress → completed` 与 Teammate 的 `working ⇄ idle → shutdown` 是两套状态，任务完成不等于 Teammate 退出。

## 2026-07-26：六篇 Claude Code 源码博客体系化核验

### Agent Loop 与 ReAct

- 起点：把 Claude Code 简单概括为“没有 ReAct，只有 `while(true)` 的 Tool-Use Loop”。
- 关键修正：Claude Code 不依赖经典 ReAct 的自由文本 `Thought/Action/Observation` 解析格式，但广义上仍通过工具形成“决策—行动—观察—再决策”闭环。
- 协议连接：`tool_use` 给出工具名和参数，`stop_reason=tool_use` 表示等待客户端结果，`tool_result` 通过 ID 回填；没有工具调用只是正常退出路径之一。
- 实现边界：`ask → QueryEngine → query → queryLoop`、`needsFollowUp`、`StreamingToolExecutor` 等来自特定构建还原，不是当前公开 SDK 契约。

### 精确代码检索与 RAG

- 起点：把博客标题理解为 Claude Code 直接运行 POSIX `grep`，并据此认为代码 Agent 不需要 RAG。
- 关键修正：当前官方 Tools Reference 明确说明 Grep 工具基于 ripgrep，并与 Glob、Read、LSP 和多轮查询改写共同形成检索闭环。
- 场景边界：单仓实时精确搜索优先使用本地权威工具；跨仓库、模糊语义、代码与文档联合检索可增加混合 RAG、重排与回源验证。
- 最终理解：模型更强会改善工具选择和检索迭代，不会消除外部信息获取与证据验证。

### 当前 Memory 体系

- 起点：把“四种类型、后台抽取 Agent、Sonnet top-5、两天 stale”当作 Claude Code 当前稳定记忆架构。
- 关键修正：当前官方文档保证的是多作用域 `CLAUDE.md`/Rules 与 Auto memory；`MEMORY.md` 前 200 行或 25KB 在启动时加载，详细主题文件按需读取。

- 处理原则：出现冲突时按 A → B → C → D 排序，所有精确常量和内部函数都要附版本边界。

## 2026-07-29：Claude Code Skills、LSP 与 Python 基础输入

### Skills 发现与调用控制

- 起点：担心 Skill 数量过多时，即使每项描述都被截短，总元数据仍超过上下文预算。
- 机制推进：单项描述上限和总 listing 预算是两层约束；总预算溢出时，低使用频率 Skill 的描述先被移除，但名称仍保留。
- 关键修正：当前默认单项上限是 1,536 字符，当前配置名是 `skillListingMaxDescChars`，不是 `maxSkillDescriptionChars`。
- 硬软边界：`disable-model-invocation` 与 `user-invocable` 由 Claude Code 宿主解析；描述匹配和正文执行才依赖模型理解。
- 安全深化：禁止 Skill 自动调用不等于禁止底层副作用；`allowed-tools` 是预授权而非白名单，高风险操作仍需权限 deny、`disallowed-tools`、PreToolUse Hook 和基础设施权限。

### LSP 与语言服务器

- 起点：把 LSP、语言服务器和更高级的代码搜索混在一起理解。
- 关键区分：LSP 是编辑器/Agent 与语言服务器通信的 JSON-RPC 协议；`gopls`、`clangd`、Pyright 等是具体实现。
- 能力边界：grep/ripgrep 回答字符模式出现在哪里；语言服务器利用 AST、作用域、类型和符号索引回答定义、引用、诊断和重命名。
- 最终连接：代码 Agent 通常先用文本检索召回，再用 LSP 消歧，最后以编译和测试验证；反射和动态加载等关系仍需要文本搜索或运行时证据补充。

### Python 标准输入与序列

- 起点：从 `for line in sys.stdin` 为什么能读输入、`list(map(int, nums))` 为什么得到整数列表开始。
- 关键修正：`split(" ")` 严格按单个空格切分，`split()` 才会折叠连续空白；`map` 在 Python 3 中返回惰性迭代器。
- 边界推进：`range(x, -1, -1)` 只有在 `x >= 0` 时才从 `x` 倒序包含到 `0`，因为 `stop=-1` 本身不包含。

# 流量削峰、异步解耦与最终一致性

> 所属分类：Message Queue / Kafka / RabbitMQ  
> 修订版本：v9 昨日今日增量版  
> 质量要求：本文件只解释本知识点，不复用其他知识点的原理段；示例尽量给出代码、伪代码、命令或配置。

## 1. 总体性概念

流量削峰把瞬时高峰写入队列，由消费者按稳定速率处理；异步解耦降低上下游直接依赖，但引入最终一致性。


## 2. 原理性解释

- MQ 缓冲峰值，不减少总工作量。
- 上游可快速返回已受理。
- 下游按能力消费。
- 需要幂等、重试、死信和状态查询。

### 流量削峰是用队列吸收瞬时峰值，而不是让请求消失

当短时间请求量超过下游处理能力时，消息队列可以把请求转化为待处理消息，由消费者按稳定速率处理。它降低了瞬时压力，但会增加延迟，并要求业务接受最终一致性。

例如下单后先写订单状态“处理中”，再把扣库存、发券、通知等动作异步化。用户不一定马上看到所有结果，但系统不会被峰值打垮。

## 3. 机制流程

1. 请求高峰。
2. 写入队列。
3. 立即返回。
4. 消费者慢慢处理。
5. 最终状态落库。

### 削峰流程

```text
突发请求
  ↓
快速校验并写入 MQ
  ↓
消费者按固定并发处理
  ↓
处理结果更新数据库
  ↓
失败重试 / 死信队列 / 人工补偿
```

关键工程点：消费者幂等、消息去重、状态机设计、重试退避、死信报警。否则异步化会把错误藏到后台。

## 4. 类比理解

像餐厅取号排队，厨房按能力做菜。

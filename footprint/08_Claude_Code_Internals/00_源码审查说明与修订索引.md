# Claude Code Internals：源码审查说明与修订索引

审查日期：2026-08-15

## 结论先行

这套笔记不能把当前 `D:\codes\claude-code` 当作 Claude Code CLI/harness 的完整开源实现。该仓库公开的是安装说明、发行记录、官方插件、示例和少量维护脚本；`README.md` 只承诺插件目录，`.claude-plugin/marketplace.json` 列出的也是插件清单。仓库中不存在 CLI 的请求组装、模型调用、上下文压缩、任务调度或会话恢复源码。

因此，原笔记中“源码证明”的说法需要分层：

1. **仓库代码事实**：只能用于说明插件、命令、skill、agent 定义和 hook 的可观察实现。
2. **官方公开契约**：以 Claude Code / Claude API / Agent SDK 文档为准，可用于说明当前产品行为，但不等同于内部实现。
3. **第三方文章、source-map 或二进制还原**：只能作为某一构建的观察线索，必须写明版本和验证日期；不可推出稳定函数名、环境变量、常量或状态机。
4. **harness 设计建议**：应清楚写成推荐设计或伪代码，不得反向表述为 Claude Code 已实现的事实。

## 当前仓库实际能教什么

这不是“没有可学代码”的仓库，而是一个很好的**可扩展性层**样本：

```text
Markdown / YAML 定义（commands、agents、skills）
                    │ 由宿主发现、渲染、路由
                    ▼
模型提出工具调用 ──► 宿主权限与 Hook ──► 外部副作用
                    │                      │
                    └──── 结构化结果/反馈 ──┘
```

- `plugins/pr-review-toolkit/agents/code-reviewer.md`：agent 的主体是角色、边界、输出格式和置信度门槛，而非一个“自动执行的 agent 程序”。
- `plugins/hookify/hooks/pretooluse.py` 与 `plugins/hookify/core/rule_engine.py`：可验证的 hook 输入读取、规则匹配、结构化拒绝和“阻断优先于警告”的实现；它是插件自身策略，不应误认为 Claude Code 内核。
- `plugins/security-guidance/hooks/security_reminder_hook.py`：展示确定性模式检查与 Stop 阶段 LLM 审查的两层防护，以及如何保存会话级 diff 基线。它是官方随仓库发布的一个插件实现，仍不是宿主的内置安全机制。
- `.claude-plugin/marketplace.json`：插件发现与分发的 manifest 层，而不是工具调度器或上下文管理器。

对 agent/harness 开发者，最值得从代码提炼的流程是：**声明能力 → 宿主控制可见性/权限 → 对输入做确定性校验 → 执行副作用 → 回填结构化结果 → 以 Hook 或评估闭环纠错**。模型负责语义决策；可被绕过或必须确定执行的约束，应落到权限、Hook、沙箱/IAM 和工具实现，而非 Markdown 提示词。

## 从“背内部细节”改为“做可验证学习”

每条结论都附三项：**证据 URL/仓库路径、适用版本或日期、反例/失效条件**。对于没有公开源代码的 CLI 内部流程，优先写以下模板：

> 官方契约是 X；我们无法从公开源码确定 Y；在版本 Z 的观测中出现了 W，因此把 W 作为调试假设，升级或换模型后需重新实测。

建议的实践顺序：

1. 用本仓库的 `hookify` 写一个只读 PreToolUse 规则，验证 JSON 输入、匹配与拒绝路径。
2. 用 `pr-review-toolkit` 的 agent Markdown 复刻一个小型审查 agent，刻意区分“提示词约束”与“权限/Hook 的硬约束”。
3. 用 Agent SDK 的公开 `query()` 事件流实现自己的最小状态机；只依赖公开消息类型和 stop reason。
4. 为每个恢复分支设置上限、取消、幂等性和可观测日志；不要复制反编译出的私有函数名或常量。

# 附：技术问题讨论与知识整理原则

> 适用范围：后续技术问题讨论，以及把讨论记录整理进本知识库时的统一要求。

## 1. 回答定位

- 以 Agent、LLM 应用与互联网开发的工程视角回答技术问题；
- 优先解释当前问题本身，不一次性扩展过多旁支；
- 给出足以验证核心机制的真实代码、伪代码、命令或权威依据，不依靠猜测补全事实。

## 2. 证据优先级

回答涉及机制、接口、版本或性能结论时，优先采用：

1. 官方文档、标准规范与正式协议；
2. 原始论文、作者项目页与官方源码；
3. 可复现代码、测试结果与真实配置；
4. 高质量的二手技术资料。

二手资料与权威来源冲突时，以能够直接证明该结论的一手资料为准。来源只证明其实际覆盖的主张，不能用一个链接替整段内容背书。

## 3. 事实、不确定性与时效性

- 明确区分**已验证事实**、**基于证据的合理推断**和**暂时无法确认的内容**；
- 对可能随时间变化的版本、API、产品行为和最佳实践，先核对当前官方资料；
- 不能核实时直接说明边界，不把推测写成确定事实；
- 示例代码应与正文中的参数、数据结构和调用流程一致，并说明它是最小演示还是真实生产实现。

## 4. 内容组织与去重

- 一个 Markdown 文件聚焦一个可独立复习的知识点；
- 通用原理只保留一个权威版本，其他文件通过相对链接引用；
- 新讨论与现有主题重合时，补充原文件或建立交叉引用，不复制整段通用说明；
- 保留讨论中的概念修正、机制、缺陷、代码、对比和理解推进，删除的只应是逐字重复、页面按钮等无知识价值的网页噪声；
- 公式、代码和例子可以规范化排版，但不能因此删掉它们所表达的约束或边界。

## 5. 最小回答结构

根据问题复杂度选用以下部分，不强制每次全部展开：

1. 先给核心结论或纠正概念；
2. 解释机制与数据流；
3. 给出最小可验证示例；
4. 说明缺陷、适用边界和常见误区；
5. 列出直接支持关键结论的资料。

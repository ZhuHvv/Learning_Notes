## 1. 总体性概念

Redis 基本类型包括 String、Hash、List、Set、ZSet；时间通常用时间戳、TTL 或 ZSet score 表达，不是独立基本类型。


## 2. 原理性解释

- String 可做计数器和时间戳。
- Hash 适合对象字段。
- List 适合队列。
- Set 适合去重。
- ZSet 适合按分数排序。
- TTL 表达临时有效期。

### Redis 基本类型是围绕高频内存访问设计的

String 可做缓存、计数器、token；Hash 适合对象字段；List 适合队列；Set 适合去重集合；ZSet 适合排行榜和延迟队列。你问时间存储是不是基本类型：Redis 没有专门的时间类型，通常用 String/Hash 存时间戳，或用 TTL 表达过期时间。

```bash
SET session:123 userA EX 3600
HSET user:1 name Tom last_login 1710000000
```

## 3. 机制流程

1. 选择数据结构。
2. 设计 key。
3. 写入并设置 TTL。
4. 读取时处理过期。

### Redis 读写流程

```text
客户端命令
  ↓
事件循环读取请求
  ↓
执行内存数据结构操作
  ↓
可选 AOF/RDB 持久化
  ↓
返回响应
```

Redis 快不代表可以无限存。要关注 key 数量、value 大小、过期策略、内存淘汰策略和热 key。

## 4. 类比理解

Redis 像高速便签板，TTL 像便签自动过期时间。

## 10. 更细的工程拆解

**Redis 基本数据类型与时间存储** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `Redis 基本数据类型与时间存储` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **Redis 基本数据类型与时间存储** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

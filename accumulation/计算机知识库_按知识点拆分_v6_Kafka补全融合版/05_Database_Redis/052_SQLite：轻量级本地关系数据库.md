## 1. 总体性概念

SQLite 是嵌入式关系数据库，不需要独立服务，数据存在本地文件。


## 2. 原理性解释

- 支持 SQL、事务、索引。
- 部署简单，适合本地、小型、测试。
- 并发写能力有限。
- 不适合高并发核心生产服务。

### SQLite 是嵌入式关系数据库，不是服务端数据库

SQLite 把整个数据库存成一个本地文件，应用进程直接链接库读写，不需要独立数据库服务。它非常适合本地工具、桌面应用、测试环境、小型单机服务，但不适合高并发写入的中心化后端。

```python
conn = sqlite3.connect("app.db")
conn.execute("CREATE TABLE IF NOT EXISTS users(id INTEGER PRIMARY KEY, name TEXT)")
```

## 3. 机制流程

1. 打开 db 文件。
2. 建表。
3. 读写。
4. 提交事务。

### SQLite 使用流程

```text
打开本地 db 文件
  ↓
执行 SQL
  ↓
事务提交
  ↓
关闭连接
```

如果项目后续要迁移到 MySQL/PostgreSQL，SQL 写法和类型系统要提前注意差异，避免过度依赖 SQLite 特性。

## 10. 更细的工程拆解

**SQLite：轻量级本地关系数据库** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `SQLite：轻量级本地关系数据库` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **SQLite：轻量级本地关系数据库** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

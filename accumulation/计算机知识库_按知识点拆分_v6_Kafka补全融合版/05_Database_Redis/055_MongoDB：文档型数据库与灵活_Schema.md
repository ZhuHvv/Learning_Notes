## 1. 总体性概念

MongoDB 用文档存储半结构化数据，schema 灵活但仍需要应用层建模。


## 2. 原理性解释

- 文档类似 JSON，可嵌套。
- 灵活 schema 不等于无约束。
- 适合整体读取和字段变化快场景。
- 高频查询字段仍需索引。

### MongoDB 的文档模型适合“聚合对象”

MongoDB 用 BSON 文档存储数据，一个文档可以包含嵌套对象和数组。它适合结构灵活、以对象整体读写为主的场景，例如用户配置、日志事件、内容草稿。它不适合需要大量跨集合 JOIN 和强事务复杂关系的核心账务场景。

```json
{"user_id": 1, "profile": {"name": "Tom"}, "tags": ["ai", "go"]}
```

## 3. 机制流程

1. 设计 collection。
2. 插入文档。
3. 建立索引。
4. 查询/更新。

### MongoDB 设计流程

```text
从查询模式出发
  ↓
决定哪些字段嵌入，哪些字段引用
  ↓
建立索引
  ↓
控制文档大小和数组增长
  ↓
必要时使用聚合管道
```

文档数据库不是“不需要 schema”，而是 schema 从数据库强约束转移到了应用设计和数据治理中。

## 10. 更细的工程拆解

**MongoDB：文档型数据库与灵活 Schema** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `MongoDB：文档型数据库与灵活 Schema` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **MongoDB：文档型数据库与灵活 Schema** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

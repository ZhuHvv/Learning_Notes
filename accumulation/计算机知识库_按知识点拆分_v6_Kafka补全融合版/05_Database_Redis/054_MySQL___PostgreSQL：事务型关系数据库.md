## 1. 总体性概念

MySQL/PostgreSQL 是事务型关系数据库，适合结构化核心数据、约束、事务和复杂查询。


## 2. 原理性解释

- schema 约束数据结构。
- ACID 事务保证一致性。
- 索引提升读但增加写成本。
- 参数化 SQL 防注入。
- 连接池影响并发能力。

### MySQL/PostgreSQL 的核心价值是事务和可靠持久化

关系型数据库通过表结构、约束、索引和事务保证数据一致性。MySQL/InnoDB 常用于互联网业务；PostgreSQL 在复杂 SQL、扩展能力、JSON/地理信息等方面强。二者都不是简单“存表格”，而是承担业务事实的权威存储。

ACID 中最容易被忽视的是隔离性：并发事务如果隔离级别不合适，会出现脏读、不可重复读、幻读等问题。

## 3. 机制流程

1. handler 接收请求。
2. service 开事务。
3. repo 执行 SQL。
4. 提交/回滚。

### 一次事务流程

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

应用层要处理事务失败、死锁重试、连接池超时和慢查询；不要把长时间外部 RPC 放在数据库事务里，否则会拖长锁持有时间。

## 10. 更细的工程拆解

**MySQL   PostgreSQL：事务型关系数据库** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `MySQL   PostgreSQL：事务型关系数据库` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **MySQL   PostgreSQL：事务型关系数据库** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

# B+树索引、复合索引与最左前缀

> 所属分类：Database / Redis / Vector DB  
> 修订版本：v6 Kafka 补全融合版  
> 质量要求：本文件只解释本知识点，不复用其他知识点的原理段；示例尽量给出代码、伪代码、命令或配置。

## 1. 总体性概念

B+树索引按有序树结构加速查询；复合索引按字段顺序排序，遵循最左前缀原则。


## 2. 原理性解释

- 叶子节点有序并适合范围扫描。
- 复合索引 `(a,b,c)` 先按 a 再按 b 再按 c。
- 缺少最左字段通常难以高效定位。
- 范围条件后的字段定位能力下降。

### B+ 树索引的优势来自“有序 + 扇出高 + 叶子链表”

B+ 树把真实数据指针主要放在叶子节点，非叶子节点只做导航，因此树高较低，磁盘 IO 次数少。叶子节点有序并通过链表连接，所以范围查询很高效。复合索引遵循最左前缀，是因为索引键按 `(a,b,c)` 的字典序排列，只有从左到右连续使用时才能有效缩小范围。

```sql
CREATE INDEX idx_user_age_city ON users(age, city);
```

查询 `WHERE age=18 AND city='HZ'` 能较好利用；只查 `city='HZ'` 通常不能充分利用该索引。

## 3. 机制流程

1. 建索引。
2. 优化器选择索引。
3. 定位叶子节点。
4. 范围扫描。
5. 必要时回表。

### 索引匹配流程

```text
WHERE 条件
  ↓
优化器判断可用索引
  ↓
按最左前缀定位 B+ 树范围
  ↓
扫描叶子节点
  ↓
必要时回表读取完整行
```

排查慢查询时要看 explain：是否走索引、扫描行数、是否回表、是否 filesort、是否索引选择性太低。

## 10. 更细的工程拆解

**B+树索引、复合索引与最左前缀** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `B+树索引、复合索引与最左前缀` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **B+树索引、复合索引与最左前缀** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

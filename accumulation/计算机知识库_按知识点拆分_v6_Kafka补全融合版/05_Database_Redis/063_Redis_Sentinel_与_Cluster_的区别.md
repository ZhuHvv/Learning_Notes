# Redis Sentinel 与 Cluster 的区别

> 所属分类：Database / Redis / Vector DB  
> 修订版本：v6 Kafka 补全融合版  
> 质量要求：本文件只解释本知识点，不复用其他知识点的原理段；示例尽量给出代码、伪代码、命令或配置。

## 1. 总体性概念

Sentinel 负责监控和主从故障转移；Cluster 负责分片扩展和高可用。Sentinel 不分片，Cluster 分片。


## 2. 原理性解释

- Sentinel 适合单主多从自动切换。
- Cluster 将数据分到多个 master。
- Sentinel 客户端发现当前 master。
- Cluster 客户端处理 slot 路由。

### Sentinel 管高可用，Cluster 管分片扩展

Sentinel 监控一主多从，主节点故障后选举新主，适合单分片高可用。Cluster 不仅能故障转移，还能把数据按 slot 分散到多个主节点，实现横向扩展。二者关注点不同，不应混为一谈。

```text
Sentinel: 1 个主分片 + 自动故障转移
Cluster: 多个主分片 + slot 路由 + 故障转移
```

## 3. 机制流程

1. Sentinel 监控 master。
2. 确认客观下线。
3. 选举并提升 replica。
4. 通知客户端。

### 选择流程

```text
数据量和吞吐单机可承受，只需要故障转移 → Sentinel
需要横向扩展容量/吞吐 → Cluster
只是本地缓存或开发环境 → 单机 Redis
```

Sentinel 模式下客户端要能感知主节点切换；Cluster 模式下客户端要支持 slot 路由和重定向。

## 4. 类比理解

Sentinel 是值班监控员，Cluster 是多分店体系。

## 5. 应用举例 / 代码或伪代码

```text
Sentinel: HA only, no sharding
Cluster: sharding + HA, 16384 slots
```

## 10. 更细的工程拆解

**Redis Sentinel 与 Cluster 的区别** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `Redis Sentinel 与 Cluster 的区别` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **Redis Sentinel 与 Cluster 的区别** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

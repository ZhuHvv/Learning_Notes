## 1. 总体性概念

SQL、MongoDB、Redis、向量库分别面向事务事实、灵活文档、高速临时状态、语义相似检索。


## 2. 原理性解释

- SQL 适合核心数据和事务。
- MongoDB 适合半结构化文档。
- Redis 适合缓存、会话、限流和临时映射。
- 向量库保存 embedding 和 metadata。
- 复杂系统常混用多种存储。

### 数据库选型要看数据模型、访问模式和一致性要求

SQL 适合强结构、事务和复杂查询；MongoDB 适合文档结构灵活、聚合对象自然存储；Redis 适合高性能缓存、会话、计数器、临时状态；向量库适合语义相似度检索。选型不是“谁更高级”，而是看读写模式和一致性边界。

例如 RAG 系统中，文档元数据可在 SQL/MongoDB，chunk embedding 在向量库，热门查询结果在 Redis，任务状态也可以在 Redis。

## 3. 机制流程

1. 识别数据形态。
2. 确定主存储。
3. 设计索引/缓存。
4. 设计一致性和过期策略。

### 选型决策流程

```text
是否需要事务和复杂 JOIN？→ SQL
数据结构是否经常变化且以文档整体读写？→ MongoDB
是否是短生命周期高频读写状态？→ Redis
是否按语义相似度召回？→ 向量库
```

真实系统常是组合使用，而不是只选一种数据库。

## 10. 更细的工程拆解

**数据库选型：SQL、MongoDB、Redis、向量库的分工** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `数据库选型：SQL、MongoDB、Redis、向量库的分工` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **数据库选型：SQL、MongoDB、Redis、向量库的分工** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。
- **Key / Index 设计**：是否能按最常用查询条件命中；是否存在大 key、热 key、无效索引。
- **一致性边界**：缓存与数据库是否可能不一致；MQ 重试是否可能重复写。
- **容量与过期**：临时状态是否有 TTL；统计结构是否能控制内存。

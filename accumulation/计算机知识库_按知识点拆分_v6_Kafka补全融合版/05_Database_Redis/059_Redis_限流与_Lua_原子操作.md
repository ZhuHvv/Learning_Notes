## 1. 总体性概念

Redis 限流常用计数器/ZSet/令牌桶；Lua 可把多命令组合为原子操作，避免并发竞态。


## 2. 原理性解释

- 固定窗口用 INCR + EXPIRE。
- 滑动窗口可用 ZSet。
- Lua 在 Redis 中原子执行。
- 脚本应短小避免阻塞。

### Lua 脚本让多条 Redis 命令具备原子性

限流常需要“读计数 → 判断 → 写计数/过期”多个步骤。如果客户端分多条命令执行，中间可能被其它请求插入，造成并发错误。Redis 执行 Lua 脚本时是原子的，脚本期间不会穿插其它命令，因此适合计数限流、库存扣减等小型原子逻辑。

```lua
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return current
```

## 3. 机制流程

1. 请求到达。
2. 计算 key。
3. Lua 增加计数并设置过期。
4. 判断是否允许。

### 固定窗口限流流程

```text
请求到达
  ↓
以用户ID+时间窗口构造 key
  ↓
Lua: INCR key，并在首次创建时 EXPIRE
  ↓
如果计数超过阈值 → 拒绝
否则 → 放行
```

Lua 不适合写复杂长耗时逻辑，因为 Redis 单线程执行命令，脚本过长会阻塞其它请求。

## 10. 更细的工程拆解

**Redis 限流与 Lua 原子操作** 要放到“数据读写路径”里理解：数据结构选择会直接影响查询复杂度、一致性和排障方式。

1. **数据模型**：先确定是关系型表、文档、KV、集合、流，还是向量。
2. **访问模式**：是按主键读、范围查、全文/向量检索、计数统计，还是临时状态更新。
3. **一致性要求**：是强一致事务，还是可接受最终一致、缓存延迟或近似统计。
4. **过期与回收**：缓存、会话、限流 key、临时映射都要设计 TTL 或清理机制。

### 最小数据访问伪代码

```python
def get_or_load(cache, db, key):
    value = cache.get(key)
    if value is not None:
        return value
    value = db.query_by_key(key)
    cache.set(key, value, ttl=300)     # 缓存必须带过期时间
    return value
```

### 工程落地要点

- 关系型数据库适合事务和复杂查询；Redis 适合高频状态、缓存、限流和临时映射。
- 索引不是越多越好，写入成本、锁竞争、内存占用都要一起考虑。
- 分布式场景下要明确：失败重试是否幂等，缓存失效是否会击穿，主从复制是否存在延迟。

## 11. 针对 `Redis 限流与 Lua 原子操作` 的专项排查

数据库与 Redis 的问题要从“访问模式”倒推设计。检查 **Redis 限流与 Lua 原子操作** 时：

- **读写比例**：高频读适合缓存，强事务写更适合关系型数据库。

## 1. 总体性概念

日志追加写入用于保留调试轨迹，尤其适合 Agent 的 Planning、Tool、Observation、Synthesis 阶段。


## 2. 原理性解释

- 追加模式 a 不覆盖旧日志。
- 日志应包含标题、时间、状态、结果和异常。
- 中文要指定 encoding。
- 异常路径也要写日志。

### 日志追加写入要同时考虑路径、刷新和异常分支

你之前的 `write_log("Planning", state, result)` 没输出，常见原因包括：函数没有被执行、异常发生在调用前、文件路径不是你以为的位置、写入后没有 flush、或者 JSON 解析失败后进入 except 分支没有记录原始 response。

```python
def write_log(title, *items, path="debug.log"):
    with open(path, "a", encoding="utf-8") as f:
        f.write(f"
{'='*10}{title}{'='*10}
")
        for item in items:
            f.write(pformat(item) + "
")
```

## 3. 机制流程

1. 封装 write_log。
2. 关键节点调用。
3. 异常时记录 traceback。
4. 按任务复盘。

### 调试日志建议流程

```text
LLM 原始响应写入 raw.log
  ↓
尝试 json.loads
  ├─ 成功：写入结构化 result
  └─ 失败：记录异常 + response 片段
  ↓
记录 state 快照和阶段名
```

日志要按阶段命名，例如 Planning、ToolCall、Observation、FinalAnswer，这样 Agent 出错时才能定位是哪一步。

## 10. 更细的工程拆解

**日志追加写入与调试输出** 在 Python 工程中通常关系到“运行时行为”而不是语法表面：

1. **生命周期**：对象、协程、文件流、上下文管理器分别什么时候创建、挂起、恢复、释放。
2. **阻塞点**：网络 IO、文件 IO、数据库查询、模型调用是异步服务最常见的等待来源。
3. **错误传播**：异常是直接抛出、被 task 包装，还是在日志中被吞掉，会决定排障难度。
4. **可观测性**：日志、trace id、结构化 JSON 输出能把一次请求的执行路径串起来。

### 最小调试骨架

```python
import asyncio
import logging

logging.basicConfig(filename="app.log", level=logging.INFO)

async def run_step(name, coro):
    logging.info("start step=%s", name)
    try:
        result = await coro
        logging.info("done step=%s result=%r", name, result)
        return result
    except Exception:
        logging.exception("failed step=%s", name)
        raise

# 用法：await run_step("retrieve", retriever(query))
```

### 工程落地要点

- 写 FastAPI/RAG/Agent 服务时，先明确哪些函数必须是 async，哪些只是普通 CPU 计算。
- 不要把大文件一次性读入内存，能流式就流式；不要在事件循环里跑长时间 CPU 任务。
- 对生成器、上下文管理器和 task，都要明确“谁负责消费、谁负责关闭、异常从哪里冒出”。

## 11. 针对 `日志追加写入与调试输出` 的专项排查

Python 服务中很多问题不是语法错，而是运行时行为与预期不一致。排查 **日志追加写入与调试输出** 时建议看：

- **是否真的被执行**：生成器、协程、上下文管理器经常只有在被消费/await/进入时才执行。
- **是否阻塞事件循环**：异步函数内部如果跑 CPU 密集循环，仍然会卡住其他请求。
- **异常是否被吞掉**：后台 task、日志函数、try/except 都可能让错误不再显式暴露。
- **资源是否关闭**：文件、数据库连接、上传流和 session 都需要明确生命周期。

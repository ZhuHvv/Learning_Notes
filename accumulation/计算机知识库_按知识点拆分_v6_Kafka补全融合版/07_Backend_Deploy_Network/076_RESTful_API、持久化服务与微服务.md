# RESTful API、持久化服务与微服务

> 所属分类：Backend / Deploy / Network

## 1. 总体性概念

RESTful API 用 HTTP 方法和资源路径表达操作；持久化服务保存业务状态；微服务是按边界独立部署的服务集合。


## 2. 原理性解释

- GET/POST/PUT/PATCH/DELETE 有语义区别。
- Handler 不应堆业务逻辑。
- Service 编排业务。
- Repository 访问存储。
- 微服务不是越拆越好。

### RESTful API 是围绕资源建模 HTTP 接口

REST 强调用 URI 表示资源，用 HTTP Method 表示动作：GET 查询、POST 创建、PUT/PATCH 更新、DELETE 删除。持久化服务则把业务状态落到数据库中，保证服务重启后数据不丢。微服务是在组织和部署层面拆分服务边界，不等于接口都写成 HTTP 就是微服务。

```text
GET /users/42
POST /orders
PATCH /orders/100/status
```

## 3. 机制流程

1. 请求到 API。
2. 中间件认证。
3. Handler 校验。
4. Service 调 DB/Redis/MQ。
5. 返回 JSON。

### 一次 API 请求流程

```text
Client → Gateway/Nginx → Service Router → Middleware → Handler
  ↓
参数校验 → 业务逻辑 → DB/Redis/MQ
  ↓
返回 JSON + 状态码
```

设计 API 时要统一错误码、幂等策略、分页、鉴权和 trace id，否则后期联调成本会很高。

## 4. 类比理解

API 是窗口，持久化层是档案室，微服务是不同科室。

## 10. 更细的工程拆解

**RESTful API、持久化服务与微服务** 需要放在“请求从客户端到服务再到下游依赖”的完整路径中看：

1. **入口层**：浏览器、客户端、代理、负载均衡、网关。
2. **服务层**：HTTP/RPC Handler、业务逻辑、连接池、缓存、数据库、MQ。
3. **运行层**：容器、Compose/Kubernetes、环境变量、挂载卷、网络策略。
4. **观测层**：日志、指标、trace、健康检查、告警。

### 最小部署/排障清单

```bash
# 1. 看容器是否运行
docker ps

# 2. 看端口是否监听
netstat -ano | findstr 9092

# 3. 看服务日志
docker logs <container>

# 4. 用 curl 验证入口
curl -v http://localhost:8080/health
```

### 工程落地要点

- 网络问题要分层排查：DNS、端口、代理、协议、认证、应用日志。
- Docker/Compose 里路径、端口、环境变量最容易出错，尤其 Windows 路径要注意冒号和绝对路径。
- 只要是线上服务，就必须有健康检查、结构化日志和关键指标，否则出错时只能猜。

## 11. 针对 `RESTful API、持久化服务与微服务` 的专项排查

后端部署和网络问题必须分层定位。检查 **RESTful API、持久化服务与微服务** 时：

- **客户端层**：请求地址、协议、端口、DNS 是否正确。
- **代理层**：正向/反向代理、网关、路径重写、header 转发是否正确。
- **服务层**：进程是否启动、端口是否监听、健康检查是否通过。
- **依赖层**：数据库、Redis、MQ、外部 API 是否可达。
- **观测层**：日志、指标、trace 是否能定位到失败点。

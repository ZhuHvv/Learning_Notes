## 1. 总体性概念

RPC 让远程调用像本地函数；gRPC 基于 HTTP/2 和接口定义文件，适合服务间强类型通信和流式调用。


## 2. 原理性解释

- REST 面向资源，RPC 面向方法。
- proto 定义 service/message。
- HTTP/2 支持多路复用。
- 调用必须处理超时、重试、鉴权和 tracing。

### RPC 关注“像调用本地函数一样调用远程服务”

HTTP REST 面向资源，RPC 面向过程/方法。gRPC 使用 Protobuf 描述接口和消息结构，通过 HTTP/2 支持多路复用、流式传输和强类型代码生成。它适合服务间调用，但对浏览器直接访问不如 REST 简单。

```proto
service UserService {
  rpc GetUser(GetUserReq) returns (GetUserResp);
}
```

## 3. 机制流程

1. 写 proto。
2. 生成代码。
3. 实现服务端。
4. 客户端调用。
5. context 传播。

### gRPC 调用流程

```text
编写 proto
  ↓
生成 client/server 代码
  ↓
客户端调用 stub 方法
  ↓
序列化 Protobuf
  ↓
HTTP/2 传输
  ↓
服务端反序列化并执行 handler
```

排查 gRPC 问题时看 proto 版本、连接超时、deadline、拦截器、服务发现和负载均衡。

## 4. 类比理解

RPC 像拨内线让另一个部门执行方法。

## 5. 应用举例 / 代码或伪代码

## 10. 更细的工程拆解

**RPC 与 gRPC：服务间调用** 需要放在“请求从客户端到服务再到下游依赖”的完整路径中看：

1. **入口层**：浏览器、客户端、代理、负载均衡、网关。
2. **服务层**：HTTP/RPC Handler、业务逻辑、连接池、缓存、数据库、MQ。
3. **运行层**：容器、Compose/Kubernetes、环境变量、挂载卷、网络策略。
4. **观测层**：日志、指标、trace、健康检查、告警。

### 最小部署/排障清单

```bash
# 1. 看容器是否运行
docker ps

# 2. 看端口是否监听
netstat -ano | findstr 9092

# 3. 看服务日志
docker logs <container>

# 4. 用 curl 验证入口
curl -v http://localhost:8080/health
```

### 工程落地要点

- 网络问题要分层排查：DNS、端口、代理、协议、认证、应用日志。
- Docker/Compose 里路径、端口、环境变量最容易出错，尤其 Windows 路径要注意冒号和绝对路径。
- 只要是线上服务，就必须有健康检查、结构化日志和关键指标，否则出错时只能猜。

## 11. 针对 `RPC 与 gRPC：服务间调用` 的专项排查

后端部署和网络问题必须分层定位。检查 **RPC 与 gRPC：服务间调用** 时：

- **客户端层**：请求地址、协议、端口、DNS 是否正确。
- **代理层**：正向/反向代理、网关、路径重写、header 转发是否正确。
- **服务层**：进程是否启动、端口是否监听、健康检查是否通过。
- **依赖层**：数据库、Redis、MQ、外部 API 是否可达。
- **观测层**：日志、指标、trace 是否能定位到失败点。

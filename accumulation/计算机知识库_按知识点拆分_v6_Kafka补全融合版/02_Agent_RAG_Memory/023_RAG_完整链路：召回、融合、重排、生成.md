## 1. 总体性概念

RAG 是把外部检索到的证据作为上下文交给 LLM 生成答案的完整工程链路，不只是向量库搜索。


## 2. 原理性解释

- 完整链路包括解析、切分、embedding、索引、query 改写、召回、RRF、rerank、压缩、生成和引用。
- metadata 过滤防止跨项目污染。
- 重排提升上下文质量。
- 生成阶段应基于证据回答，不知道就承认。

### RAG 是“检索系统 + 生成系统”的组合工程

RAG 的难点不在“把文档塞给模型”这一句，而在整条链路的每个环节都会影响最终答案：文档清洗、切分、embedding、索引、召回、融合、重排、上下文拼接、引用约束、生成后校验。任何一环质量差，都会表现为“模型胡说”或“明明文档里有但答不出来”。

```text
Garbage in retrieval → Garbage in generation
```

因此 RAG 调优要先定位问题发生在召回前、召回中、重排中还是生成阶段。

## 3. 机制流程

1. 上传/解析文档。
2. 切分并入向量库。
3. 用户提问。
4. 多路召回。
5. 融合与重排。
6. 生成答案并附来源。

def rag_answer(query):
    q = rewrite_query_if_needed(query)
    dense_hits = vector_search(embed(q), top_k=50)
    sparse_hits = bm25_search(q, top_k=50)

排查顺序：先看 topK 里有没有正确 chunk；有则看重排是否把它排前；仍有则看 prompt 是否过长或证据约束不明确。

def rag(question):
    q = rewrite(question)
    dense = vector_search(embed(q), top_k=30)
    sparse = bm25(q, top_k=30)
    fused = rrf([dense, sparse])
    docs = rerank(question, fused)[:8]
    return llm(question, context=compress(docs))

## 10. 更细的工程拆解

把 **RAG 完整链路：召回、融合、重排、生成** 放进 Agent 系统时，核心不是“让 LLM 多想几句”，而是要设计可追踪的状态机：

1. **State**：保存用户目标、当前计划、工具结果、检索证据、失败原因、是否结束。
2. **Policy**：决定下一步是调用工具、检索、反思、重试，还是输出 final answer。
3. **Memory / Evidence**：区分临时上下文、可长期复用经验、外部文档证据，避免把噪声写入长期记忆。
4. **Stop Condition**：防止无限循环，通常结合充分性、一致性、重复行动次数和最大步数。

### 最小 Agent 状态伪代码

```python
state = {
    "goal": user_query,
    "plan": [],
    "evidence": [],
    "tool_trace": [],
    "memory_hits": [],
    "final_answer": None,
    "stop_reason": None,
}

while not state["final_answer"]:
    decision = policy_llm(state)       # 选择 search/tool/reflect/final
    if decision.type == "tool":
        obs = run_tool(decision.name, decision.args)
        state["tool_trace"].append((decision, obs))
    elif decision.type == "retrieve":
        state["evidence"] += retriever(decision.query)
    elif decision.type == "reflect":
        state["memory_hits"] += reflect_and_retrieve(state)
    elif decision.type == "final":
        state["final_answer"] = decision.answer
```

### 工程落地要点

- 任何 Agent 范式都要落成“可序列化状态”，否则无法调试、恢复、缓存或流式输出。
- 对工具结果要保留原始 observation，不要只保留模型改写后的摘要。
- 对反思和记忆写入要加过滤条件，避免长期记忆被一次错误执行污染。

## 11. 针对 `RAG 完整链路：召回、融合、重排、生成` 的专项排查

在 Agent 工程里，判断 **RAG 完整链路：召回、融合、重排、生成** 是否设计正确，可以看四个问题：

- **状态是否显式**：计划、证据、工具轨迹、记忆命中、停止原因是否能被打印和回放。
- **工具调用是否可控**：是否限制最大步数、参数 schema、错误重试和超时。
- **证据是否可追溯**：最终回答能不能回到具体 observation、文档片段或 memory item。
- **失败是否可恢复**：失败后是直接结束，还是进入反思、重试、改写 query 或降级回答。

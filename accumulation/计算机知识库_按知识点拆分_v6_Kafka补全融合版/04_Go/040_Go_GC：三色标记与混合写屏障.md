## 1. 总体性概念

Go GC 使用三色标记和混合写屏障，在并发标记期间防止对象引用变化导致误回收。


## 2. 原理性解释

- 白色未访问，灰色待扫描，黑色已扫描。
- 写屏障在指针变更时补充标记。
- 删除旧引用时需保护旧对象可能引用的子图。
- 标灰不代表永不回收，只是本轮避免漏扫。

### 混合写屏障解决的是并发 GC 下的漏标问题

三色标记中，白色表示未扫描，灰色表示待扫描，黑色表示已扫描。如果用户程序和 GC 并发运行，黑色对象可能新增对白色对象的引用，导致白色对象明明可达却没被扫描，出现误回收。写屏障就是在指针写入/删除时插入额外标记逻辑，维持三色不变式。

你问“删除原本引用为什么要把原本被引用的标记成灰色”，核心是防止某个对象因为引用被删除后，其内部子对象还没来得及被扫描就丢失路径。

## 3. 机制流程

1. root 标灰。
2. 扫描灰对象。
3. 对象变黑。
4. 写屏障处理并发修改。
5. 清扫白对象。

### GC 流程抽象

```text
STW 短暂停顿，开启写屏障
  ↓
从 root 扫描，灰色队列推进
  ↓
并发标记：扫描灰色对象，标黑，并把子对象标灰
  ↓
处理写屏障记录，完成标记
  ↓
清扫白色不可达对象
```

Go 的 GC 目标不是“完全无停顿”，而是把停顿压短，同时让并发标记与用户 goroutine 交替运行。

## 10. 更细的工程拆解

**Go GC：三色标记与混合写屏障** 在 Go 后端中通常要和 Handler、Context、goroutine、连接池、日志与错误处理一起看：

1. **入口**：HTTP/RPC 请求进入 Handler 或 Middleware。
2. **依赖**：DB、Redis、Logger、Service 通常通过闭包、结构体或依赖注入传入。
3. **控制**：Context 负责超时、取消和跨函数传递请求级信息。
4. **退出**：错误要被明确返回或集中处理，goroutine 要避免泄露。

### 最小服务骨架

```go
type App struct {
    DB     *sql.DB
    Logger *log.Logger
}

func (a *App) Handler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()
    if err := a.DB.PingContext(ctx); err != nil {
        http.Error(w, "db unavailable", http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
}
```

### 工程落地要点

- 能通过参数传递的依赖，不要到处使用全局变量。
- 对外部 IO 使用 `context.WithTimeout`，否则请求取消后后端仍可能继续消耗资源。
- 中间件适合做认证、日志、错误收集、跨域和限流，不适合塞入复杂业务逻辑。

## 11. 针对 `Go GC：三色标记与混合写屏障` 的专项排查

Go 后端的关键不是只写出能跑的代码，而是保证请求生命周期、资源释放和并发安全。检查 **Go GC：三色标记与混合写屏障** 时：

- **请求路径**：请求从 router 到 middleware，再到 handler，最后到 service/dao，链路是否清楚。
- **Context 传播**：数据库、Redis、RPC 调用是否使用同一个请求 context 或带超时 context。
- **错误处理**：错误是返回、包装、记录，还是 panic；是否有统一错误响应。
- **并发安全**：共享 map、连接池、全局对象是否存在竞争或生命周期问题。
